# 777 智能体自我改进：实施边界与用户可见档案

> 架构依据：`docs/ARCHITECTURE.md`、`AGENTS.md`、`docs/SECURITY.md`、`docs/VALIDATION.md`。
> 本文记录分阶段范围；已计划功能不等于已实现或已验证。

## 默认认知与行动整合（2026-11-14，PR #903）

本轮在 #895 已有的发现记录、来源观察、Goal 延续与自我改进基础上直接增强：

- LocalAgentCognitionGuidance 为 Chat/Work 提供一致的默认认知原则；Chat 保留角色与用户风格，Work 保留工具授权，探索深度随任务自然变化，无新增 UI 模式。
- Work 模型可以根据真实工具结果调整假说和下一步动作；有价值的发现由原 work_finding 绑定真实工具回执，复杂场景的好奇、惊讶和兴奋由模型依据实际调查自然表达。
- 调查进度和最新发现跨越最近 320 条展示窗口仍能追溯；已读完的来源不再重复提示继续读取，全目标进度身份由原 Session EventLog 派生。
- 真实读取游标后又读取新范围可作为成功方法线索参与一次受控经验候选提炼；相同范围重复读取和未验证的假说不作为改进有效的证明。
- 只读 TaskGraph 重规划按任务、模型、权限、文件版本、依赖和来源结果复用仍然有效的节点；变更的节点与其下游重算，崩溃后沿现有恢复机制复查；可写任务继续沿用原副作用保护。
- 相关源码和 JVM 回归测试已写入 #903。实际 CI 和 Android 设备结果须以最终合并提交对应的运行回执判断，源码静态检查不等于运行通过。

对照 Codex 的模型工具循环、Checkpoint 与授权边界，以及 Claude 317 已提取的工具协作和交互机制，继续复用 777 的统一 Agent Runner、Session EventLog、ToolRegistry 与本地存储，不建立第二套探索引擎或新后台任务服务。反编译代码中的静态线索不意味着所有行为默认启用。

## 目标与 Owner

从真实 Work 执行证据形成可检验的经验、策略候选、提示词改进与技能建议，
在用户工作区持续展示，并为后续 App 工程迭代提供可追踪的问题线索。

- WorkFeature 解释 Work 执行、Goal、验收与策略改进；本机用户可见档案是 Work 所有的派生投影。
- Session EventLog 是执行历史的唯一事实源。档案 Markdown 不参与 Goal 完成判定、运行恢复、工具准入或策略采纳。
- Model/Agent/Tool/Resource/Usage 沿用现有唯一入口和 Owner。
- ToolsFeature 拥有技能配置变更和发布入口；用户规则与授权不会由模型自行改写。
- `harness-core` 只在真实复用需求成立后放入平台无关的候选/证据/比较纯逻辑，不提前引入第二执行引擎。
- 不扩张 `LocalRuntimeKernel`，不增加新顶层产品 Feature 或 Gradle module。

## 用户工作区档案（P0）

存放在现有应用私有工作区下的 `自我改进/`，没有外部同步：

| 文件 | 权限 | 含义 |
| --- | --- | --- |
| 00-自我改进总览.md | Work 自动生成 | 真实完成、问题与已采纳项目状态 |
| 01-经验与方法.md | Work 自动生成 | 经验与来源；无独立证据不能宣传为验证成功 |
| 02-改进与采纳.md | Work 自动生成 | 候选、基线、比较、采纳及回退 |
| 03-提示词优化.md | Work 自动生成 | Prompt 层次、版本、任务适用性及验证结果 |
| 04-问题与迭代.md | Work 自动生成 | 真实运行失败、交付问题与复现线索 |
| 05-验证与成效.md | Work 自动生成 | Goal/工具执行统计和真正可比较的质量指标 |
| 06-我的备注.md | **用户编辑** | 创建一次，系统永不自动覆盖 |
| 07-调查发现.md | Work 自动生成 | 当前发现、来源回执、调查状态与下一步，修订保留在 Session EventLog |

当前分支的 P0 工作区档案已扩展出 P1–P3 的受控实现：
- 对具有真实成果/测试凭据的 Work Goal，利用既有 Model/Usage 请求通道生成一次可溯源经验候选，并记录来源和限额；模型建议本身不算验证。
- 在同项目、同模型/配置、同 Goal 任务与验收签名的用户自然任务中，低优先级试用候选动态指导；不改写 System Prompt，不自动重放外部操作，续跑的同一 Goal 保持原候选。
- 对具备真实验证命令回执与可核实 Token 用量的前后任务运行，使用统一核心比较逻辑做窄作用域验证；负收益拒绝，无法比较则保留基线。该对照是自然发生的观察比较，并非随机实验，不能声称广泛泛化收益。
- 验收通过且类型为技能的候选只写入用户可见的未安装草案，真正安装/修改仍须经过 ToolsFeature 正式入口及授权。
- 当前分支尚未合并，须以最终提交对应的 CI 与设备验证为准，不得把此处的代码状态写成已发布结果。
系统生成文档明确显示未实现的采纳能力为“暂无记录”，确保用户能看出当前能力边界。
文档通过现有工作区的文件列表、预览、分享入口使用，不需要新文件系统或独立 UI 路由。

来源日志只读取可定位的事件类型，并按回合/Goal/工具回执计数；
报告不复制原始模型输出、Prompt 正文、工具参数、个人记忆或密钥。
摘要列表有界；完整历史仍在 Session EventLog。读写发生在 Work 持有的 IO scope，
文件写入沿用 `LocalWorkspace` 原子写入与路径边界。
用户笔记不参与自动同步、不作为策略采纳证据。

## Harness² 经验提炼起步准则（本 PR 已实现）

参考 Google Research [Harness²](https://github.com/google-research/harness2/tree/1cfe254e8d25b15f37048c3730134686abe60335)
的经验反思方法（[prompts.py](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/prompts.py)、
[library.py](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/library.py)）。
上游采用 `cue / lesson / evidence / confidence` 和领域索引，强调从实际执行差异归因，
证据不足时允许 `NO_ENTRY`，并明确认为单次未隔离变化不足以证明因果关系。

777 没有从上游导入已验证的通用经验（该仓库没有可直接移植的生产经验数据集）。
本 PR 新增 `WorkExperienceBootstrap.kt`，将理念独立实现为本机只读提炼准则：

- 工具错误事件 → 检查错误状态与不可安全重试的副作用；
- Goal 完成变更被拒绝 → 检查用户要求的交付和验收条件；
- 交付质量事件有冲突 → 核实完成声明与文件、工具、测试回执。
- 仅传入事件类别与聚合计数；**不复制**敏感工具输出、模型完整对话或验收答案给反思请求。
- 新增有来源的调查发现事件：模型可在当前 Work 任务中用 `work_finding` 关联精确已完成的工具回执，记录、修订、否定线索；同一线索以最新状态呈现于 `07-调查发现.md`。这份档案仍为事件日志的派生展示。
- 具备真实来源且最后状态仍为 `supported` 的调查记录可触发可复用调查**方法**候选；被否定的线索不再按成功发现提炼，记录本身不证明研究结论。
- 没有相应的真实异常事件或有来源的调查线索则不调用辅助模型；模型输出必须带已观察事件的 `evidence_tag`，
  否则丢弃候选；每 Goal revision 至多执行一次反思。
- 静态规则只辅助候选生成，在工作区《经验与方法》中标记为「方法模板，未验证经验」；
  **不预先激活或发布为正式策略、技能和 System Prompt**。
- 提炼结果仍为待验证候选，保持原 P1/P2 的基线对照、作用域校验和回退准入。

这种引导让 777 有明确的起步方法，同时不会因为某次成功任务产生不可靠的“伪经验”。

## P1：经验学习及运行时策略/提示词激活（后续）

- 从已结算 Work 运行中提取可溯源的经验候选；区分任务完成、机器验收和可归因的策略改善。
- Work 拥有策略持久事实，保存来源 Run/Goal/事件、作用域、适用环境、版本与状态；
  不将机器推断经验当作用户长期记忆，不复制另一个 Session EventLog。
- 已验证且适用的策略才通过现有 Work Prompt / Skill Guidance 入口激活。
- 每次执行的策略版本与模型路由冻结；用户规则、明确置顶技能和审批优先。
- 对跨项目/模型的迁移必须检查兼容性与失效条件。

## P2：受控候选比较和 Prompt 模板优化（后续）

- 有安全且可比较的测试工作负载时，保留旧版本作为基线，对候选进行独立验收。
- 按任务类型评价完成质量、真实工具结果、Token/成本、重复调用与返工；不以模型自评分替代结果。
- 在无可信独立验收、存在不可重放副作用或测试环境无隔离的情况下，不自动升级。
- 分开管理当前任务的动态指导与长期稳定模板；`PromptLayerComposer` 继续负责纯组合，
  不变成业务学习或权限解释器。
- 采用已验证候选须记录版本与效果，可失效与回退。正常 Work 资源额度不受优化试验侵占。

## P3：技能改进和长期开发迭代（后续）

## 模型工具调用习惯差异与契约纠错（首轮落地及后续范围）

777 的工具执行权限由现有 ToolsFeature / `ToolRegistry` 权威决定；Model Adapter 只转换
各供应商的工具调用协议，Work 只能解释任务及执行证据，不拥有第二个工具路由器。
因此不能为不同模型各自复制或松动一套工具契约。

**本轮实现（PR #839）：**

- 继续复用 `LocalModelToolCallValidation` 对工具调用 ID、JSON 参数对象、重复 ID 的硬校验；
  使用 `LocalToolPolicy.canonical` 已注册、明确、有限的旧别名，未知工具绝不模糊改名执行。
- `ToolRegistry` 在进入执行器前拒绝不符合实际 schema 的参数。此前向模型回报
  `INVALID_TOOL_ARGUMENTS` 时只有泛化指导；现在在确认 **executor 没有启动** 后，
  附上注册工具真实的必填字段与参数类型。执行已开始且存在副作用可能的错误，
  仍坚持先检查状态、禁止盲目重试。
- Work 的 `WorkExperienceBootstrap` 从权威 `tool/result` 的 `error_code` 汇总
  `UNKNOWN_TOOL`、`INVALID_TOOL_ARGUMENTS`、`TOOL_INVALID_ARGUMENT`，
  作为单独的 `tool_contract_error` 经验候选来源；不把超时、审批拒绝或设备错误混淆为
  模型不懂调用格式，也不会复制敏感参数内容给复盘模型。
- 已建立对应 JVM 测试：不合 Schema 的调用不启动 executor；返回真实字段指导；
  模型调用契约错误可与其他工具失败区分；敏感工具输出不进入反思提示词。

**尚待独立完成的端到端适配：**

- 对运行时模型协议（OpenAI Chat Completions、Responses、兼容接口等）分别运行
  工具名、嵌套字段、required/enum/array、并行调用、流式拼接、重复调用 ID 回归。
- 只从现有 Session EventLog 聚合匿名错误类别、工具契约版本与不可逆模型路由身份，
  建立「模型/协议 × 具体工具」失败率画像；不要引入第二个 Usage、Session 或审计账本。
- 对具有充分证据且同版本工具 schema 下的重复错误，试用窄作用域模型专属动态提示；
  采用前必须测量修正率、增加的 Token、重复失败与质量回归。不能无证据臆断哪个模型习惯。
- 可对确定为未开始执行的、语义完全等价的旧工具名别名进行规范化；
  不能模糊猜测权限、自动填入缺失值、替换有副作用命令、改变审批决定。
- 后续将匿名统计与错误纠正结果映射至工作区问题与迭代报告，暴露修复前后结果。

## 已有工具让模型真正使用：注册—发现—暴露—执行闭环（本 PR 继续补强）

- 命令入口继续由唯一 `ToolRegistry` 负责。Android Runtime 的进程/终端工具、
  LSP/GitHub/MCP 等扩展使用相同注册表；模型权限和本轮工具 Schema 是两个不同的准入条件。
- `LocalToolRouter` 保持核心工具常驻、可选能力按真实任务发现的策略；模型使用
  `capability_search` 明确发现某工具后，Work 的后续步骤**只追加**新发现的任务相关工具，
  不再重复把模糊关键词命中排到明确选择之前。下一次新的用户任务仍可重新排序。
- `LocalWorkRuntimeContext` 给模型简短的执行规则：只调用本轮真实工具表中的名字/参数，
  已注册但没暴露的工具先发现，下一步获得 Schema 后再执行；遇到不合法参数遵循当前 Schema，
  有副作用时不能盲目重放。
- 保留旧 `read_skill` / `list_skills` 命令的等价别名，
  均交给已注册 `skill` 能力的**同一** Schema、可见性、权限和审批边界。
  不再因为历史命令名与正式注册名不同而被误判不存在；不会自动猜测其他模型私有命令格式。
- 既有若干 Work/媒体执行入口仍返回展示字符串，本次只对**精确、明确的失败签名**
  转成 `ToolResult(isError=true,errorCode=...)`，避免失败内容被标记成功；
  对任意工具输出中碰巧出现错误关键词，不得推断该工具失败。
- 保留现有 `TOOL_NOT_EXPOSED`、`UNKNOWN_TOOL`、`INVALID_TOOL_ARGUMENTS`、
  `APPROVAL_DENIED`、`MUTATION_SCOPE_BLOCKED` 和副作用未知结果的不同处置策略。
  权限、审批、执行器和工具结果回执仍来自唯一 Tool Owner，不添加旁路执行器。
- 测试同时核验：工具可通过发现进入下一轮模型表并真正执行；显式发现优先级持续有效；
  历史技能命令采用正式契约；Work/媒体错误有真实失败码；普通输出不会误判错误。
  CI 和 Android 16/17 设备回归须以**最终 HEAD** 为准，不能沿用其他提交的结果。

## 后续代码级复查：批量可见性与混合模型目录结果

- Agent 核心调度器已经利用 `isParallelTool` 把未暴露的调用排除在并行批次之外；
  Work 的 `toolBatch` 回调此前本身没有再次校验冻结的本步骤模型工具表。
  现已在 `LocalWorkTurnToolRuntime.executeBatch` 为**每一个调用**提供统一
  `blockedCall` gate，串行/并行两种分组共同使用 `executeAdmittedWorkBatchCall`，
  并由 `LocalWorkAgentTurnExecutor` 按最新 `LocalModelToolStepSurface` 判定。
  因而即使以后改变 Agent 分组策略，也不能直接执行只注册、却未交给模型的工具。
- 新增回归覆盖：无效工具不会执行、并行组中只有暴露工具会执行、允许的旧别名
  继续共享真实注册名、用户修订后的旧调用不能进入执行。
- `list_subagent_models` 可在一次结果中同时包含真实本地档案和失败的在线供应商目录。
  之前只匹配输出开头导致在线目录失败没被正确标记，现使用该命令独有的
  「指定配置的官方模型目录」结果分隔标记识别，保留原本地目录并报告
  `MODEL_CATALOG_UNAVAILABLE`；一般 `read` 文件内容同样的文字不会被误判。
- 本阶段属于源码与 JVM 回归补强。实际不同 provider 的行为及 Android 设备结果
  仍按当前 HEAD 的完整 CI 与设备测试单独签收，不以更早的通过结果代替。

## 核心不变量

1. 任何模型陈述“优化成功”都不能改变事实；有正式验收与准入结果才可标记为生效。
2. 任何策略/提示词更新不能越过用户明确规则、系统安全边界和工具审批。
3. 不建立第二个 Agent Runner、Session/Run Owner、Usage 账本或恢复调度器。
4. 真实外部副作用不可通过候选 A/B 直接重放。现有 write_scopes 不是 OS 沙箱。
5. 恢复、取消、Session 删除/重置、日志 generation/identity 变化必须使过时结果失效。
6. 档案不是执行依据；遇到冲突以对应 Owner 的持久事实为准。
7. 用户备注永久独立于自动生成文件；自动失败不改变原任务状态。
