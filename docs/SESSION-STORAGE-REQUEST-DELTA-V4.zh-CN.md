# 777 会话证据增量存储 V4

## 问题与实现

2026-11-14 的实机调查中，5 个会话共包含 7,728 条事件，事件库约 190 MB；其中模型请求反复保存历史消息、随后对重复正文建立搜索索引，是主要可控增长源。原始调查文件：`自检报告/本地会话存储检查.md`。

### 新版请求写入

真实发送的模型请求继续由 `LocalModelRequestCoordinator` 构造和计算摘要，脱敏规则仍由 `redactModelImages` 管理。请求消息面由以下两种等价格式组成：

- 完整面：`{"version":4,"digest":"...","messages":[...],"redacted":false}`
- 增量面：`{"version":4,"digest":"...","base_surface_seq":123,"keep":60,"tail":[...],"depth":1,"redacted":false}`

`keep` 表示与前一完整消息面相同的前缀消息数；`tail` 是本次剩余消息。相较于完整面确实节省字节时才写入增量；连续 32 层之后强制生成完整检查点，避免长会话重放链无限增长。

请求头、工具面、上下文面、模型重试事件仍保留原始摘要和不可变引用序号。重放时逐层核验引用方向、层数、对象类型和 **重建后的完整消息摘要**。不允许使用破损链产生未经验证的证据。V1 证据级请求和 V2/V3 完整消息面保持可读。

`LocalRequestEvidenceSurfaceMemo` 只作为进程内加速层；首次请求或进程重启时，从事件日志恢复最后一次提交的消息面，避免重启后再存整段历史。写入锁保障并发下引用与记录的顺序。

### 旧版数据迁移和空间回收

`SqliteSessionEventDatabase` 数据库从 V5 升至 V6。SQLite 升级事务逐条验证 V2/V3 完整消息的 SHA-256，原位转成等价增量面，保留 `session_id + sequence`、时间、原始消息摘要、重试及请求头的引用。任何摘要错误会终止升级并由 SQLite 回滚。

只有权威事件内容发生变化，才清空可再生的 `session_search_blocks` / `session_search_coverage`；首次搜索自动重建，因此仍能检索原始记录过的内容。旧 JSONL 导入也使用同一份严格校验和增量转码逻辑。

成功迁移后留下可恢复的 `pending_vacuum` 标记，在应用启动的 IO 工作线程上调用原有 `compactAll()`：排他锁、WAL checkpoint、两个库的 `VACUUM` 全部成功之后清除标记；失败则保留标记以便下次启动继续。此行为由一次性数据库升级触发，不会创建周期任务。

会话删除仍通过 `session_event_cursors` 的外键级联回收事件及搜索索引，并清理 `tool-output` 和有关快照、恢复记录；工具结果与多媒体本体策略不受增量请求改变。

### 成本与边界

本方案以连续会话的增量请求为主要优化对象；当早期消息发生大规模重写，增量可能因不节省空间而回到完整快照，确保写入结构始终有效。每 32 次增量另存一次完整检查点，换取有上界的恢复成本。它不改变模型收到的消息、用量计费或工作状态投影。

`runtime/node`、`runtime/shared` 等目录已使用 SHA-256 共享库和硬链接。必须先按 inode、硬链接数和实际磁盘块核实物理重复量，再决定是否改造。这部分无需引入第二套运行时安装器。

## 验证路径

1. `LocalRequestMessageSurfaceTest`：120 次连续请求的持久化字节对比、每 11 轮重建、32 层检查点、重启继续增量、脱敏状态、篡改拒绝、V3 回放。
2. `LocalRequestReconstructionTest`：V4 请求头关联新消息面完整验证，同时回归 V1/V2/V3 旧请求。
3. `SqliteRequestDeltaMigrationAndroidTest`：真实 SQLite 的 V5→V6，迁移后重放、索引重建、同会话级联删除，损坏源数据下原子回滚。
4. CI：`Android 能力契约回归` 执行 JVM 单测、Android 测试代码编译及 Android 调试构建。设备端真实大小、写入耗时、旧库迁移时间应使用 `storageStatus` / SQLite `dbstat` 再核对。

## 注意事项

用户会话数据始终位于设备本地；迁移不联网、不创建远端归档。多媒体原始字节不会因请求证据增量存储而复制到事件日志。
