## 原本的工作链

1. **变更分类（scope）**：按文件风险选择静态检查、架构检查、单测、双 ABI APK、Android 16/17；产品 main 提交要求完整 CI，便于发布门禁引用。
2. **静态/架构门禁**：验证安全边界、Gradle/CI 供应链、功能树与源码索引一致性；同时编译 shell/Python 脚本并运行内建自测。
3. **主 CI**：独立跑 Kotlin/JVM 测试、ARM64 编译；x86 构建一组三种 APK，Android 16/17 启动时各自复用本次 CI 的测试产物。
4. **独立四组合矩阵**：原先又在另一个 Runner 上重复进行 x86 Debug、AndroidTest、Optimized 三个 APK 编译，随后依次执行 Android 16/17 × 4KB/16KB 真实设备十轮性能/功能对照。
5. **开发工具链**：为离线安装发布 JDK、Android SDK、Gradle 依赖、运行时及模拟器组件 Artifact；重新预热 JVM 单测、Lint 和 APK，并进行 build/full 两套安装回归。
6. **发布资格（Release APK）**：仅 main 完整 CI 成功且有新产品变更才能签名发版。正式 APK 继续独立签名、核对大小及完整性、制作差分更新并附校验和/清单。
7. **归档/清理**：保留最近三个正式 Release；退役 Release 使用显式留痕，避免错误重新发布已退役版本。

## 经代码核实的低效和根因

| 优先级 | 现象 | 根因 | 本轮处理 |
| --- | --- | --- | --- |
| P0 | 四组合矩阵重复构建三种 APK | 另一个工作流没有复用主 CI 的相同提交产物 | 同 SHA 查找并下载 CI Artifact，检查源提交、PR head 与三 APK SHA-256 |
| P0 | 已构建产物跨工作流存在错用风险 | 以前的等待脚本只检查文件非空，同源只靠 CI Run ID | 统一写入/验证 source-sha、head-sha、SHA256SUMS；未知/错版/损坏即失败 |
| P1 | 正式发布的 Runtime 下载不能可靠复用 CI 缓存 | release.yml 私有缓存键与 setup-runtime-cached 的键不同 | Release 直接使用同一个已验证运行时准备 Action，保持签名、哈希、ABI 检查 |
| P1 | 开发工具链频繁重复获取 Gradle 依赖 | 隔离的 GRADLE_USER_HOME 未复用 Gradle 依赖下载缓存 | 在测试前恢复、Gradle 预热后立即保存限定的依赖/包装器缓存 |
| P1 | 缺少正式签名材料时浪费构建准备时间 | 签名材料验证位于 JDK/SDK/Gradle/Runtime 安装之后 | 签名材料校验移到 release 作业 checkout 后 |
| P1 | 功能树机器人写回取消当前检查 | 产品功能树的源码指纹混入了 GitHub CI 工作流文件，纯 CI 修改也触发四份生成文件写回与检查取消 | 生成器和独立复核器都排除 `.github/` 控制平面，只跟踪产品与运行时源码；CI 脚本仍通过独立静态/安全检查，且新增自测防回退 |
| P2 | 双版本/四组合重复执行部分测试 | 独立性能矩阵与功能仪器测试口径不同，且四组合报告要求同一宿主 | 保留真实设备与十轮对照，不直接删除，也不将四组分散到不同 Runner |
| P2 | 工作流数量多 | CI、矩阵、工具链和发布的职责不同；Release 还需独立稳定签名 | 明确所有者/资格，避免用增加工作流数量来掩盖性能问题 |

## 本轮实施的可靠性约束

- `device-artifacts-x86` 一次性生成 Debug、AndroidTest、Optimized 包；写入每个 APK 的 SHA-256、真实 Git checkout SHA、PR 头 SHA。
- 两个主 CI 设备作业继续消耗 **同一 CI run** 的产物；原文件非空检查升级为内容哈希与真实提交校验。
- 四组合矩阵通过 `actions: read` 获取 **同一源码头与相同 checkout** 的 CI 产物。旧提交、另一 PR、损坏包、超时、CI 失败且未产出 Artifact 均显式报错，绝不借用最新成功构建替代。
- 独立四组合仍在一台 Runner、同一套 APK 上依次执行，继续用真实系统 `getconf PAGESIZE` 检验 4KB/16KB，保持 Android 16、17 和十轮性能样本的可信性。
- 发布代码继续经过正式签名、版本与发布门禁。统一 Runtime Action 消除缓存版本键分叉和未签名下载路径。
- 开发工具链仍跑全部模块测试和 build/full 安装测试，缓存只是提高同等验收的重复执行速度。

## 本次不做的“伪优化”

- 不将 4 台不同主机并行跑得的 FPS/内存值直接当成同一宿主对照数据。
- 不通过跳过仪器测试、减小十轮样本量或修改测试失败阈值让门禁变绿。
- 不将 PR CI 成功等同于正式 Release；仍严格遵循 main 完整 CI、签名与 APK/增量包验证。
- 不增设定时任务，不更改既有定时任务；也不借助隐藏的异常忽略路径。
- 不把 #892 尚未进入 main 的同 SHA 四组合正式发版要求、签名连续性检查和发布后资源复核标记成已交付。本 PR 应与 #892 合并审查冲突。

## 验收与实际提速的统计口径

1. `bash -n` 和 `wait-android-device-artifacts.sh --self-test` 必须通过，涵盖缺包、错 SHA、哈希篡改。
2. CI 静态/架构/完整单测和双 ABI 编译、Android 16/17 仪器检查全绿；源码索引与最新 HEAD 完全同步。
3. 四组合矩阵无需独立 Gradle 编译，产物为已验证的同 SHA CI artifact；四台设备环境组合逐项通过，仍产生完整比较与原始证据。
4. 工具链安装 build/full 回归、JDK Artifact 可用性检查通过。
5. 正式发布缓存复用和签名提前检查必须经过主线首次真实发布验证，无法以 PR 的单测推断签名流程已经成功。
6. 对比新/旧 workflow 的 *elapsed time*、缓存命中及四组设备的完成状态；区分墙钟耗时、runner 计算资源和排队耗时。
