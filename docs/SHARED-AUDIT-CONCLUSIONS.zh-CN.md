# 可共享审计结论库

> 本文件用于沉淀可以跨功能、跨模块、跨 PR、跨后续审计复用的系统级审计结论。
>
> 具体某个 PR、某个文件、某次故障的事实仍写在对应审计结果中；只有已经抽象为稳定规律、能够指导其他功能审计的结论才进入本文件。
>
> 使用时必须重新核对当前代码事实。共享结论用于指导检查范围和判断方法，不能替代对最新代码的实际审计。

## 1. 目的

全量系统联审不仅要发现当前问题，还要把已经验证过的通用规律沉淀下来，避免后续在其他功能中重复遗漏、重复研究、重复发现。

共享审计结论与具体问题分离：

```text
具体问题
→ 核实直接原因
→ 追到系统根因
→ 判断是否具备跨功能复用价值
→ 形成独立共享结论
→ 后续审计引用并重新验证
```

具体问题回答“这次哪里有问题”。

共享结论回答：

- 后续还应该到哪里找同类问题；
- 哪类局部正确不能证明系统正确；
- 哪些上下游、字段、配置、入口和生命周期必须成组检查；
- 什么证据才能判定真正闭环；
- 哪些实现差异容易再次形成旁路、漂移或最后一公里缺口。

---

## 2. 进入共享结论库的条件

满足以下任一条件才进入：

1. 同一根因已经影响两个及以上独立功能、入口或模块；
2. 某问题暴露出明确的系统级检查盲区，且该盲区适用于其他功能；
3. 某项架构、状态、数据或生命周期规律可以直接用于后续审计；
4. 修复后仍需要对其他同类路径做横向排查；
5. 已形成稳定的验证方法，可以作为后续审计的固定动作。

以下内容不进入：

- 单个页面的偶发视觉细节；
- 只适用于某个 Provider 的临时服务端异常；
- 一次性迁移问题且不存在其他调用路径；
- 尚未核实的推测；
- 只描述某次 PR 代码细节、没有可复用判断价值的结论。

---

## 3. 使用规则

每次系统联审先读取本文件，再执行当前代码审计。

共享结论只提供检查框架，实际判定仍必须遵循：

```text
最新 main / 目标 PR
→ 当前权威文档
→ 当前真实入口
→ 当前调用链
→ 当前字段 / 配置 / 状态
→ 当前测试与运行事实
```

引用共享结论时推荐写法：

```text
共享结论：SC-003 状态生产端成功不等于消费端闭环
本次证据：……
本次影响链：……
本次判定：仍存在 / 已闭环 / 不适用
```

不得因为某项共享结论曾经成立，就默认当前代码仍有同一问题。

# 4. 共享结论

## SC-001 完整功能必须按真实入口逐一闭环

### 结论

一个功能存在实现、单个入口可用、单测通过，都不能证明完整功能已经闭环。

必须先枚举所有真实触发入口，再逐个沿完整链路核实。

### 固定核查路径

```text
功能目标
→ 所有真实入口
→ 统一业务边界
→ 状态 / 数据
→ 副作用
→ 下游消费
→ 持久化 / 对账
→ 恢复
→ UI / 用户最终结果
```

真实入口至少考虑：

- 页面操作；
- 生命周期回调；
- App 前后台切换；
- 自动刷新；
- 后台任务；
- 定时任务；
- 恢复流程；
- 通知 / Deep Link；
- 快捷入口；
- 外部事件；
- 导入 / 同步。

### 重点风险

- 主入口完整，旁路只执行一半；
- 手动入口完整，自动入口漏后处理；
- 页面内调用走 Coordinator，生命周期回调直接调底层；
- 恢复入口没有执行正常路径中的对账逻辑。

### 完成标准

所有真实入口均进入正确的权威边界，或者差异具有明确设计依据和独立验证。

---

## SC-002 同一能力的多入口必须汇聚到统一编排边界

### 结论

同一能力如果存在多个调用入口，底层函数相同不代表语义相同。

一个高层编排通常还包含：

- 状态对账；
- 关联数据同步；
- 生命周期保护；
- busy gate；
- 失败分类；
- UI 投影；
- 后处理。

旁路直接调用更底层对象时，最容易形成“底层动作成功、业务结果没有完成”。

### 审计动作

对同一业务能力搜索全部调用方，比较调用层级：

```text
入口 A → Presentation / Coordinator → Runtime → Store
入口 B →                    Runtime → Store
入口 C →                              Store
```

如果不同入口调用层级不同，必须继续证明遗漏的上层语义是否确实不需要。

### 默认候选问题

以下结构默认进入候选问题复核：

```text
主路径 → 高层统一入口
旁路   → 底层具体实现
```

---

## SC-003 状态生产端成功不等于消费端闭环

### 结论

生产者成功更新状态，只能证明“状态被产生”。

完整功能还必须证明所有需要该状态的消费者实际获得并正确处理。

### 固定核查路径

```text
Producer
→ State / Event / DTO
→ Projection / Mapping
→ Store / Cache
→ Flow / Callback / Subscription
→ Consumer
→ UI / Secondary Feature
```

### 重点检查

- 更新后是否真正发出通知；
- Projection 是否丢字段；
- Consumer 是否订阅正确对象；
- Consumer 是否使用旧缓存；
- 页面重建后是否重新获得当前状态；
- 后台更新是否能传播到前台；
- 下游成功后上游是否仍显示旧值。

### 典型表现

- 数据库已经更新，页面仍旧；
- 远端目录已经刷新，本地选择器未变化；
- Worker 已完成，任务列表状态仍旧；
- Runtime 状态正确，UI projection 没有同步。

---

## SC-004 跨层字段契约必须逐字段对账

### 结论

同一业务数据经过多个 DTO、State、Event、JSON、数据库、Projection 或协议层时，必须逐字段核对，不能只确认对象类型大致一致。

### 必查项

- 字段名称；
- 类型；
- 可空性；
- 默认值；
- 单位；
- 枚举全集；
- 时间基准；
- ID 含义；
- 状态语义；
- 序列化 key；
- schema version；
- 新旧字段迁移；
- 缺失字段处理；
- 未知字段处理。

### 固定核查路径

```text
定义源
→ 写入模型
→ 序列化
→ 持久化
→ 读取
→ 转换
→ Projection
→ Consumer
```

任一层新增、删除或改名字段后，都必须检查所有下游消费者。

---

## SC-005 配置、常量和定义必须有唯一权威来源

### 结论

同一业务规则分散定义在多个位置时，即使当前数值一致，也已经具备漂移风险。

### 横向比较对象

- 默认值；
- 最大 / 最小值；
- 超时；
- 重试次数；
- feature flag；
- Provider capability；
- Model capability；
- Enum / sealed type；
- Schema；
- 数据库 / JSON key；
- UI 可选项；
- 测试 fixture；
- 文档说明；
- 构建配置；
- 协议版本。

### 判断

存在差异时必须明确属于：

```text
有依据的平台 / 协议差异
或
重复定义 / 配置漂移
```

禁止把多处定义默认解释为合理差异。

---

## SC-006 关联组件必须验证协同链，不能逐组件单独判绿

### 结论

多个组件分别正确，组合起来仍可能不完整。

审计必须额外检查“一个组件状态变化后，所有依赖该变化的关联组件是否都执行了对应动作”。

### 示例结构

```text
输入框聚焦
→ 输入区尺寸变化
→ IME inset
→ 页面可视区域变化
→ 列表滚动状态
→ 最后一条消息可见性
```

```text
模型目录变化
→ 账户状态
→ 远端目录
→ 本地 Profile
→ Active Profile
→ 模型选择器
→ Run 路由
```

### 审计重点

- 谁产生变化；
- 谁应感知变化；
- 通过什么机制传播；
- 谁负责对账；
- 是否存在顺序要求；
- 中间任一消费者缺失时用户最终感知什么。

---

## SC-007 “自动”能力必须验证最终业务状态

### 结论

后台动作被触发，不代表自动功能成立。

凡产品声明“自动刷新、自动同步、自动恢复、自动迁移、自动清理、自动重试”，必须验证到最终业务结果。

### 固定核查路径

```text
触发条件
→ 自动入口
→ 实际执行
→ 状态 / 数据对账
→ 下游消费
→ 失败处理
→ 延迟 / 重试
→ 最终用户结果
```

### 禁止的完成判断

- 定时器触发了；
- 网络请求成功了；
- refresh() 返回了；
- Worker 成功了；
- Store 写入了。

只有最终业务状态与用户可见结果达到预期，才算自动能力闭环。

---

## SC-008 生命周期路径必须与手动路径做语义对账

### 结论

onStart / onResume / 后台恢复 / 进程恢复 / 定时 Worker 等生命周期入口，经常只复用底层动作，没有复用完整业务语义。

因此所有生命周期路径都必须和对应手动路径比较。

### 比较内容

- 调用入口；
- 状态保护；
- 运行中 gate；
- 身份冻结；
- 数据对账；
- 错误分类；
- 取消行为；
- 最终 UI 更新。

### 重点场景

```text
手动刷新 vs App 回前台自动刷新
手动同步 vs 后台定时同步
正常启动 vs 进程恢复
页面内操作 vs 通知跳转
前台运行 vs 后台 Worker
```

---

## SC-009 依赖和导入路径也是功能契约的一部分

### 结论

同类功能通过不同层级对象调用，往往意味着部分路径绕过了统一业务规则。

因此审计不能只看运行结果，还必须比较依赖和 import。

### 检查

- UI 是否直接导入 Store / Service / Repository / Gateway；
- Feature 是否直接导入 sibling Feature internal；
- 是否绕过统一 Coordinator / Policy / Registry；
- 同类入口是否依赖不同层级对象；
- 是否存在直接构造而绕过单例 / 组合根；
- 新实现接管后旧依赖是否仍有调用方。

### 目标

同一业务能力原则上通过同一公开边界进入。

---

## SC-010 最后一公里属于功能正确性

### 结论

底层数据、状态和副作用都正确，如果最终没有正确传递到用户可见结果，功能仍未完成。

### 最后一公里包括

- UI projection；
- 列表位置；
- loading / success / failure；
- 页面返回状态；
- 通知；
- 可点击状态；
- 错误提示；
- 自动更新后的选择项；
- 恢复后的页面状态；
- 无障碍反馈。

### 审计要求

系统联审必须从底层结果反向追到用户最终看到的状态。

---

## SC-011 “已有能力”不能代替“完整接入”

### 结论

代码库中已经存在某个函数、Store、Coordinator、自动刷新器或测试，只能证明能力存在，不能证明目标功能真正接入。

### 必须区分

```text
能力存在
接入存在
主路径使用
所有入口使用
异常路径使用
恢复路径使用
最终结果闭环
```

审计发现“已有这个功能”时，应继续检查实际调用者和消费者，禁止提前结束。

---

## SC-012 修复一个同类问题后必须反向横扫同类入口

### 结论

当一个问题被确认属于入口旁路、状态未对账、字段漂移、配置漂移或关联组件未协同时，修复当前点后必须用根因反查其他功能。

### 横扫方式

例如根因是“直接调用底层 refresh 绕过统一对账”，则继续搜索：

- 同一 refresh 的全部调用方；
- 其他同类 refresh；
- 生命周期中的直接底层调用；
- 后台 Worker 的直接调用；
- 恢复代码中的直接调用。

### 完成标准

当前问题修复 + 同类路径排查 + 无遗漏证据 + 对应回归保护。

# 5. 共享结论与具体问题的分工

具体审计报告继续记录：

- 涉及文件；
- 当前实现；
- 直接问题；
- 本次根因；
- 本次影响链；
- 用户实际感知；
- 本次修复方向。

共享结论库记录：

- 通用规律；
- 通用检查动作；
- 适用范围；
- 容易遗漏的路径；
- 完成判定。

同一个具体问题可以引用多个共享结论。

例如：

```text
问题：某自动刷新只更新远端状态，本地选择器未同步

引用：
SC-001 完整功能必须按真实入口逐一闭环
SC-002 多入口必须汇聚统一编排边界
SC-003 状态生产端成功不等于消费端闭环
SC-007 自动能力必须验证最终业务状态
SC-008 生命周期路径必须与手动路径做语义对账
```

# 6. 维护规则

新增共享结论前必须确认没有与现有条目重复。

相似结论优先合并，避免结论库本身碎片化。

每条结论应保持：

- 单一主题；
- 可独立引用；
- 可独立执行；
- 可独立判定；
- 不依赖某次 PR 才能理解。

当架构变化导致结论失效时：

- 明确标记废弃或被哪个新结论替代；
- 不静默删除历史判断依据；
- 后续审计使用新的当前规则。

共享结论库本身也必须定期去重、合并和复核。
