# 可共享审计结论库

> 本文件用于沉淀可以跨功能、跨模块、跨 PR、跨后续审计复用的系统级审计结论。
>
> 具体某个 PR、某个文件、某次故障的事实仍写在对应审计结果中；只有已经抽象为稳定规律、能够指导其他功能审计的结论才进入本文件。
>
> 使用时必须重新核对当前代码事实。共享结论用于指导检查范围和判断方法，不能替代对最新代码的实际审计。

## 1. 目的

全量系统联审不仅要发现当前问题，还要把已经验证过的通用规律沉淀下来，避免后续在其他功能中重复遗漏、重复研究、重复发现。

共享审计结论与具体问题分离：

```text
具体问题
→ 核实直接原因
→ 追到系统根因
→ 判断是否具备跨功能复用价值
→ 形成独立共享结论
→ 后续审计引用并重新验证
```

具体问题回答“这次哪里有问题”。

共享结论回答：

- 后续还应该到哪里找同类问题；
- 哪类局部正确不能证明系统正确；
- 哪些上下游、字段、配置、入口和生命周期必须成组检查；
- 什么证据才能判定真正闭环；
- 哪些实现差异容易再次形成旁路、漂移或最后一公里缺口。

---

## 2. 进入共享结论库的条件

满足以下任一条件才进入：

1. 同一根因已经影响两个及以上独立功能、入口或模块；
2. 某问题暴露出明确的系统级检查盲区，且该盲区适用于其他功能；
3. 某项架构、状态、数据或生命周期规律可以直接用于后续审计；
4. 修复后仍需要对其他同类路径做横向排查；
5. 已形成稳定的验证方法，可以作为后续审计的固定动作。

以下内容不进入：

- 单个页面的偶发视觉细节；
- 只适用于某个 Provider 的临时服务端异常；
- 一次性迁移问题且不存在其他调用路径；
- 尚未核实的推测；
- 只描述某次 PR 代码细节、没有可复用判断价值的结论。

---

## 3. 使用规则

每次系统联审先读取本文件，再执行当前代码审计。

共享结论只提供检查框架，实际判定仍必须遵循：

```text
最新 main / 目标 PR
→ 当前权威文档
→ 当前真实入口
→ 当前调用链
→ 当前字段 / 配置 / 状态
→ 当前测试与运行事实
```

引用共享结论时推荐写法：

```text
共享结论：SC-003 状态生产端成功不等于消费端闭环
发现范围：定义 / 调用方 / writer / reader / 注册点
本次证据：……
负向验证：已经排除哪些相邻路径
本次影响链：……
完成证据：……
本次判定：仍存在 / 已闭环 / 不适用
```

每次引用至少给出“发现范围 + 正向证据 + 负向验证 + 完成证据”中的适用项，禁止只写“符合 SC-xxx”。

不得因为某项共享结论曾经成立，就默认当前代码仍有同一问题。

## 4. 共享结论（按同类归组）

> 共享结论编号保持稳定，分组只用于阅读和审计定位。后续新增结论优先放入对应主题，避免再次按新增时间堆叠。共享结论负责补足最容易跨功能重复漏审的细节，不替代主规范。

### 4.1 功能链路、入口、生命周期与最终闭环

这一组用于判断“功能是否真正接入并形成完整链路”，重点覆盖多入口、关联组件、自动路径、生命周期和最后一公里。

### SC-001 完整功能必须按真实入口逐一闭环

#### 结论

一个功能存在实现、单个入口可用、单测通过，都不能证明完整功能已经闭环。

必须先枚举所有真实触发入口，再逐个沿完整链路核实。

#### 固定核查路径

```text
功能目标
→ 所有真实入口
→ 统一业务边界
→ 状态 / 数据
→ 副作用
→ 下游消费
→ 持久化 / 对账
→ 恢复
→ UI / 用户最终结果
```

真实入口至少考虑：

- 页面操作；
- 生命周期回调；
- App 前后台切换；
- 自动刷新；
- 后台任务；
- 定时任务；
- 恢复流程；
- 通知 / Deep Link；
- 快捷入口；
- 外部事件；
- 导入 / 同步。

#### 重点风险

- 主入口完整，旁路只执行一半；
- 手动入口完整，自动入口漏后处理；
- 页面内入口走 Feature-owned 稳定 API / Port，生命周期回调却直接穿透 internal / Shared 实现；
- 恢复入口没有执行正常路径中的对账逻辑。

#### 完成标准

所有真实入口均进入正确的权威边界，或者差异具有明确设计依据和独立验证。

---

### SC-002 同一能力的多入口必须汇聚到统一编排边界

#### 结论

同一能力如果存在多个调用入口，底层函数相同不代表语义相同。

一个高层编排通常还包含：

- 状态对账；
- 关联数据同步；
- 生命周期保护；
- busy gate；
- 失败分类；
- UI 投影；
- 后处理。

旁路直接调用更底层对象时，最容易形成“底层动作成功、业务结果没有完成”。

#### 审计动作

对同一业务能力搜索全部调用方，比较调用层级：

```text
入口 A → Feature API / Port → Feature Owner → Shared Capability（如适用）
入口 B → Feature internal
入口 C → Shared / Store / Platform 具体实现
```

审计关注的是“是否绕过权威 Owner 与公开边界”，不能用旧式固定层数判断正确性。如果入口 B / C 绕过 Feature 所有权、状态对账、策略或生命周期语义，默认进入候选问题复核。

#### 默认候选问题

以下结构默认进入候选问题复核：

```text
主路径 → 高层统一入口
旁路   → 底层具体实现
```

### SC-006 关联组件必须验证协同链，不能逐组件单独判绿

#### 结论

多个组件分别正确，组合起来仍可能不完整。

审计必须额外检查“一个组件状态变化后，所有依赖该变化的关联组件是否都执行了对应动作”。

#### 示例结构

```text
输入框聚焦
→ 输入区尺寸变化
→ IME inset
→ 页面可视区域变化
→ 列表滚动状态
→ 最后一条消息可见性
```

```text
模型目录变化
→ 账户状态
→ 远端目录
→ 本地 Profile
→ Active Profile
→ 模型选择器
→ Run 路由
```

#### 审计重点

- 谁产生变化；
- 谁应感知变化；
- 通过什么机制传播；
- 谁负责对账；
- 是否存在顺序要求；
- 中间任一消费者缺失时用户最终感知什么。

---

### SC-007 “自动”能力必须验证最终业务状态

#### 结论

后台动作被触发，不代表自动功能成立。

凡产品声明“自动刷新、自动同步、自动恢复、自动迁移、自动清理、自动重试”，必须验证到最终业务结果。

#### 固定核查路径

```text
触发条件
→ 自动入口
→ 实际执行
→ 状态 / 数据对账
→ 下游消费
→ 失败处理
→ 延迟 / 重试
→ 最终用户结果
```

#### 禁止的完成判断

- 定时器触发了；
- 网络请求成功了；
- refresh() 返回了；
- Worker 成功了；
- Store 写入了。

只有最终业务状态与用户可见结果达到预期，才算自动能力闭环。

---

### SC-008 生命周期路径必须与手动路径做语义对账

#### 结论

onStart / onResume / 后台恢复 / 进程恢复 / 定时 Worker 等生命周期入口，经常只复用底层动作，没有复用完整业务语义。

因此所有生命周期路径都必须和对应手动路径比较。

#### 比较内容

- 调用入口；
- 状态保护；
- 运行中 gate；
- 身份冻结；
- 数据对账；
- 错误分类；
- 取消行为；
- 最终 UI 更新。

#### 重点场景

```text
手动刷新 vs App 回前台自动刷新
手动同步 vs 后台定时同步
正常启动 vs 进程恢复
页面内操作 vs 通知跳转
前台运行 vs 后台 Worker
```

---

### SC-010 最后一公里属于功能正确性

#### 结论

底层数据、状态和副作用都正确，如果最终没有正确传递到用户可见结果，功能仍未完成。

#### 最后一公里包括

- UI projection；
- 列表位置；
- loading / success / failure；
- 页面返回状态；
- 通知；
- 可点击状态；
- 错误提示；
- 自动更新后的选择项；
- 恢复后的页面状态；
- 无障碍反馈。

#### 审计要求

系统联审必须从底层结果反向追到用户最终看到的状态。

---

### SC-011 “已有能力”不能代替“完整接入”

#### 结论

代码库中已经存在某个函数、Store、Coordinator、自动刷新器或测试，只能证明能力存在，不能证明目标功能真正接入。

#### 必须区分

```text
能力存在
接入存在
主路径使用
所有入口使用
异常路径使用
恢复路径使用
最终结果闭环
```

审计发现“已有这个功能”时，应继续检查实际调用者和消费者，禁止提前结束。

---

### SC-012 修复一个同类问题后必须反向横扫同类入口

#### 结论

当一个问题被确认属于入口旁路、状态未对账、字段漂移、配置漂移或关联组件未协同时，修复当前点后必须用根因反查其他功能。

#### 横扫方式

例如根因是“直接调用底层 refresh 绕过统一对账”，则继续搜索：

- 同一 refresh 的全部调用方；
- 其他同类 refresh；
- 生命周期中的直接底层调用；
- 后台 Worker 的直接调用；
- 恢复代码中的直接调用。

#### 完成标准

当前问题修复 + 同类路径排查 + 无遗漏证据 + 对应回归保护。


---

### SC-014 注册、声明与装配属于功能链的一部分

#### 结论

代码实现和调用链存在，并不能证明功能已经进入真实生产运行。

DI、composition root、Feature / Page / Tool / Worker / Registry 注册、Manifest / 权限、导航和 serializer / codec 等装配环节都属于功能契约。

任何一个注册点遗漏，都可能形成“代码存在、测试能直接调用、用户实际入口不可用”。

#### 固定核查路径

```text
实现类 / API
→ 构造 / DI provider
→ composition root
→ Registry / Catalog / contribution
→ Manifest / permission / navigation / Worker
→ 真实生产入口
→ 生命周期 / 恢复
→ 用户结果
```

#### 必查项

- DI binding / provider 是否指向唯一权威实现；
- production 与 debug / test 装配是否不同；
- Feature / Page / Tool / MCP / Worker / Job 是否真实注册；
- serializer / codec / schema 是否加入生产路径；
- Manifest、权限、intent/filter、deep link、foreground service 声明是否完整；
- navigation、Back、Drawer、restore contribution 是否配套；
- 新实现接管后旧 provider、旧 registry、旧 worker、旧 serializer 是否退出；
- 是否存在两个实现都被 composition root 注入的双 Owner。

#### 完成标准

实现存在 + 生产装配存在 + 注册唯一 + 声明完整 + 恢复入口存在 + 旧装配退出 + 真实入口验证通过。

---

### SC-017 异步结果必须验证身份、顺序与失效条件

#### 结论

异步任务只校验“请求完成”仍不够。

结果写回前必须证明它仍属于当前合法操作，并且没有被更晚请求、Owner 切换、取消、超时或恢复流程淘汰。

#### 固定核查路径

```text
触发
→ requestId / runId / generation / owner
→ 并发执行
→ 乱序 / timeout / cancel
→ 页面 / Session / Account / Model 切换
→ 结果返回
→ 提交前再次校验身份
→ 持久化 / UI
```

#### 对抗场景

- ABA：同一身份离开后又返回；
- 同渠道后发先回；
- 不同渠道并行；
- 重复点击 / 重复 Worker；
- 新 Owner 接管旧任务；
- 取消后迟到成功；
- timeout 后后台仍完成；
- 配置 / 模型切换后旧结果返回；
- 进程恢复与旧 Runtime 同时尝试提交。

#### 完成标准

唯一身份贯穿 + 顺序规则明确 + 取消真实传播 + 迟到结果拒绝 + 重复副作用受控 + 恢复 Owner 唯一 + 对抗测试覆盖。

### 4.2 数据、状态与字段契约

这一组用于判断数据是否完整流转、消费端是否闭环，以及跨层字段语义是否保持一致。

### SC-003 状态生产端成功不等于消费端闭环

#### 结论

生产者成功更新状态，只能证明“状态被产生”。

完整功能还必须证明所有需要该状态的消费者实际获得并正确处理。

#### 固定核查路径

```text
Producer
→ State / Event / DTO
→ Projection / Mapping
→ Store / Cache
→ Flow / Callback / Subscription
→ Consumer
→ UI / Secondary Feature
```

#### 重点检查

- 更新后是否真正发出通知；
- Projection 是否丢字段；
- Consumer 是否订阅正确对象；
- Consumer 是否使用旧缓存；
- 页面重建后是否重新获得当前状态；
- 后台更新是否能传播到前台；
- 下游成功后上游是否仍显示旧值。

#### 典型表现

- 数据库已经更新，页面仍旧；
- 远端目录已经刷新，本地选择器未变化；
- Worker 已完成，任务列表状态仍旧；
- Runtime 状态正确，UI projection 没有同步。

---

### SC-004 跨层字段契约必须逐字段对账

#### 结论

同一业务数据经过多个 DTO、State、Event、JSON、数据库、Projection 或协议层时，必须逐字段核对，不能只确认对象类型大致一致。

#### 必查项

- 字段名称；
- 类型；
- 可空性；
- 默认值；
- 单位；
- 枚举全集；
- 时间基准；
- ID 含义；
- 状态语义；
- 序列化 key；
- schema version；
- 新旧字段迁移；
- 缺失字段处理；
- 未知字段处理。

#### 固定核查路径

```text
定义源
→ 写入模型
→ 序列化
→ 持久化
→ 读取
→ 转换
→ Projection
→ Consumer
```

任一层新增、删除或改名字段后，都必须检查所有下游消费者。

### SC-016 兼容性必须覆盖旧、新、未知与混合数据

#### 结论

“当前版本数据能读写”只能证明当前 happy path。

涉及持久化、协议、导入导出或历史会话时，必须同时验证旧数据、新数据、未知字段 / 事件、混合 schema 和非法版本。

#### 固定核查路径

```text
旧数据读取
→ normalize / migrate
→ 当前模型
→ 当前写回
→ 再读取
→ 未知字段 / 事件
→ 混合新旧字段
→ 非法 version
→ 恢复 / 导入 / 导出
```

#### 必查项

- encode / persist / decode round-trip；
- 未知 JSON 字段的契约行为；
- 未知事件 / 内容类型 passthrough 或诊断；
- 无 schema / 旧 schema / 新 schema 混合；
- 新版已编辑值不能被旧字段回写覆盖；
- 非法 version 不得静默伪装为旧版本；
- migration 重复执行必须幂等；
- 协议 baseline 升级同步 fixture、锁定来源和 conformance；
- 历史恢复不能因新字段缺失而中断。

#### 完成标准

旧数据可读 + 当前数据可写 + 写回不丢信息 + 未知内容安全处理 + 混合版本规则明确 + 非法版本明确失败 + migration 幂等 + 回归覆盖。

### 4.3 配置、依赖与所有权

这一组用于判断业务规则、配置和依赖边界是否存在重复事实源、配置漂移、跨层旁路或错误上收 Shared。

### SC-005 配置、常量和定义必须有唯一权威来源

#### 结论

同一业务规则分散定义在多个位置时，即使当前数值一致，也已经具备漂移风险。

#### 横向比较对象

- 默认值；
- 最大 / 最小值；
- 超时；
- 重试次数；
- feature flag；
- Provider capability；
- Model capability；
- Enum / sealed type；
- Schema；
- 数据库 / JSON key；
- UI 可选项；
- 测试 fixture；
- 文档说明；
- 构建配置；
- 协议版本。

#### 判断

存在差异时必须明确属于：

```text
有依据的平台 / 协议差异
或
重复定义 / 配置漂移
```

禁止把多处定义默认解释为合理差异。

---

### SC-009 依赖和导入路径也是功能契约的一部分

#### 结论

同类功能通过不同层级对象调用，往往意味着部分路径绕过了统一业务规则。

因此审计不能只看运行结果，还必须比较依赖和 import。

#### 检查

- UI 是否直接导入 Store / Service / Repository / Gateway；
- Feature 是否直接导入 sibling Feature internal；
- 是否绕过该能力所属 Owner 的公开 Port / Policy / Registry；
- 同类入口是否依赖不同层级对象；
- 是否存在直接构造而绕过单例 / 组合根；
- 新实现接管后旧依赖是否仍有调用方。

#### 目标

同一业务能力通过其权威 Owner 的公开边界进入；Feature-owned 能力不因多个消费者就上收到 Shared，Shared-owned 能力也不得反向解释 Feature 领域规则。

---

### SC-013 跨功能通用配置必须收口到共享权威配置

#### 结论

当两个及以上功能、模块或入口维护同一业务语义的配置时，审计必须判断能否提取为共享配置。

确认属于真正中立的跨领域配置后，应建立唯一权威配置来源，各功能按需读取，禁止继续各自维护一套相同配置。

如果配置具有明确 Feature 业务语义，即使被多个功能消费，也应继续由该 Feature 拥有，通过稳定 Port / Feature API 对外提供；消费者数量不能改变业务所有权。

“当前数值相同”不能作为继续分散维护的理由；多份独立定义本身就会形成后续漂移风险。

#### 固定核查路径

```text
搜索配置定义
→ 找到全部生产者 / 写入者 / 消费者
→ 按业务语义归类
→ 判断是否真正同一配置
→ 判断作用域与生命周期
→ 确定唯一共享 Owner
→ 各功能改为读取共享配置
→ 清理重复定义 / 重复持久化
→ 验证更新传播、迁移、恢复和回归
```

#### 优先识别的通用配置

重点横扫：

- 默认值；
- 最大 / 最小值；
- 超时与重试；
- 数量、大小、时间、Token、并发等预算；
- feature flag；
- 能力开关；
- Provider / Model capability；
- 公共 Enum / 状态集合；
- Schema / JSON key / version；
- 资源限制；
- 调度策略参数；
- 缓存容量与失效规则；
- 安全 / 审批 / 权限策略；
- 同类 UI 选项背后的业务配置；
- 多功能共同读取的持久化设置。

#### 所有权与共享判定

先判断业务 Owner，再判断是否进入 Shared。

```text
有明确 Feature 业务语义
→ 继续由该 Feature 拥有
→ 通过稳定 Port / Feature API 对外暴露最小配置能力

真正中立、跨领域
+ 更新应影响多个 Feature
+ 生命周期可由中立 Owner 管理
+ 权限 / 安全边界一致
+ 不解释任何 Feature 专属业务规则
→ 才进入 Shared Capability
```

共享配置可放在中立的 Configuration / Policy / Registry / Capability 数据源中。

Feature 只能通过公开接口读取自己需要的最小配置视图，禁止为了共享配置反向依赖其他 Feature internal。

SettingsFeature 只负责设置体验和配置入口；真实配置所有权仍归对应 Feature 或 Shared Capability。

#### 不应强行上收 Shared 的情况

以下情况应保留原业务 Owner，或允许独立维护，但必须有明确依据：

- 配置具有明确 Feature 专属业务语义；
- 业务含义实际不同；
- 生命周期不同；
- Provider / 协议契约不同；
- 平台能力不同；
- 权限或安全边界不同；
- 一个值只是恰好相同，未来变化方向并不一致。

禁止只根据“字段名相似”或“当前数值相同”强行合并。

#### 单一事实源要求

共享配置形成后：

- 只有共享 Owner 可以维护权威值；
- 各功能不得保留可独立修改的副本；
- 运行中的任务可以冻结配置快照，但快照只属于该次 Run 生命周期；
- UI / Projection 可以缓存派生视图，但不得写回成为第二事实源；
- 测试 fixture 应优先从同一配置契约生成或引用，不再复制业务常量；
- 文档中的固定值应指向权威配置或明确由当前实现生成，避免文档再维护第二份事实。

#### 配置变更闭环

共享配置变化时必须继续检查：

```text
权威配置变更
→ 持久化 / version
→ 缓存失效
→ 所有消费者
→ 后台 / 前台
→ 恢复
→ UI 投影
→ 新 Run / 已启动 Run 的冻结语义
```

必须明确哪些变化立即生效，哪些只对下一次 Run 生效。

#### 审计输出要求

发现重复配置时，最终问题必须明确：

1. 重复配置出现在哪些功能 / 文件；
2. 是否属于同一业务语义；
3. 正确的业务 Owner 是 Feature 还是 Shared Capability；
4. 当前有几个事实源 / 写入点；
5. 是否应统一提取；若为 Feature-owned，应通过哪个稳定 Port / API 暴露；
6. 推荐的唯一 Owner / 边界；
7. 哪些消费者应改为按需读取；
8. 哪些旧定义、旧持久化或旧缓存应退出；
9. 若不能共享，保留独立配置的明确依据。

#### 完成标准

```text
可共享配置已识别
+ 业务 Owner 判定正确
+ 唯一权威来源已确定
+ 各功能通过正确边界统一读取
+ 重复定义 / 重复持久化退出
+ 运行期快照边界明确
+ 更新传播 / 缓存失效 / 恢复已验证
+ 独立配置差异有明确依据
```

### 4.4 验证证据与完成判定

这一组用于防止“代码看起来正确、旧 CI 也绿，所以直接判完成”。

### SC-015 验证证据必须匹配风险并绑定当前 Head

#### 结论

验证是否执行过不等于结果成立。

每个结论都必须使用与改动风险匹配的验证路径，并且验证结果必须属于当前最新 Head；代码、依赖、主线、fixture、配置或门禁变化后，旧结果不能继续作为完成证据。

#### 固定核查路径

```text
改动范围
→ 风险分类
→ 当前 VALIDATION 要求
→ static / architecture gates
→ unit / conformance
→ build / artifact
→ device
→ merge gate
→ 当前 Head 再核
```

#### 必查项

- 产品源码、资源、Gradle、Runtime 改动是否走完整产品 CI；
- 架构改动是否经过 architecture-3-gates；
- 协议改动是否覆盖全部已注册协议语义；
- fixture / 上游锁定来源变化是否经过 provenance / reference-validation；
- UI / UX 风险是否做真实设备复验；
- Android 16 / 17、arm64、x86_64 等当前规定矩阵是否适用并完成；
- 测试是否验证状态、持久化、副作用、取消、恢复和身份隔离，不只断言返回值；
- PR Head 变化后是否重新验证。

#### 完成标准

风险识别正确 + 验证路径匹配 + 当前 Head 全部证据有效 + 设备风险有设备证据 + 无旧结果冒充当前结果。

## 5. 共享结论与具体问题的分工

具体审计报告继续记录：

- 涉及文件；
- 当前实现；
- 直接问题；
- 本次根因；
- 本次影响链；
- 用户实际感知；
- 本次修复方向。

共享结论库记录：

- 通用规律；
- 通用检查动作；
- 适用范围；
- 容易遗漏的路径；
- 可共享配置与唯一事实源治理要求；
- 完成判定。

同一个具体问题可以引用多个共享结论。

例如：

```text
问题：某自动刷新只更新远端状态，本地选择器未同步

引用：
SC-001 完整功能必须按真实入口逐一闭环
SC-002 多入口必须汇聚统一编排边界
SC-003 状态生产端成功不等于消费端闭环
SC-007 自动能力必须验证最终业务状态
SC-008 生命周期路径必须与手动路径做语义对账
```

## 6. 维护规则

新增共享结论前必须确认没有与现有条目重复。

相似结论优先合并，避免结论库本身碎片化。

每条结论应保持：

- 单一主题；
- 可独立引用；
- 可独立执行；
- 可独立判定；
- 不依赖某次 PR 才能理解。

当架构变化导致结论失效时：

- 明确标记废弃或被哪个新结论替代；
- 不静默删除历史判断依据；
- 后续审计使用新的当前规则。

共享结论库本身也必须定期去重、合并和复核。
