# 777 本地存储统一架构与分阶段实施

## 已确认的边界

- **SQLite 是核心业务数据权威**：会话目录、消息历史、Session EventLog、Work/工具事实、用量和持久化恢复游标应通过正式存储接口读取和更新，禁止以旧 JSONL 文件扫描结果替代 SQLite 枚举。
- **JSON/Markdown 仍然是合法文档格式**：技能 SKILL.md、用户设置导出、经验归档、提示词和可版本化模板可以保留为文件。它们不能充当与 SQLite 冲突的第二份权威会话状态。
- **大体积图片、视频及音频优先保存在应用私有本地文件**；SQLite 管理其资源标识、归属、哈希、字节数、媒体类型、引用和状态。缩略图/小图可根据设备实测结果采用 BLOB。
- **仅使用本地存储**；不引入云端同步或自行运营的服务器。外部 API 连接遵循既有用户授权边界。

## P0：当前 PR 立即生效的修复

- 图片回收的会话全集取自 SQLite Session EventLog 的 `historicalSources()`、SQLite 会话摘要、当前会话及待处理编辑器；不再扫描 `*.events.jsonl`。
- 对每个会话分别读取可恢复快照和完整事件引用；前台模型历史单独保留。历史读操作使用独立 reader，不挤占前台 EventLog LRU。
- 任一权威来源读取失败时**终止整个回收批次**；只有引用集合完整时才允许开始删除。后台执行，失败不记录成功的清理时间。
- 活跃 Work/前台模型运行期间不回收；存在尚未纳入数据库的编辑草稿时暂停回收，优先保护图片。
- 配额回收增加一小时新资源保护期，避免文件写入与事件提交之间的短暂空窗导致图片被删除。
- Android SQLite-only 历史会话 + JVM 跨会话引用、快照引用、异常阻断及容量压力测试作为基本回归。

**注意**：上述实现仍基于按需扫描已提交的 SQLite 事件和会话快照。它是纠正危险的旧文件枚举路径的第一阶段；尚未宣称完成持久化资产索引或全部附件种类的迁移。

## P1：SQLite 资产目录（下一阶段）

建议采用与会话权威同属一个一致性边界的数据模型：

```text
assets(
  asset_id PRIMARY KEY, content_sha256 UNIQUE, media_type, byte_size,
  storage_kind, storage_path NULL, blob_payload NULL,
  created_at, state, schema_version
)
asset_references(
  session_id, message_id, asset_id, reference_kind,
  PRIMARY KEY(session_id, message_id, asset_id, reference_kind)
)
```

- `assets` 是资源清单；`asset_references` 是引用关系。单资源可被多会话、多消息复用；禁止仅凭删除一个会话就删除共享原图。
- BLOB 与文件路径互斥，文件必须局限于受控的本地资源根目录，校验路径、哈希、类型和大小。
- 通过事件写入/模型历史持久化的提交边界索引引用；不能从“曾在历史中出现过”推断仍然有效，编辑/删除/分叉都要更新存活引用。
- 删除采用标记待删 → 事务提交引用变更 → 延迟校验 → 删除文件 → 回写结果的可恢复状态机。重启后可以重试；任何错误均保留数据。
- 资源扫描、回填、哈希计算与缩略图生成在后台有限并行处理，不能阻塞会话切换或主线程。
- 迁移现有 `.dsh/attachments` 时必须先扫描/核验、建立引用和恢复点，再启用基于索引的清理；禁止边迁移边清空旧文件。

## P2：单数据库与完整备份的评估

现有 #845 将 Session snapshots 和 Session EventLog 存在两个 SQLite 数据库。WAL 优化单库并发，但两个数据库之间不自动提供统一提交事务。应对照以下两种路线：

1. **合并到一个核心数据库**：会话快照、事件与资源目录可以统一事务，适合要求严格原子性的链路。代价是迁移、兼容和锁争用评估。
2. **保留多库**：继续分离冷热负载，通过一致性导出锁、双库恢复检查点和恢复校验保障跨库备份，禁止将两库复制视为天然原子事务。

最终选择以 Android 16/17 实测为准，至少覆盖 10 万消息、图片引用压力、长时间运行、并行读写、杀进程、存储耗尽、损坏备份、删除重建和旧版本升级。

## 验收门槛

- 多会话引用同一图片，删除一条消息或会话后共享图片仍存在；
- SQLite-only 会话没有 JSONL 文件时，图片不会被误判为孤儿；
- 旧事件格式、快照、未完成草稿和损坏记录不能触发误删；
- 图片加入、编辑、移动、重复上传、重启、备份恢复及磁盘满均有实际回归；
- 会话切换只读取最近消息，历史滚动分页，不因为全量资源扫描产生卡顿；
- CI 编译、JVM、Android 16/17 设备测试全部通过后方可合并；
- #846 必须吸收 #845 的最新修复并重新执行集成 CI；避免重复定义 `historicalSources()`。

## P1 阶段一：资源索引基础（关联下游草稿 PR）

- 会话 Event SQLite 数据库新增 v3 Schema：`local_assets`、`local_asset_references`。元数据随现有事件数据库的 WAL 备份导出；**图片/音视频等外部资源文件尚未打包进入 SQLite 备份**，目前仍属于不完整的资源备份，不能宣称单独导出数据库就能完整恢复媒体。
- 选取文件和 MCP 图片经统一 `LocalAttachmentImporter` 发布后登记 SHA-256、相对路径、媒体类型和字节数，重复登记保证元数据一致。
- 正式 `user/message`、`assistant/message` 事件写入时，在同一个 SQLite 事务内为已登记资源建立事件级引用。会话事件代际被删除时外键同步清理其引用；共享资源目录保留。
- 未登记的模型生成图片、既有旧附件和无法回填的历史，不因索引未覆盖被清理；老 GC 仍须完成权威会话事件 + 快照扫描，`local_asset_references` 尚不可独立充当删除依据。
- 设备验收需覆盖 v2→v3 升级、已有事件保留、重复导入、跨会话共享、引用外键、缺元数据情况以及读取失败时禁止误删。

下一步仍需：**现有旧素材及其他生成/工具媒体的完整回填**、消息编辑/删除的活跃引用状态管理、把外部原文件纳入备份恢复包并校验哈希、恢复前后一致性比较、数据库版本跨度与真实设备验证。直到覆盖完成前，不启用基于资产索引的自动物理删除。
