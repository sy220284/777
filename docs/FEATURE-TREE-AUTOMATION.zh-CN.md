# 功能树自动维护与复核

## 工作方式

GitHub Actions「自动维护功能树」在 `main` 更新、定时任务、手动触发和 PR 时扫描全仓库代码/配置文件，分别清点生产 Kotlin/Java、测试、路由、可见界面与工作流。不依赖 PR 描述推断产品能力。

执行顺序：**全量扫描 → 不写文件的预览与候选分类 → 符号/归属/测试证据复核 → 刷新中文功能树与交互视图 → 独立复核 → 创建或更新单一维护 PR**。复核失败不得提交。PR 上的扫描生成可下载的 Actions 检查产物；已有分支内的实际代码与当前主线需独立核实。自动维护操作不得直接绕开主线合并和发布门禁。

持续维护文件：
- `FEATURE-TREE.zh-CN.md`：中文功能树。
- `FEATURE-TREE.zh-CN.html`：同层级交互树，对有直接测试引用的节点标记“局部测试证据”，不作全部验收承诺。
- `FEATURE-SOURCE-INDEX.auto.json`：扫描范围、路由、界面候选与源码内容指纹。
- `FEATURE-REVIEW.auto.json`：**每个末级功能的证据级别**、批准的变更、待确认变更及验证边界。
- `FEATURE-TREE-SOURCE-REGISTRY.json`：已复核的稳定功能身份和源码证据。
- `ACCEPTANCE-MATRIX.json`：仅记录已存在的实际测试证据；移动功能时对齐路径，不新增虚构测试。

## 什么条件才可自动确认功能

扫描器不会根据文件名、类名、文案相似度或模型猜测来删除/新增业务功能。只有源码明确登记、**同时通过独立证据核查**的功能变化才会写入树。例如对应生产入口附近使用：

```kotlin
// FEATURE_TREE: {"id":"chat.diary.revise","path":"第一层｜产品功能与界面 / 聊天功能 / 人物与人设 / 日记纠正","entry":"reviseDiary","owner":"CHAT","test":"app/src/test/java/example/DiaryTest.kt#reviseDiaryWorks"}
```

上面仅是字段格式示意，路径及方法必须在对应仓库中实际存在才会获准。检查要求：稳定唯一 `id`；`path` 末级必须是中文名称；`entry` 必须为当前生产源码的真实声明；`owner` 必须归属七个架构业务模块；`test` 必须指向实际存在的 Kotlin `@Test` 方法且引用对应入口。

身份未变而 `path` 改变时，自动移动/改名并迁移已有验收索引。首次接管旧节点并同时重命名时，可注明 `previous_path`。已确认的功能退役需在仍存留的生产源码中声明 `action: "retire"`、原 `id` 和 `path`，以及中文 `reason`；仅删除文件或登记会保留旧节点并报告“待复核”，避免误删。

**重要区别：通过这些检查，只能证明源码声明、功能归属与测试引用有一致证据，仍无法证明功能实际效果、启动链路、设备交互和所有异常恢复均已完成验收。** 未登记的历史功能保持原有层级；源代码尚无法自动确定的变化只列候选。

## 旧版已删除功能的自动识别与更新

除主动新增的稳定 `FEATURE_TREE` 登记外，扫描器还**反向检查历史 447 项源码证据台账**：逐条对比现行功能树和当前 Git 工作目录下的生产源码。结果单独记录在 `FEATURE-REVIEW.auto.json`：

- `obsolete_historical_evidence`：曾经列出的功能，现行树已经没有该路径；区分“旧生产文件全部消失”“旧实现仍存在，可能改名/合并”及“证据不足”。历史路径消失不直接证明产品能力已经删除。
- `current_tree_outdated_sources`：现行功能仍在，但历史记录指向的生产源码文件已消失。这类功能必须追查新入口；禁止仅因文件删除就删除节点。
- `approved_legacy_retirements` 和 `legacy_retirements_requiring_review`：独立审批后准予删除，以及因为仍有源码/测试/历史来源疑点而拒绝删除的项目。

旧功能没有 `FEATURE_TREE` 登记也可以被确认为退役，但必须先在 `docs/FEATURE-TREE-RETIREMENTS.json` 添加审核记录。例如：

```json
{
  "version": 1,
  "approvals": [
    {
      "path": "第一层｜产品功能与界面 / 旧模块 / 已移除功能",
      "source": "app/src/main/java/example/RemovedFeature.kt",
      "symbol": "RemovedFeature",
      "reason": "已核对新实现，原入口确认完全退出"
    }
  ]
}
```

这是数据格式示例，不能直接用于真实功能。工作流会核实原生产源码确曾出现在历史证据或稳定登记中；检查**全部现存 Kotlin/Java 生产源码中无原入口声明**、相关 Kotlin/Java 测试没有引用该入口、验收映射已处置、节点仍为末级功能且没有当前的源码登记。任何一项不满足，就维持旧节点并列出拦截原因。审核记录保留以便追溯；再次运行不会重复删除。

对历史功能已有明确替代实现的情况，应先维护对应的新功能及测试映射，再批准删除旧节点。扫描无法通过“找不到旧文件”证明功能彻底不存在，也不应把更名/合并误判为退役。对于已不在树内的旧台账记录，只标记历史失效，不会错误地重新新增到树中。

## 功能覆盖等级和变更发现

所有现行末级功能在 `FEATURE-REVIEW.auto.json` 的 `leaf_evidence` 中独立登记，以中文名称关联，不把静态源码线索误写成“已可用”。分级可区分：

- 有真实 `@Test` 映射且具名生产入口声明存在；
- 有真实测试映射，但完整调用链仍待确认；
- 具名生产源码声明存在，尚无直接测试映射；
- 历史生产文件仍存在，但具体入口还需进一步核实；
- 只有候选生产文件，证据不足；
- 历史生产源码失效，需确认迁移、替换或退役；
- 没有可确认的现行入口证据。

每个节点保留历史证据等级、实际存在和缺失的源码文件、具名符号是否声明，以及直接测试引用数。交互 HTML 展开叶节点即可查看这些事实；全部属于**静态证据**，无法代替端到端、真机和模型效果验证。

`FEATURE-SOURCE-INDEX.auto.json` 额外保存全部生产 Kotlin/Java 的独立源码内容指纹，并在 `observed_delta` 中跟踪相邻不同快照的 **生产文件增加／删除／修改／内容完全一致的移动、路由增加／删除、可见界面候选增加／删除**；删除一个 Kotlin 文件只意味着“待调查代码变化”，功能语义需要证据复核。首次建立索引只登记基线，不把原有全部文件虚报为新增；相同代码内容指纹重复运行不会产生变更噪声。这些细节也在复核报告中出现，方便从功能树排查哪些源码可能需要重新映射。

目前的历史功能树仍有未登记稳定身份的条目，这类既有功能通过上述证据清单持续跟踪；要实现可信的**自动改名、合并前的移交、退役**，必须将稳定 ID 和真实入口证据逐步补入相关生产代码。对任意两个既有功能直接碰撞、无证明接管旧路径、把原有叶节点转成分类等破坏性操作，工作流都会拒绝自动执行并记录待审原因。

## 工作流权限、维护方式和故障处理

`pull_request` 触发的 **PR 只读扫描及证据复核** 不保存 GitHub 凭据，也不向功能树分支写入文件。它运行完整扫描、回归自测及独立检查，上传可检查产物，并显示功能数量及变化摘要。PR 连续更新时会取消同一个 PR 的过期检查以减少无效执行。

`push(main)`、定时任务及 `workflow_dispatch` 使用单独的 **主线单一维护 PR**：无论用户从哪个分支触发手动任务，扫描源固定为 `main`；只有复核成功、有真实文档差异时才写入 `automation/feature-tree-maintenance`，创建或复用同一个中文维护 PR。它不会向 `main` 强行提交。首次运行可能需要仓库管理员允许 GitHub Actions 创建拉取请求；如未授权，必须明确记录失败，不能声称已自动维护。

**边界提醒：** 工作流可以依据实际源码确定文件、路由、声明入口、已登记身份、测试引用和证据状态；它不能靠自动猜测彻底理解每项业务功能，也不能在缺少替代实现验证时自行删除旧能力。功能合并和拆分应先明确实际承接者与测试迁移，最后让工作流验证并更新树。

## 第二阶段：现有功能身份接管与缺证据排查

此前现行树有 444 项末级功能。其中 185 项可从历史台账找到**现存的具名生产源码声明**，但同一个入口符号可能被用于多个不同产品功能。逐项按 `生产源码路径 + 真实符号` 复核后，只有 **117 项**具有互不重复的入口锚点；另外 **68 项**共享代码符号，尚不能单凭源码声明确定独立功能边界。

因此建立 `docs/FEATURE-TREE-LEGACY-IDENTITIES.json`，把上述 117 项分配固定 `existing.NNNN` 身份，保留**中文路径、真实源码文件、入口符号、模块归属和静态证据级别**。固定编号在未来重命名时继续使用；不能根据名称变化重新生成编号。对这些记录，每次全仓库扫描都反查源码和功能树：如果文件、入口或旧路径失效，先产生待复核警报，**不能凭这批静态身份自动删除、改名、合并或拆分功能**。

这些 ID 是只读追踪级别，独立于需要实际 `FEATURE_TREE` 源码声明与直接测试引用才能进行语义自动变更的权限。此阶段 **117 项静态追踪身份、0 项具备自动写入权限的正式源码登记**。未来验证完整调用链及测试后，再逐项升级到有自动变更权限的登记，不可直接扩大授权。

最初 55 项缺少现行入口证据的历史功能已逐项分类。通过检查真正的跨 Gradle 模块源码，新增 `docs/FEATURE-TREE-EXPLICIT-EVIDENCE.json`：**10 项**原缺证据能力找到实际 Kotlin 声明（4 项语言服务器、6 项会话身份/恢复），由独立验证器核实具体函数、文件和 LSP 工具分支，仅升级为静态证据；其余 **45 项**继续留在 `FEATURE-REVIEW.auto.json` 的 `unproven_feature_triage`。每项列出排查领域、**仓库中实际存在的候选文件**与仍需验证的调用链、测试。文件存在和方法存在都不能冒充完整产品验收。共享源码符号歧义名单另存 `ambiguous_named_entry_paths`，不得算成独立功能身份。

人工复核某项弱证据时，至少需要定位实际生产声明、确认对应用户入口和调用链、发现真实测试方法并核对相关行为，再更新对应源码身份。对公共工具、LSP、设备服务、GitHub Actions 等非聊天模块，需跨模块检查真实实现，不可仅因为其位于其他 Gradle module 就当作已删除。

## 第三阶段：跨模块证据与 CI 配置语义分离

接续上一轮尚缺入口的功能，本轮继续对源码进行定点核查。**共新增 17 项**终端、Android 设备、MCP、Git、人物状态、Node/Python 等具名源码证据，统一保存至 `docs/FEATURE-TREE-EXPLICIT-EVIDENCE.json`。该台账现共 **27 项**（含上一轮的 10 项），具体声明与工具分支由独立复核器从生产 Kotlin/Java 代码重新读取，严禁以类似文件名替代真实声明。

对 GitHub Actions 工程能力，单独建立 `docs/FEATURE-TREE-WORKFLOW-EVIDENCE.json`，登记 **14 项**构建、架构、设备回归、CI 语义检查及发布能力的 **工作流文件、job ID 和该 job 范围内真实命令/步骤**。只有定位到具体作业内部的预期命令，才可升级为“工程工作流门禁入口存在（静态）”；别的 job 或其他文件碰巧包含相同文字，不算证据。**配置中有作业，不代表这次执行了该作业，更不代表已经成功。** 条件跳过或环境依赖仍需另查对应真实 GitHub Actions 运行记录。

此外，Node.js 和 Python 的运行时分别在仓库中存在 `BundledNodeRuntimeTest` 与 `BundledPythonRuntimeTest` Android 仪表测试方法。扫描器逐项检查方法名、`@Test` 和生产类引用，单独记为“具名源码及仪表测试声明存在（静态，未执行）”，不混入原有 128 项直接测试映射，更不能在没有真实设备报告时声称已经通过。

共享入口歧义已从简单的路径名单升级为 `ambiguous_named_entry_groups`：每组记录**实际包含声明的源码文件、真实符号、对应的全部功能中文路径**。独立校验器重新从文件内容计算，不能把一个源码文件里的符号推定为其他文件的声明。若入口承担多个业务能力，可以继续共享，但其细分行为、调用方和测试归属需要分别验证；无需为了减少歧义数量强行拆分生产代码。

待核清单已按 Git、MCP、终端以及人物设定与采样专题调整候选源码路径，避免将 Git 功能指向 LSP 或设备插件。所有缺入口证据功能继续保留在功能树中，并维护可追踪的排查路线。生成 HTML 为每一项展示可用的静态身份、源码级别、工程作业数量和未执行仪表测试数量。

## 本地/CI 校验

```bash
python3 .github/scripts/sync-feature-tree.py --self-test
python3 .github/scripts/sync-feature-tree.py --preview
python3 .github/scripts/sync-feature-tree.py
python3 .github/scripts/sync-feature-tree.py --check
python3 .github/scripts/check-feature-tree-sync.py
python3 .github/scripts/check-acceptance-matrix.py
```

预览不会修改文件；后续同步必须执行双视图、全量文件数量、稳定内容指纹、逐叶证据和已有测试方法验证。检查过程有任何缺口就拒绝提交。生成文档的提交本身不会改变实际产品代码；仓库 CI 与真机验收仍按 `VALIDATION.md` 执行。

源码内容指纹是确定性的，不受仅修改生成文档所造成的 Git SHA 变化影响。功能变化必须在修改它的同一个 PR 中同步核对，不能依赖下一次定时任务补漏。
