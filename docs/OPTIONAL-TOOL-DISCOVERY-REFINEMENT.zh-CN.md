# 可选工具发现误激活治理（接续 #619）

## 代码依据
- `LocalToolRouter.relevantOptionalToolNames` 在旧实现中使用包含式匹配工具名、关键词、能力族。英文短关键词可命中普通词内部，例如 `api`→`capital`、`pr`→`preview`、`web`→`website`。
- 单独提到泛化能力族，例如“智能体”“网络”“会话”，会触发所属可选工具大批预激活；与最小化模型工具表的既有架构目的相冲突。
- `capability_search` 已使用注册表真实内容检索和动态启用；权限 / 自动审批另有独立门禁，不能因为减少预激活而取消该能力。

## 采用方案
1. 预激活时匹配明确的工具名及工具 `discoveryKeywords`，不再把通用 `family` 当作直接激活依据。
2. 英文和 ASCII 下划线标识使用词界，不再匹配长单词内的短关键词；中文短语保留包含匹配，仍支持“使用GitHub工具”一类中英文相邻表达。
3. 继续保留实时注册工具、MCP 插件动态扩展、显式 `capability_search` 能力族检索、权限审批、Token 定义预算、当前任务排序，不以静态 allowlist 替代。
4. 添加词界、中文混排、能力族不扩散、协调器真实暴露和动态发现回归测试。

## 取舍与保留项
- 不做工具树的二次静态目录：已由实时注册表解决。
- 不删除 Plan Mode、`todo_write`、`create_goal`、`subagent_fork` 或 `workflow`：这些分别承担状态权威、授权和任务编排语义。
- 不改变 #617 的 LSP 发现代码或其他进行中的聊天/页面 PR。
- 预激活只解决低成本精确线索；较模糊的自然语言仍可通过 `capability_search` 发现，避免为了“智能”猜测大量不相关工具。

## 验证
需要 GitHub Actions 的 unit-tests、架构/静态门禁及 Android 构建通过。任何测试失败均在本 PR 内修正后再评估合并。
