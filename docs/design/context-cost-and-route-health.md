# 上下文成本与路由健康治理

本文件记录真实长 Work 会话暴露出的模型成本与失败重放问题，以及当前已经落地的分层治理。历史实测数据来自 SessionEventLog / TokenUsage 诊断字段，用于说明问题规模，不作为固定性能承诺。

## 1. 历史实测

一次长会话曾出现：

| 指标 | 实测值 |
|---|---:|
| 模型请求次数 | 52 |
| 估算输入合计 | 2,788,769 tokens |
| 单次输入峰值 | 116,487 tokens |
| 首末请求 | 8,067 → 116,487 |
| 失败请求 | 12 次 |
| 失败请求累计估算输入 | 361,467 tokens |
| 用户消息 | 15 条 |
| 单次工具结果 | 80,000–120,000 字符 |

其中单一路由出现过 10 次同类 `CHATGPT_PLAN_STREAM_INTERRUPTED`。单次失败并不可怕，危险在于自动续轮再次选择同一故障路由并重新发送大上下文。

## 2. 已由 #381 收敛的成本根因

最新 main 已经完成以下治理：

- Work 请求超过稳态阈值后，派生“可信检查点 + 近期原文”的有界投影，不再让输入随完整历史无限线性增长。
- 旧工具结果先衰减，连续 system 前缀和当前运行约束保持原样。
- 成功请求按供应商真实 input Token 结算；未知受理使用校准后的 uncertain exposure。累计 exposure 只用于诊断，不再作为单轮 Work 的硬停止条件。
- 长 Work 不设置累计 input Token 总量上限；单请求上下文窗口、稳态投影、并发 pending admission、请求次数与超时继续承担真实安全边界。
- 请求取消携带 admission state，明确未发送取消释放预算，可能已送达才保守计入。
- Prompt cache comparison baseline 按“会话 + 物理路由指纹”隔离，并输出缓存诊断。
- 诊断导出有界读取 EventLog / TokenUsage，不另建第二套事实源。

## 3. 当前传输失败处理（2026-10 修订）

历史版本曾使用跨 Work run 的传输故障熔断：连续三次失败后阻塞 90 秒，恢复探测再次失败则指数延长至 15 分钟。该设计只能减少再次请求，并不能修复网络中断，还可能在网络恢复后继续拒绝合法请求。本次已移除这层预先阻断，也不保留单次恢复探测门禁。

现行规则：

- 每次请求按实际 HTTP / SSE / 网络结果结算；临时中断须向调用方返回原始模型错误，后续用户请求不继承此前的阻断状态。
- **未发送**且可安全重试的传输错误，按当前有限次数退避处理；**可能送达或已经接收**的请求，禁止静默整轮重放，防止重复推理、工具副作用与套餐消耗。
- HTTP 明确拒绝（例如 401/403/429）仍按账户授权、服务端错误及 Retry-After 处理，不能用本地冷却替代真实错误。
- Work 检查点、自动续轮与消息恢复保持独立运行；同一路由后续任务可以按用户意图继续尝试，并据真实结果报告失败。
- Responses 流式请求取消固定六分钟整次超时，允许正常长推理持续传输；连接超时、读空闲超时、运行切片超时与用户取消仍生效。
- 当前上下文窗口、单请求容量、运行切片、并发预算及取消安全机制不受此次变更影响。

诊断关注 `request_id`、`failure_kind`、`admission_state`、传输异常类型、实际 HTTP 状态和请求终态。单独的 `stream_interrupted` 只能证明连接未正常完成，无法从错误代码推断是运营商、代理、HTTP/2 还是远端服务主动关闭。

## 4. 与自动续轮的关系

流中断后 Work 可以保存检查点并生成新的继续任务。是否继续由当前工作恢复规则决定；本地不再通过跨请求路由冷却阻止下一次真实尝试。已受理请求仍不能未经确认就自动重发相同整轮内容。

## 5. 缓存成本与前缀连续性

缓存优化不能只看输入 Token 下降。当前账本额外记录供应商实报的 `cache_write_tokens`，并继续保留 cache hit / miss；缓存写入是 miss 的子集，不重复计入总 Token。这样后续可以按真实供应商价格比较“保持稳定前缀”和“重写后重新预填”的成本，而不是只比较 raw input。

缓存敏感路由还维护一个只存 SHA-256 指纹的请求序列状态：上一次成功请求的工具面必须保持一致，且上一次成功消息序列必须是当前消息序列的精确前缀，才记为 `continuous`；历史重写、工具面变化会开启新的 generation。失败请求不会成为下一次基线。诊断只保存布尔状态、代数和消息数量，不保存第二份 Prompt 文本。

当前先把事实源补齐，不在缺少真实成本样本时动态改写压缩阈值。DeepSeek / OpenAI 的下一阶段治理只允许消费这些实测字段做决策。

## 6. 后续方向

- 对供应商明确支持的增量续轮协议，可在 provider / model / protocol / auth / account 完全一致时研究增量发送；ChatGPT 套餐当前 Responses contract 禁止 `previous_response_id`，不得强行套用。
- 工具输出继续按现有有界投影治理；如实测仍占据主要成本，再基于 Token 账本决定是否引入独立份额，而非先加固定限制。
- 性能验收以诊断事实为准：关注单请求 input 分布、缓存命中、同路由重复失败的真实原因、错误呈现和实际 provider 请求数。

## 7. 验证要求

专项测试至少覆盖：

- 连续发生多次 `CHATGPT_PLAN_STREAM_INTERRUPTED` 后，下一次合法请求仍能立即到达 provider，返回的仍是原始传输错误。
- 失败 / 用户取消后的 token reservation 结算不回归；已接收、可能接收及未发送状态继续遵守不同的自动重试边界。
- 并行请求和其它 Work run 不再共享临时故障阻断。
- 上下文、预算、认证与服务器明确拒绝等独立有效约束继续生效。
