# 上下文成本与路由健康的根因与设计修复

本文件记录一次真实会话（`b3e9ac1e…`）的 token 成本根因分析，以及按“从软件设计上解决”的要求给出的修复分层。
数据来源：本机 Harness 会话事件日志的自身估算字段（`estimated_input_tokens` 等）。

## 1. 实测事实

| 指标 | 实测值 |
|---|---|
| 模型请求次数 | 52 |
| 估算输入合计 | 2,788,769 tokens |
| 单次输入峰值 | 116,487 tokens（末次） |
| 首末请求对比 | 8,067 → 116,487（14.4 倍） |
| 失败请求 | 12 次（23%） |
| 失败请求累计估算输入 | 361,467 tokens |
| 用户消息数 | 15 条 → 平均每条触发 3.5 次请求 |
| 单次工具结果体量 | 80,000–120,000 字符 |
| 持久历史长度 | 约 216,203 字符 |

同一路由（DeepSeek）在其后的 57 次请求中，输入 1,421,638 tokens，其中缓存命中 787,840（51.1%）。
既有预算：`model_attempts=3`、`max_parallel_worker=1`、`max_steps_per_worker=8`、`automatic_continuation=2`。

关键失败画像：单个 profile 上出现 10 次同码 `CHATGPT_PLAN_STREAM_INTERRUPTED`（`attempt=1`、`retryable=false`），
每次请求平均约 36,147 tokens。失败本身不致命，但它以“每次重新发送整段上下文”为代价被反复重放。

## 2. 根因分层（按消耗占比）

### C1 每轮全量重放整个会话（约占 83%）
每轮都把系统指令、完整历史、工具结果与工具定义重新发送，单次输入因此随会话线性增长到 11 万 token。
用户输入只是“继续”“排查下问题”这类短文本，成本却由累积历史决定。

### C2 工具结果与上下文预算脱钩
工具返回（会话日志、grep、构建输出）单条可达 8–12 万字符，且“时间衰减/投影”只做后缀截断，不约束“工具结果总共应占多少预算”，
因此一次大输出就能把后续每一轮都拖到高位。

### C3 没有路由健康熔断：失败被当成“再试一次”重放
现有熔断只覆盖**持久性**故障（账号/凭据/额度：`isTerminalRouteFailure`），
传输层故障（`stream_interrupted`、`unexpected_eof`、`connection_reset`、`timeout` …）既不熔断也不累计，
于是同一不可用路由被自动续轮再次重放，每次都重新付费。

### C4 缓存命中率没有进入可控指标
同一路由已有 51.1% 缓存命中，但客户端既没有缓存诊断字段（`cache diagnostic unavailable`），
也没有“稳定前缀”约束：历史投影/压缩会改写中段消息，改写点之后的前缀缓存全部失效。
“有界投影”与“前缀缓存命中”目前是相互冲突且无人观测的两个目标。

## 3. 本轮已实现（本 PR：路由健康熔断）

设计取向：**不靠“再试一次”解决问题，而是让不可用路由停止被重放**，同时保留可观测与可恢复语义。

- `LocalModelRouteCircuitBreaker` 改为两层：
  - **持久层**（账号/凭据/额度）仍为 per-run，沿用既有 `MODEL_ROUTE_CIRCUIT_OPEN`；
  - **传输层**新增连续失败 streak 与冷却窗口，抛出稳定码 `MODEL_ROUTE_CIRCUIT_COOLDOWN`。
- streak 与冷却状态放在**进程级**的 `LocalModelRouteHealth`：
  路由健康是“路由”的属性，不是“一次运行”的属性；per-run 状态会在每个自动续轮被重置，正是失败重放能连续发生 10 次的原因。
  持久层故障不写入该注册表，避免两套判定互相污染。
- 冷却策略：连续 3 次传输类失败触发，首次 90 秒，重复失败翻倍，上限 900 秒；任意一次成功即清零。
- 可观测：`LocalRouteCooldown(reason, failureStreak, millis, until)`，`consecutiveFailures()`；
  失败码在 `modelFailureKind` 中登记为 `route_circuit_cooldown`（与 `route_circuit_open` 同级）。
- 短路位置在 `requireClosed(profileId)`：位于预算预留与模型请求之前，
  因此“冷却中被拦下”的续轮不产生任何模型消费，符合 AGENTS.md §6“禁止盲目自动重试”。
- 用户可见语义：错误信息给出失败次数、原因与暂停秒数，并明确提示可切换到其它模型档案后继续（不静默改路由、不静默换账户）。
- 测试：`LocalWorkExecutionBudgetTest` 新增 4 例（阈值与冷却触发、成功清零、冷却过期后放行一次探测并按倍数延长、持久故障不触发传输层冷却）。

## 4. 设计层后续（按收益排序，尚未实现）

- **D1 增量续轮**：同路由同身份下用供应商续轮字段（`previous_response_id` 类）或用稳定消息 ID 描述增量，
  使每轮只发送新增片段。这是 C1 的唯一根治手段；需按 AGENTS.md §9 的“同路由身份才可重放供应商私有状态”实现，
  并在发送前校验身份（供应商、模型、协议、认证方式、账户）完全一致，否则退化为全量。
- **D2 工具结果预算份额**：为工具结果分配历史预算的固定份额（例如 25%），按“最新保真、越旧越紧”分配，
  超出份额即投影为 `tool_output_read` 引用；使单条大输出不再拖高后续每一轮。现实现只按“保真条数”截断，与预算无耦合。
- **D3 续轮前的路由健康门禁**：`shouldAutoContinueWorkFailure` 目前只判断 `continuationEligible` 与次数上限，
  应在冷却窗口内直接不排队自动续轮，把“拦截”从错误提示提前为“不产生这一轮”。
- **D4 前缀稳定性与缓存指标**：压缩/投影只允许在“缓存安全前缀”之后发生，前缀在显式压缩纪元前不可改写；
  同时把缓存命中率纳入可观测字段，用命中率而非仅 token 总量衡量优化效果。
- **验收口径**（建议）：同一会话单次输入 P95 ≤ 40k tokens；失败重放次数 ≤ 1；
  传输类失败发生后 5 分钟内不得出现同路由同码重复请求。
