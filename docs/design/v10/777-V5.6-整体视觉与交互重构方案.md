## 一、重构目标和设计决策

### 1. 需要解决的根本问题

当前 777 的主要问题并非某个按钮或配色值，源头是“所有页面共同继承旧的视觉性格及相近的空间组织”。聊天、工作、发现能力、定时任务、人物和设置承担不同任务，却在多个页面中呈现类似的空状态中心构图与过强的统一表面语言。之前的审计还确认存在小字号、高字号长按钮垂直断行、部分重复标题、图标来源与材质层级竞争等问题。

在保持功能和行为所有权的同时，重构要取得五项跨越：

1. 从**统一皮肤**转为**由真实任务决定的空间结构**；
2. 从**装饰性状态**转为**目标—执行步骤—结果可检查**的一条直观视觉关系；
3. 从**单件组件修补**转为**基础设计变量—语义角色—场景组件**的可维护系统；
4. 从**静态画面好看**转为**全状态、跨设备、长时使用的整体审美**；
5. 从**测试通过便算完成**转为**行为回归 + 原生截图审美复核 + 目标用户评价**的双轨验收。

用户已否定的旧暖米白、深棕、杏色视觉方向退出新方案的艺术参考基线；历史截图仅用于证明问题和保持功能覆盖。

### 2. 777 的新设计命题

**“让每一步行动，有清晰的形状。”**

用户可以在 Chat 中讨论、在 Work 中授权并执行任务、通过能力中心连接工具，最终查看可以复核的文件与结果。这些行为构成同一产品的完整故事。设计的第一视觉焦点应是**当前对象和下一步行动**；当真实执行发生时，界面要把**运行阶段与交付物**展现为连续的关系。视觉识别应从排版比例、轨迹线、状态节点、图形边界与适度大胆的主色共同产生。

保护目标：现有操作路径和真实行为、分级权限、本地数据、输入法、系统返回、功能完整性、已验证的错误恢复与可访问性。

## 二、三套真正不同的视觉方向

三套设计均使用相同任务：“发布前检查与问题复核”，同一任务数据和手机尺寸。它们的**主要内容位置、视觉中心、观看路径、信息密度和动线**确实不同，避免同构换皮。

| 方向 | 主要构图机制 | 情绪与观看顺序 | 优点 | 必须控制的代价 |
|---|---|---|---|---|
| **01 ORBIT · 行动轨迹**（推荐验证） | 一块聚焦任务的主视觉板，向下串接执行节点与交付成果 | 先看当前目标，再看进行到哪，最后看实际产物 | 对 Chat/Work/任务状态有天然关联；清晰、可扩展，有识别性 | 主视觉板不能挤占长任务步骤；纹理仅作为内容配角 |
| 02 EDITORIAL · 叙事编排 | 大字排版、时间编号与纵向章节，减少卡片 | 先感受任务叙事，再顺序阅读 | 独特、适合聊天和长内容 | 工作高频控制和较小屏幕会被大字占据空间 |
| 03 COMMAND · 精密控制 | 高密度仪表、成组状态指标、统一坐标式事件表 | 先看状态与异常，再精密操作 | 专业、高可观察性，适合复杂运行 | 轻量聊天、人物体验可能过于紧绷；字号放大须全面重排 |

**推荐 01 作为统一重构的设计验证基线**，不直接宣布其审美已获得用户认可。02 的文字艺术和 03 的专业信息密度可以在合适页面局部吸收，但不能把三套主题生硬拼接。预览可在 HTML 原型中切换：相同目标、不同构图。

## 三、01 ORBIT 的完整视觉体系

### 1. 空间与构图（D01—D03）

- **主角**：优先展示用户当前目标、当前动作或正在阅读的内容；不放空洞的英文口号，不为对称强行制造卡片。
- **轨迹线**：以连续细线、节点和结果锚点表达过程。只在任务流程、历史记录和状态进展中出现；普通设置列表不使用。
- **视觉配重**：强色区域集中在当前目标，不使菜单、标题、按钮、背景同时抢焦点。一般内容页用清晰文字和对齐建立节奏，人物页允许更生动的图像面积。
- **空间重组**：工作页“主目标—步骤—成果”；聊天页“当前会话—消息—输入”；能力中心“搜索—结果—管理”；设置页“搜索—分组—选项”；任务页“状态—任务—创建”；拒绝一张卡片的构图应用于全部页面。
- **屏幕变化**：320—430dp 以单列为基本结构；较宽的平板允许 Work 当前目标和执行轨迹并列、工具区成为可收起辅助栏。依任务重组，不缩放手机界面充当平板。

### 2. 色彩与光影（D05，**候选语义色**）

以冷雾蓝白背景＋深墨蓝文字建立干净的阅读空间，把高对比钴蓝用在当前主任务。薄荷绿色承担“通过/完成”的语义；风险色单独保留。大面积装饰性色彩应慎用；无需再依赖旧的暖米色和杏色。

| 语义角色 | 浅色建议 | 深色建议 | 设计职责 |
|---|---|---|---|
| Canvas / 页面 | `#F3F5FA` | `#111827` | 低噪声的内容背景 |
| Surface / 实际内容 | `#FFFFFF` | `#1D2739` | 阅读区、文件列和信息面 |
| Ink / 主文字 | `#14233B` | `#EDF2FE` | 标题、主体文案 |
| Muted / 次文字 | `#657088` | `#B4C0D5` | 日期、解释与辅助信息（实测对比度） |
| Primary / 行动 | `#334ED5` | `#91A2FF` | 主操作、当前焦点、活动节点 |
| Primary Ink | `#FFFFFF` | `#111827` | 主行动面上的文字 |
| Positive | `#0B725E` | `#53E1BD` | 已完成／已连接，仍需文字标识 |
| Caution | `#865B10` | `#F0C06C` | 待处理、等待连接 |
| Danger | `#B83E45` | `#FF9099` | 失败、风险和确认后果 |
| Outline | `#DBE1EB` | `#38435C` | 轻量分组与控件边界 |

**这是用于设计对照的候选值，不是已经经过所有动态壁纸、真实设备与不同字体字号验证的生产变量。** 接入 Compose 前需要对真实表面颜色、图像叠层与高对比度模式逐一测试；正文目标 WCAG 2.2 AA 常规 4.5:1，大字和有意义控件边界依据适用标准检查 3:1。状态颜色必须同时有图标、文字和正确的实际回执。

保留已有的动态壁纸、自定义背景与对比度基础能力，但重新定义材质使用条件：长文区域主要使用不透明或经过实测的承载面；半透明和模糊仅在与背景关系真实可控的浮层场景使用。拒绝所有卡片机械地叠加阴影和玻璃效果。

### 3. 字体与图形（D04、D06）

- **延续真实可用资源**：现有源码已用 Outfit 和 Noto SC 子集作 UI 字体、Android CJK 回退，代码文字使用 Mono。优先维持现有字库能力，重新调整视觉角色；如另换字体，应先评估安装包、中文字符覆盖和渲染成本。
- **字阶候选**：页面大标题 26—30sp；工作目标 22—26sp；正文 15—16sp；主要列表 14—16sp；真正的次级说明 13—14sp。11.5—12sp 仅用于短且不承担关键操作判断的辅助信息；极端字号需要重新分组与换行。
- **字体关系**：正常高频页面以稳健中文文本为主，避免为了装饰反复加入英语小标签；数据和时间可使用数字字形形成识别点。
- **图标统一**：建立一套 20/24dp 主规格、1.75—2dp 的线条形态和光学对齐规则；复核现有 FeatherIcons、SyEntryIcons、Material Icons 的重复职责，保留语义再统一造型。图标本身不得独自承担危险操作含义。
- **品牌图形**：以“起点—轨迹—结果”曲线和节点作为可变表现方式，实际出现在工作进度、文件关联与任务状态，不在全部页面增添装饰弧线。

### 4. 组件结构（D07—D11）

- 按层使用组件：**基础变量 → 语义控件 → 场景组件**。共享行为与语义，不强求所有内容都呈相同卡片。
- 主要操作应明确区分 Primary、Secondary、Tertiary、Danger、Disabled、Loading、Success；均能承载加载与失败状态。
- 触控目标至少按照 Android 48dp 目标设计；密集内容通过视觉留白与命中区域分离，不能用缩小命中区域换视觉密度。
- 浮层需明确从哪个对象进入、修改什么、关闭后回到哪里；系统返回、输入法遮挡、导航抽屉与底部弹层统一检查。
- 动效与变化：只在对象状态变化、空间重新组织、成功或失败反馈中使用，尊重用户减少动效；不要用全屏动画掩盖耗时任务进度。

## 四、八类关键页面的结构方案与行为边界

| 页面 | 新空间结构 | 重点交互 | 必须保留的生产能力 |
|---|---|---|---|
| **Work 工作** | 当前目标视觉板 → 执行轨迹 → 最新成果 → 持续输入 | 中断、排队、审批、追问、成果打开和恢复 | 工具执行状态、真实回执、任务队列、工作记录、附件、计划模式 |
| **Chat 对话** | 会话对象 → 对话阅读 → 轻量建议 → 输入 | 人物切换、对话操作、附件、模型与思考档位 | 单聊/群聊、不同消息类型、历史与工作模式隔离 |
| **Tools 能力中心** | 搜索 → 发现/已添加 → 分类 → 真实条目 | 添加、连接、更新、删除和状态检查 | Skills、插件、连接器、GitHub、设备能力、加载与连接异常 |
| **Tasks 定时任务** | 运行概况 → 按状态组织任务 → 创建入口 | 编辑、暂停、恢复、立即运行、结果和失败回执 | 调度器真实数据、通知设置、不同运行状态、不误创任务 |
| **Workspace 文件** | 当前路径 → 搜索/筛选 → 文件行 → 实际打开 | 选择、导入、预览、版本/代码审查 | 本地文件归属、多选、文件选择恢复、异常说明 |
| **Persona 人物** | 搜索 → 人物内容为视觉主体 → 详细资料 | 人物选择、编辑、对话和日记关联 | 图片和资料真实存在才展示，不伪造头像或完成状态 |
| **Settings 设置** | 搜索直达 → 语义分组 → 对应设置项 | 搜索匹配、定位/返回、保存/撤销 | 设置目的地、运行状态、字号/主题/模型/存储/诊断 |
| **Permissions 授权** | 需求解释 → 真实授权状态 → 对应操作 → 返回核对 | 选择、去系统设置、重连、稍后 | 无障碍、通知读取、发送通知分离；授权与服务连接分离 |

### 关键页面的进一步规定

**Work** 应区分“尚未开始、运行中、等待审批、可追问、失败恢复、已完成、成果可打开”等视觉状态。运行中展示真实时间/阶段，不将模型产生的文字解释冒充系统确认。长期 Work 不采用过高的首屏装饰，将多余空间还给进度、证据和成果。成果文件与产生它的步骤保持视觉关联，用户可以顺着轨迹回查。

**Chat** 的阅读内容优先级高于模式入口、建议提示和品牌装饰。用户消息与助手消息在排版与对齐上区分；同一正文使用相同阅读基线，避免因身份不同而使用难读的字号。输入区进入编辑、附加文件、工作计划、群聊时按空间需求展开，保留已有的焦点/IME 恢复机制。

**Tools** 移除顶部多重平级筛选给手机带来的空间竞争。以“发现/已添加/更新”为主状态，类别筛选按需横向展开；查询结果优先用标题、能力说明、连接状态、操作组成可扫描的一条。底层仍由原能力所有者决定安装与连接状态。

**Tasks** 把“下一次执行、最近结果、是否需要处理”排在视觉首层。创建/编辑可按“目标→时间条件→通知/执行确认”组织，首次进入不重复两次“新建自动化”。日期时间优先采用设备语言与 12/24 小时设置；运行反馈以服务返回为准。

**Settings** 一层为可扫描的大类，二层为设置组，三层最多到独立详细设置；搜索能直接定位，但不引入额外隐藏深层导航。重复的页面标题只保留一个视觉主标题。无障碍与权限检测保留清晰且平等的入口。

**Permissions** 严格将未授权、系统已授予、服务等待连接、服务实际连接和失败恢复区分开。界面上的“打开系统设置”只说明已进入设置页面；必须依据返回后的系统数据更新成功状态。按需授权，允许稍后设置。

## 五、完整导航与信息架构

仅保留三层以内的用户可见菜单：

1. **全局工作空间**：Chat / Work 模式，抽屉入口，当前会话与状态。抽屉不与系统边缘返回手势冲突。
2. **功能列表或分组**：人物、日记、任务、工具、文件、设置等；由对应 Feature UI 所有者提供内容，Shell 只负责导航和协调。
3. **具体详情/编辑**：一项任务、一个扩展、一份文件、一项设置或某个权限步骤。深层技术状态通过详情中的信息分组展示，不创建第四层导航。

导航必须保留现有会话来源、打开抽屉来源和返回路径。Chat 和 Work 切换保留各自语义；停止或排队等操作不改变全局导航归属。

## 七、完整执行顺序和依赖

### 设计决策关口

先对照三套**真实不同的整页方案**，以用户实际任务评估：三秒内的首要焦点是否准确；页面能否看出 777 的身份；真实长内容和复杂状态下是否清晰；有没有为独特而牺牲操作。方向 01 是当前推荐基线，进入生产前仍需确认其完整效果。

### 实现步骤（同一整体目标，按依赖推进）

1. **设计系统与映射**：确定色彩语义、字阶、控件状态、图标规范、材料层级；将审美表面与真实业务状态分离；避免旧值散落各页面重新形成旧风格。
2. **Shell 与导航**：主界面、抽屉、统一返回、安全区、模式切换，以及跨页面文字与菜单层级。新旧页面逐步统一到同一语义机制，但主线不得停留在新旧皮肤混搭的最终交付状态。
3. **Chat + Work 双核心**：分别建立阅读主次与行动轨迹；恢复输入框与弹层行为；对停止、批准、排队、文件产出等全部真实状态做一一映射。
4. **Tools + Tasks + Settings**：完成高密内容页面的专有构图、搜索、分组、状态说明和日期格式；在小设备和超大字号下重排。
5. **Workspace + Persona + Permissions + 全部子页面**：覆盖完整功能，不留下视觉断层；空、加载、失败、断开连接、权限未开通等状态统一使用新语义但不强制相同构图。
6. **全量审核与回归**：编译、单测、原生交互巡检、截图审美比较、不同设备检查；发现视觉/操作问题继续修订，达到标准后方可合并发布。

每次修改要以页面真实行为与视觉质量的变化为证据，不以“更新了一个配色变量”“完成一个组件”宣布整体重构成功。
