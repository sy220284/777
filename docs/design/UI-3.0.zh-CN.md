# 777 UI 3.0 权威规范：可插拔界面体系

> **R4 实施范围裁定（2026-10-16）**：本规范的长期可替换架构目标不变，当前 R4 仅交付 V6 独立包、Host/Feature Port 和真实业务验收；Next 与完整双 UI 切换不在 R4 范围。下列旧双包要求是长期架构验证目标，不是当前 R4 完成或合并门槛；以 `design/ui3/R4-CODE-TASKS.json` 为准。

> **规范级别：UI 最高权威（UI Authority）**
> **规范编号：UI-3.0 / 版本：3.0.0 / 生效规则：本文件合入 `main` 后即成为 UI 领域最高规范**
> **适用范围：** 777 所有生产 UI、设计包、AI 动态界面、布局、导航、组件、交互、动效、可访问性、UI 迁移和验收。
> **权威与事实的区别：** 本文描述应当实现的规范，**不声称可插拔底座已经在生产代码中落地**。已上线的真实功能、接口与行为以主线代码及对应验证证据为准。
> **依据：**《777 UI v3.0 · 可插拔界面底座与智能交互完整实施方案》前 0–12 章、777《架构 3.0》、现有 `LocalFeatureCatalog`、`LocalFeatureUiContribution`、V6 设计源及 v2.2-R2 核实结果。历史方案不自动成为本规范条款。

## 1. 规范定位与文档优先级

**UI 3.0 是一套长期有效的 UI 技术与体验契约，不是一套固定视觉皮肤。** 它的目标是：未来更换整套 UI 时，只需提供新的 UI 包、对应设计资产以及最少量注册配置，无须逐页改业务代码、重新连接模型/工具/媒体/记忆/任务的执行逻辑。

发生 UI 领域的设计冲突时，按下列顺序判定：

| 优先级 | 文档与事实 | 管辖范围 | 冲突处理 |
|---|---|---|---|
| 0 | `docs/ARCHITECTURE.md`（架构 3.0）及现行业务安全/持久化契约 | Feature 所有权、权限、运行时、事件事实、数据安全 | **不得被任何 UI 规范推翻**；UI 新需求必须遵守已有业务边界 |
| **1** | **本文件 `docs/design/UI-3.0.zh-CN.md`** | **UI 的跨设计包架构、行为、接入、替换、验收的最高规范** | **优先于全部其他 UI 设计文档、设计稿和历史 UI 方案** |
| 2 | 当前已发布 UI 包自己的规范（现为 `docs/design/v6/README.zh-CN.md`、`docs/UI-UX.zh-CN.md` 相关视觉章节） | **该 UI 包内部**的配色、排版、材质、组件、页面布局、动效 | 仅在不违反 UI 3.0 时生效；不能约束未来其他 UI 包 |
| 3 | 具体页面设计稿、Figma 文件、视觉预览、截图与素材包 | 具体 UI 包的设计意图与视觉验收 | 须服从上层契约；截图本身不证明真实功能正确 |
| 4 | v2.2、v3.0 方案、旧版本设计文档、历史 PR、过往 ZIP | 历史动机、缺陷证据及实施参考 | 与本规范冲突时自动让位，不作为新开发的默认依据 |

**优先级仅在各自职责内比较**：架构 3.0 是系统架构权威，UI 3.0 是 UI 领域最高权威。不得借“UI 最高规范”改变产品 Feature 的归属、审批规则、收费规则或真实运行状态。

本文修改时必须同步审查现有 UI 文档的冲突描述；禁止仅更换“唯一设计源”标题而继续保持互相矛盾的执行规则。UI 3.0 之外的设计包文件无权降低这里的接口、权限和验收要求。

## 2. 不可退让的设计目标

1. **整套可替换**：能替换信息架构、页面布局、导航、控件、图标、材质、动效和视觉语言，不止换色/换皮。
2. **功能一次接入，多 UI 使用**：同一业务功能以独立稳定的 UI 接口提供状态、动作、能力及结果；每套 UI 只负责自己的呈现与操作组织。
3. **事实唯一**：UI 只能展示或请求变更业务 Owner 持有的事实，不能制造第二套任务、进度、完成、审批、用量或媒体执行记录。
4. **可解释且可恢复**：错误、权限、未知结果、无数据、断线、后台与重启在不同 UI 下必须保持一致、可理解、可继续。
5. **体验和验收可证明**：以真实用户行为闭环和独立 V6 摆脱旧 Shell 的反向构建/运行测试验收；不得以截图、编译成功或组件数量替代。

**非目标：** 不把所有 UI 压成一种风格；不强迫新设计继续使用 `Sy*`/V6；不允许未授权的动态代码热加载；不将变更 UI 等同于变更真实业务执行器。

## 3. 唯一合法的 UI 接入结构

```text
Chat / Work / Project / Automation / Tools / Settings 的既有业务 Owner
                       ↓
              Feature UI Ports（业务插座）
     只读 Snapshot · 强类型 Command · Capability · Receipt
                       ↓
                UI Host（极薄宿主）
    生命周期 · 系统导航 · 返回 · 系统权限交互 · 恢复与兜底
                       ↓
           UI Pack（相互独立的界面插头）
      自己的页面 · 组件 · 布局 · 导航 · 材质 · 动效
                       ↓
                     用户
                       ↓
                  用户意图/输入
                       ↓
          业务 Owner 重新做准入、授权与执行
```

现有 `LocalFeatureCatalog` 维持产品功能的**单一归属**和当前 7 条一级路由；新 UI 包不得注册第二份业务所有权。不同 UI 包可为同一个 Scene 提供不同的渲染器，不得为同一业务任务建立不同的执行真相。

### 3.1 业务插座（Feature UI Port）

每个业务 Owner 向所有 UI 包提供稳定、可测试、版本化的独立契约：

- **Snapshot**：只读场景状态、可展示数据、加载/空白/失败/内容状态、身份和版本、事件来源及失效原因；不暴露业务可写对象。
- **Commands**：按业务领域划分的强类型操作，例如发送、编辑、重生成、真实审批、启动/停止、任务变更、媒体提交；禁止万能字符串执行入口。
- **Capabilities**：本次可用的操作、不可用原因、授权需求、风险或副作用含义；用于显示，不替代真实执行授权。
- **Receipts**：操作已受理、拒绝、等待确认、排队、失败、结果未知或完成等可核实回执；必须带可定位的来源/身份。
- **Identity & recovery**：会话、分支、消息、运行、项目、账户、任务代次和请求版本按实际业务需要绑定；操作前重新核验合法性。

**禁止** UI 包、UI Host 直接读取或写入 Feature 内部 `Store/Coordinator/Runtime`，也不得调用未经所属 Feature Port 暴露的工具、媒体、自动化执行方法。UI 防连点不是业务幂等保护。

### 3.2 场景协议（Scene / Slot Manifest）

每个需要用户到达的真实场景必须具有稳定的场景身份。一级页面之外还必须包括：

- 会话、消息时间线、输入区、模型/人物/群聊、运行步骤、审批、成果证据、媒体卡等**可组合插槽**；
- 编辑、确认、菜单、搜索、阅读、账户/模型选择、文件选择、费用提示、设置二级页等**非一级页面**；
- 加载、无数据、权限不足、失败、离线、已取消、结果未知、部分完成、过期、历史不完整、会话恢复等**行为状态**；
- 返回、深链、通知回跳、键盘/焦点、滚动位置、分支切换、跨会话和进程重建等**体验路径**。

建议的声明包含 `sceneId/slotId/owner/requiredCapabilities/minContractVersion/entryActions/restorePolicy/accessibilityRequirements`。实际结构以经过代码审查的强类型契约为准。这是**语义清单，不是硬编码 UI 布局模板**。

各 UI 包声明自己的场景覆盖范围。遗漏必需 Scene 必须阻止“整包替换完成”验收；迁移期若暂时使用旧界面兜底，必须显式标记，**不能把兜底当作新包已经实现**。V6 的 38 个设计场景是当前发布包的验收参考，不是所有未来 UI 包的场景上限。

### 3.3 UI Host（宿主）

仅负责通用 Android 系统服务、生命周期及契约路由：页面定位与返回、输入法、焦点、文件/分享选择器、系统权限界面、屏幕安全区、通知回跳、已授权设备反馈、无障碍入口、错误兜底及状态恢复。**不渲染具体业务风格、不解释业务完成条件、不直接执行任务。**

宿主不得为每个新 UI 包逐页增加 `if (pack == ...)` 分支。宿主 API 新增必须源于真正共用的能力缺口，且单独进行兼容性审查。

### 3.4 UI Pack（界面包）

每套 UI 包独立拥有：页面层级、导航展示、全量 Scene/Slot 渲染、组件库、排版/图标/材质、动效、状态外观、动态文档渲染及自身的视觉规范。其清单建议包含：

`packId / packVersion / minContractVersion / supportedScenes / requiredCapabilities / supportedWindowClasses / accessibilityCapabilities / fallbackPolicy`。

**UI 包不得引用另一个 UI 包的专用页面/组件或业务私有实现。** 例如未来新包不得依赖 V6 的 `LocalConversationSurface`、`SyButton`、`SyMaterialSurface` 才能完成核心功能。所有 UI 都应在相同业务插座下得到同样的真实回执。

## 4. 三种替换等级与发布边界

| 级别 | 可以替换的范围 | 发布与加载方式 | 边界 |
|---|---|---|---|
| 视觉资源包 | 配色、字体角色、图标、背景、标准动效参数 | 已内置或通过受控资源配置切换 | 不能宣称已更换完整交互布局 |
| 安全声明式布局包 | 已有语义 Scene 的布局、导航排列、组件组合与支持的动效 | 必须先有经过验证的受限协议与渲染器 | 未支持的复杂交互须扩展协议或 UI 包实现，不能执行任意脚本 |
| **完整原生 Compose UI 包** | **页面结构、导航、组件、交互方式和完整视觉语言** | 未来若预装多个包可按准入切换；全新包随 APK/AAB 发版，R4 不实施第二包 | 不把任意 Kotlin、HTML/JS 或未知 APK 当成可信配置热执行 |

**目标验收级别是“完整原生 UI 包可替换”。** 资源换肤和声明式布局是辅助能力，不能替代 R4 的独立 V6 真实业务行为验证。

## 5. 跨包统一的交互与事实语义

1. **执行状态、验证状态、用户操作需求必须分开**：执行结束不等于验证通过，更不等于用户验收。`CANCELLED` 与 `OUTCOME_UNKNOWN` 不得合并；取消是否安全重试须依据真实副作用证据。
2. **进度只能来源于真实运行事实**：步骤消耗不冒充完成百分比；Chat 文字预览关闭时不模拟流式推理；Todo 与团队任务不并账；媒体未知耗时不画假的进度比例。
3. **结果必须可追溯**：成果、错误和审批可定位到真正任务/消息/事件身份；未验证、不可判定、历史截断必须明示。
4. **用户操作必须可回执**：按钮可以被隐藏或禁用，但每次有效请求都应收到所属 Feature 的准确结果；不允许“点了没反应”或 UI 自行宣布成功。
5. **权限每次重验**：即使 UI 包已经展示按钮，提交时仍由真实业务 Owner 重新检查账户、能力、权限、会话/运行代次和可能的副作用。
6. **草稿与恢复**：切换 UI 包、离开页面、进程重启后，仍能恢复应保留的草稿和阅读状态；陈旧会话、分支、运行或项目绑定的旧动作必须失效，不能污染新状态。
7. **助手回复创作入口**：完整且有内容的助手回复，在下方操作区显示独立「创作」按钮；点击须携带该条回复的可见内容，打开统一多模态创作面板，由用户继续选择图片、视频、语音等受支持的能力与创作账户。不得要求长按文字才能创作，亦不得在点击按钮时直接提交付费生成；流式未完成、无可执行回调时不得展示空入口。

## 6. AI 智能交互 UI 属于同一标准插排

AI 生成的是**安全受约束的 `UiDocument` 内容**，不是一段可直接运行的 UI 程序，也不是一份自动拥有权限的业务命令。

固定流程：`模型输出 → 共享 JsonSchemaValidator + 专用节点/动作语义验证 → 合法持久引用与来源绑定 → UI Host 提供动态场景入口 → 当前 UI Pack 绘制 → 用户确认 → 真实 Feature Port 执行 → 读取真实结果原位更新`。

- 共享的数据/动作契约 **不依赖 V6 `Sy*`**；具体组件由当前 UI 包自己提供。
- 未通过验证的 JSON、未知节点/动作、脚本、任意命令或文件路径不得执行，必须有可解释的安全回退。
- Chat 不得为生成交互卡而偷偷获得 Work 工具权限；产生额外模型请求时要有真实用量记录。
- 动态卡仅为消息时间线的独立展示项，不能冒充普通助手文字并污染人物记忆、模型历史或媒体任务事实。
- UI 包切换不得重新触发已提交的收费任务，也不得将 `OUTCOME_UNKNOWN` 变成允许盲目重试。
- 初期采用**已校验完整快照 + 现有业务事实投影**；只有确认收益后再引入可恢复的 `UiPatch`。

## 7. 各 UI 包自由设计，但用户体验有公共底线

不同 UI 包**无需共用 V6 的三主题、暖纸材质、颜色、图标、圆角、交互层级或动画**。统一的是可用性结果，而非具体长相。

必须满足：

- 手机可达性、系统返回/预测返回、输入法/安全区、字体放大、深链定位、滚动追尾和长文回看；
- 无障碍语义与焦点顺序，不能只凭颜色传达状态；减弱动效、触控范围与对比度按明确的设计/平台验收门槛检查；
- 加载/空白/错误/权限/失效/结果未知/待审批/部分成功/已核验等状态不遗漏；
- 复杂页面有按需展开策略，不以信息隐藏、假按钮或无上限防御性限制换取视觉简洁；
- 后台刷新、局部结果、异步回执不强制跳转页面，不打断正在输入或阅读的用户；
- 安全权限/收费提醒必须真实清楚，不能用 UI 包自己的动效或文案消除必要确认。

每套 UI 包有**自己的设计令牌和视觉验收矩阵**；共用的是 Scene/Action/State 契约与最低用户行为验收条件。

## 8. 设计交付与新 UI 插入规范

设计稿/Figma/素材包只是设计输入，不能作为功能已实现的证明。新 UI 的标准操作路径为：

1. 将设计稿中的所有页面、弹层、状态、控件和动效对应到 `SceneManifest`，逐项检查已有业务 Port 能否承接；
2. 缺少接口时优先完善**共用业务插座**，禁止为了新 UI 私自调用 Store、工具执行器或复刻业务判断；
3. 在**独立 UI Pack** 实现自己的布局、导航、组件和动态文档绘制，不改已有 UI 包以求兼容；
4. 编译并检查声明的接口版本、全 Scene 覆盖和动作来源；
5. 在同一组业务事实与回执上分别运行旧 UI 和新 UI 的行为测试，再运行新 UI 的专属视觉/无障碍验收；
6. 保留稳定包回退能力；只有切换后不丢失会话、任务、草稿、输出和设置时，才能宣布可完整替换。

新增真正业务能力、宿主尚未提供的设备系统交互、或新增媒体格式允许单独扩展契约；**不能把新增业务的必要开发误判为插拔失败**，但 UI 换代不得借机更改旧业务执行语义。

## 9. 强制门禁与完成定义

### 9.1 架构门禁

- UI Pack 不能导入另一 UI Pack 的页面/组件或业务 `Store/Runtime/Coordinator`，不能直接使用 `LocalHarnessViewModel`、原 `LocalFeatureUiActions` 巨型回调或旧页面作为永久依赖；
- 功能路由 Owner 唯一；所有动作通过对应 Feature Port；UI Host 不承担业务运算、模型请求、工具执行、媒体提交或自动化调度；
- Schema 验证复用已有共享 `JsonSchemaValidator`；UI 节点协议只补领域专用校验，不创建第二个通用 JSON Schema 引擎；
- 新 UI 包不得让生产宿主出现针对自身设计的成片分支；特殊系统能力变更应单独审计。

### 9.2 可替换能力验收（R4 先验收独立 V6）

本次 R4 以**原 V6 功能在独立 `:ui-pack-v6` 中运行，且不再依赖旧 App Shell 页面**作为首轮完整验收。不开发 Next 或第二套 UI，也不要求双包在线切换、双包行为平权或双包设备 E2E。未来新 UI 包按本规范的中立 Port/Host/Scene 契约独立立项。

- Chat/Work 创建与切换、发送、编辑、重生成、附件、群聊/人物、历史/分支、输入草稿及阅读位置恢复；
- Work 审批/撤权、停止、部分结果、证据核验和结果未知；
- 媒体生成与已提交付费任务恢复，自动化、工具、设置和文件的真实 Owner 操作；
- 键盘/系统返回、通知深链、200% 字体、TalkBack、弱网/离线、跨进程恢复与异步迟到结果。

V6 独立包必须完成 75 个必需场景与 173 项动作的真实等价验证，不能用源码登记、伪造回执、旧 Shell 代画或合成测试替代。保留 Host 对未来多个界面包的中立兼容、准入与恢复能力，但 **R4 不要求实际内置第二包**。

### 9.3 验证证据

- 静态检查：模块依赖与所有权、接口版本、场景覆盖、动作权限、Schema 边界；
- JVM/Android 自动化：主任务闭环、历史恢复、状态一致性、崩溃后投影重建、深链返回；
- 设备验证：Android 16/17、真实键盘/返回、TalkBack、字体放大、背景与对比度、性能及弱网；
- UI 专属：每套包自己的主题、尺寸、布局、动效和目标设计稿比对。

**测试缺证不能标成通过。** 未覆盖的 Scene、临时旧页兜底、因 UI 更换而不得不修改的业务文件，应在交付报告中明示。

## 10. 迁移原则（不是长期双系统）

1. 盘点全部现行功能入口、二级页、弹层、状态与恢复路径，建立 Scene/Feature/Action/Owner 矩阵；
2. 在现有 App 内建立真实业务 Port 与系统宿主接口，先利用兼容桥接，不直接跨模块剪切 `internal` 类型；
3. 用 V6 包与一套异构极简 UI 包做第一轮**不改业务代码的真实操作试验**；
4. 再将 V6 页面、布局和导航迁移为独立 UI 包，删除不必要的兼容回调；
5. 接入 AI 动态文档、事件驱动渐进回复和成果证据，并由不同 UI 包分别绘制；
6. 最后通过编译模块/静态门禁证明 UI 包隔离，再把一次性兼容层清理干净。

当前 R4 已建立 `:ui-contract`、`:ui-host`、`:ui-pack-v6` 的代码模块；未来新增 UI 包另行立项，不能将已取消的 `:ui-pack-next` 视为必需模块。

## 11. 规范治理与冲突处理

- 本规范是**唯一跨 UI 包的 UI 设计与接入权威文档**。每套 UI 包可以发布自己的设计系统和逐屏验收方案，但只能细化自己的视觉实现，不能改写此文件的全局行为合同。
- `docs/UI-UX.zh-CN.md` 作为当前交互实施说明；`docs/design/v6/*` 作为现行 V6 UI 包设计和视觉事实源。它们不能强制其他 UI 包使用 V6 外观、旧页面或 V6 组件名。
- 提交新设计或新增 UI 能力时，应先比对本规范的 Scene/Port/Host/Pack 边界；真正需要改变共用合同，应单独提出规范修订并同步更新接口、CI 与迁移兼容策略。
- 新规范版本必须明确：新增/修改的合同条款、影响的 UI 包、兼容策略、迁移期限和对应测试；禁止只改旧设计文档，造成“看起来一致、代码里没执行”的伪完成。
- 当本文与主线业务真实行为冲突时，不得偷偷变更业务事实；应提交架构/规范冲突记录，先确定责任归属，再单独修改对应业务能力或本规范。
