# 777 智能体自主补齐能力：运行链与验收

## 基线与真实问题

2026-10-23 用户在手机 Work 模式创建本地 X/Twitter MCP stdio 服务，连接成功、注册了九个工具，却在同一轮继续调用 `mcp_x_twitter_x_post` 时得到 `TOOL_NOT_EXPOSED`。这并不等价于服务创建失败：服务注册表与**本次模型请求实际提供的工具定义**是两套不同时间点的数据。原有单工具执行已检查当步暴露，Work 批量执行入口缺失相同检查。

## 本次修复

1. Work 每次请求工具定义时对比本会话已观测的实时 ToolRegistry。只有在首个工具表形成后新出现的 MCP 可选工具才优先进入后续模型请求；已断开的工具从待选集合移除。旧 MCP 服务仍可使用 `capability_search` 和用户显式固定入口，不把所有已安装扩展塞入每次请求。
2. Work 的批量调用和单次调用一样，必须持有当步工具表中已暴露的工具名。未暴露工具返回 `TOOL_NOT_EXPOSED`，不会进入执行器，也不能通过同一个批次前面的连接动作取得权限。后续步骤重新暴露后方可调用。
3. 缺少能力时，Work 按实时目录 → GitHub/官方实现 → 本机脚本或自建 MCP → 注册 → 下个模型请求工具定义 → 真实调用测试 → 记录与复用的路径推进。依然遵守源代码校验、凭据隔离、工具审批、工作区权限和第三方平台授权。
4. 插件层的外部 Android DEX/JAR 动态载入仍未实现，不能把 MCP 服务冒充可独立安装的原生插件。需要原生能力时由工程构建与发布链交付。

## 验收场景

- 原步：`mcp_stdio_connect` 已暴露；新创建的 `mcp_x_twitter_x_post` 没有被暴露，单次或混合批次均不可执行。
- 下一步：真实 MCP 注册表新增工具；Work 以当次会话观测为准优先推荐新工具；模型工具定义预算可容纳时，实际暴露新工具，按既有审批执行。
- 断开：工具从实时注册表消失后不能重新装入，更不能自动重放写入调用。
- 大目录：工具预算不足时仍给出原因和 `capability_search` 精确发现路径，不能假装工具已可调用。
- 认证失败：不能将 reader 网页抓取、X 官方 API 或用户 Token 混为一谈；不得把抓取回执误报为已验证的数据。
- 工作区复用：已安装技能可通过 `SKILL.md` 复用；本机 MCP 脚本应存放工作区，由实际连接状态决定是否可执行。

## 检查边界

本 PR 增加动态 MCP 优先激活和批量暴露检查的 JVM 回归测试。CI 通过才可确认静态编译和单元层面；Android 16/17 设备上复现九工具连接、逐个业务调用、断线恢复及重启后的配置恢复仍需独立签收，不得以注册成功代替业务成功。

## 第二批：可调用工具和持久工作区记录

- 原生 `skill_create` 调用原有 LocalSkillStore.create 并读取 `SKILL.md` 核验，避免智能体只写个模板却未真正安装。
- `skill_update` 保存原版哈希文件再写入和复读；`skill_rollback` 校验版本内容并保留当前版本，支持可逆迭代。
- `extension_record` 为技能、工具、连接器、MCP、插件的创建/注册/测试/改进/失败保存工作区记录，且测试声明必须指向现存证据文件；记录中明确标为尚未独立核验。
- `extension_inspect` 从真实技能、ToolRegistry、PluginManager 获取当前状态，避免将本地脚本或记录冒充已注册工具。
- 自动生成 .dsh/extensions 下四份长期文档：EXPERIENCE.md、IMPROVEMENTS.md、PROMPT-CHANGES.md、ISSUES.md，供用户随时读取并后续维护。不能凭空自动声称已优化提示词。
- 所有变更工具共用既有模型可见工具表、工作区权限与审批机制，不建立第二套注册器，也不绕过运行时审核。

新增回归测试覆盖技能创建、版本备份/回退、数据记录核验与动态注册状态。
