# Agent 工具执行与故障恢复指南

本文对应当前 Android Harness 的工具调用契约。所有模型和智能体优先通过**工具自己的描述、参数与真实执行回执**确定下一步；本页提供用户、开发者和调试工具可共同复查的示例。实际权限、审批、状态与验证由工具执行器判断。

## 1. 工具编排：直接引用真实返回正文

`code_mode_run` 中的 `steps` 从 **1** 开始编号。先执行有结果的工具，后续的 `when.step` 引用此前的步骤；`when.path` 是**该工具返回的正文 JSON 内部的字段**。不需要拼 `steps[0].content`、`result.output` 等外围结构。

前序工具真实返回 `{"approved":true}` 时：

```json
{
  "steps": [
    {"tool": "check", "args": {}},
    {
      "tool": "next", "args": {},
      "when": {"step": 1, "path": "approved", "equals": true}
    }
  ]
}
```

`check` 和 `next` 仅为演示步骤；调用时替换成当前工具表中存在的真实工具及其参数。

- 返回 JSON 对象：按实际字段写 `path`，支持 `approved`、`$.file.path`、`items[0].name`；`equals` 保持真实 JSON 类型（布尔值、数值、字符串）。
- 返回普通文本（如 `ready`）：省略 `path`，直接以 `{"step":1,"equals":"ready"}` 比较整个结果。
- 后续参数取值：使用 `{"$step_result":1,"path":"file.path"}` 引用前序结果字段，省略 `path` 可传递整个结果。
- 可选工具：先通过 `capability_search` 找到并加载，待模型收到包含该工具的下一轮实际工具表，再用于编排。

字段找不到时，回执会指出字段路径和实际 JSON 对象的可用字段；结果为普通文本时，明确提示去掉 `path`。当条件引用失败，后续步骤不会假装执行成功。

## 2. Android 输入：先定位，后写入，按实际结果决定下一步

优先使用 `android_input_text`，避免固定依赖会随界面变化而漂移的 node 编号。

1. 已知控件资源 ID：`android_input_text({"id":"<当前控件 ID>","value":"新文字"})`。
2. 输入框已经聚焦：`android_input_text({"value":"新文字"})`。页面仅有一个可编辑框时，也支持自动定位。
3. 不知道控件 ID：`android_find` 查找目标后，依据真实结果使用 `id`；只有无法通过 ID/焦点确定时才使用本次观察得到的 `node`。
4. 界面切换后重新查找目标；不要依赖早先页面的树编号。

`android_type`、`android_set_text_node` 和 `android_input_text` 共用同一个写入与验证过程。三个输入工具统一返回：

| 返回码 | 实际状态 | 适当的后续动作 |
|---|---|---|
| 成功（`true`） | 已回读目标内容 | 继续下一任务 |
| `ANDROID_INPUT_TARGET_UNAVAILABLE` | 当前界面无法确定目标输入框 | 重新读取界面，选择正确 ID / 焦点 |
| `ANDROID_INPUT_ACTION_UNCONFIRMED` | 已定位目标，系统未确认接受写入请求 | 读取当前文字后判断 |
| `ANDROID_INPUT_READBACK_UNCONFIRMED` | 系统已接受写入请求，未能确认同一控件中的最终内容 | 再读当前界面；内容确实不符时再修改 |

清空文本也使用 `value:""`。回读未确认时首先核对实际值，可避免已经清空却反复写入。

剪贴板清理使用 `android_clipboard_clear`，或 `android_clipboard_set({"text":""})`。空格是普通文本。

## 3. Work 成果与验收：看具体证据

成果与验证根据当前 Goal、真实工具调用、执行记录和文件版本核验。模型自称“通过”不能替代执行证据。

- “验收命令尚无当前目标下的真实执行记录”：直接单独执行 Goal 声明的原始命令；与其他命令拼接后无法匹配。
- “验收命令最新执行失败”：检查该次执行的退出码与输出，修复对应错误，再运行原命令。
- “验收命令没有可核验的退出码”：检查执行工具是否产生了可核验的正常退出结果。
- “成果文件不存在或无法读取”：确认实际产物已落到 Goal 声明的路径。
- “成果版本已变化”或“验收后成果版本已变化”：对最新文件再次执行原验收命令，确认新版本后结算。

结算失败不会清除已经通过核验的进度。针对当前具体原因操作即可，无需重建整个 Goal。

## 4. 后台任务、团队与虚拟屏

后台任务通过 `job_list` 查询、`job_output` 读取、`job_kill` 终止。持久代理用 `agent_inspect` 查看、`agent_close` 关闭；Team 可以用 `team_stop_all` 停止全部正在运行的成员激活（保留身份和恢复状态）；暂时停用指定成员用 `team_disable_member`（释放未完成任务）；永久移除成员用 `team_dismiss_member`（终止 Agent 并释放任务）；需要成员自主同意关闭时走 `team_request_shutdown` → `team_respond_shutdown`。按真实任务 ID 操作，分别检查运行状态、保留身份和历史记录，避免把已停止任务误当占用槽位的执行。

虚拟屏启动优先用 `android_vscreen_start`，失败时系统是否允许应用在目标显示器启动是 Android 平台决定的；本次启动失败会清理刚创建的虚拟显示。分析平台拒绝原因时记录返回的系统异常，不通过重复创建虚拟显示绕过系统限制。

## 5. 系统诊断与运行时存储

普通 Android 应用可见的 `/proc`、`dumpsys`、`pm` 数据会受到 SELinux、系统权限与多用户空间约束。诊断从**实际可读取的指标**出发；进程被终止应优先查应用可获得的系统进程退出记录，不能单凭 `MemFree` 推断低内存击杀。

运行时库按内容 SHA-256 复用 canonical blob，安装时优先使用硬链接。同名或同体积的多个 `.so` 路径，需在真机查看 inode、链接数和实际分配块后才能判断是否发生物理重复占用。

## 6. 维护约定

当修改工具参数、返回码、行为或操作顺序时，同步更新该工具的模型可见 schema/metadata、本页对应条目和实际回归测试。文档讲操作方法，工具回执给出当下真实状态；避免另建与源码容易脱节的故障规则副本。
