# 全量系统联审规范

> 本文件是仓库内进行全量代码联审、系统架构审计、功能成熟度审计、性能与体验联审时的**权威规范**。
>
> 当本文件与临时审计提示词、历史聊天结论、旧阶段检查表冲突时，以当前代码、`AGENTS.md` 以及本文件为准。历史审计结论不得代替当前代码事实。
>
> 可跨功能、跨模块、跨 PR 复用的稳定审计规律独立维护在 `docs/SHARED-AUDIT-CONCLUSIONS.zh-CN.md`。具体问题与共享结论分开记录：具体问题保留本次代码证据，共享结论只沉淀可复用规律。

## 1. 审计目标与完成标准

全量联审最终要回答四个问题：

1. 哪些功能目前只是能用，还没有达到长期稳定、可恢复、可扩展的完整实现？
2. 哪些模块已经成为其他功能的公共短板，会拖累完整功能链？
3. 哪些问题会随着时间、数据量、并发、会话数量和功能增长持续恶化？
4. 哪些根因修复后，可以同时消除一批关联问题并提升系统上限？

审计完成标准：

```text
当前代码事实准确
+ 功能链完整
+ 横向关联已核
+ 纵向调用链已核
+ 所有权与依赖已核
+ 字段 / 配置 / 契约已核
+ 数据与生命周期已核
+ 持久化与恢复已核
+ 并发与异步已核
+ 性能规模化已核
+ 用户体验已核
+ 工程质量已核
+ 安全与可观测性已核
+ 候选问题已沿调用链复核
+ 已解决项已剔除
+ 误报已撤回
+ 根因已归并
+ 可共享结论已提炼
```

禁止以“CI 全绿”“功能能运行”“某个单测通过”替代系统联审。

## 2. 审计前置：先锁定权威基准

开始联审前必须：

1. 读取 `AGENTS.md`。
2. 读取与本次范围相关的当前权威文档：
   - `docs/ARCHITECTURE.md`
   - `docs/SECURITY.md`
   - `docs/VALIDATION.md`
   - `docs/PROTOCOL.md`
   - `docs/COMPATIBILITY.md`
   - `docs/UI-UX.zh-CN.md`
   - `docs/SHARED-AUDIT-CONCLUSIONS.zh-CN.md`
   - 其他直接相关的当前文档。

   当前架构事实以 `ARCHITECTURE.md`、当前代码、`architecture-3-gates` 和真实生产装配共同确认。审计必须把每项能力映射到当前 Feature / Shared Capability / Runtime Kernel / 应用组合根 / UI projection 边界，并以当前真实 Owner、公开 Port、状态与配置事实源作为判断依据。
3. 锁定：
   - 当前最新 `main` SHA；
   - 当前活动 PR；
   - 目标 PR 最新 Head；
   - 如审计“合并后效果”，使用当前 `main + PR head` 的真实组合基准。
4. 审计期间如果 `main`、PR Head、关键配置、测试或 CI 基准变化，旧结论必须重新核验。

禁止：

- 用旧 PR 结论代替最新代码；
- 只看 diff 不看全量调用链；
- 只看注释不看真实行为；
- 只看设计文档不核当前实现；
- 只查报错文件不查上下游；
- 因共享结论曾经成立就跳过当前代码复核。

## 3. 总体审计方法

### 3.1 先建立系统地图

所有具体检查开始前，先建立：

- 一级 Feature 与 Shared Capability；
- 状态、数据与配置的权威 Owner；
- 主要 Coordinator / Registry / Policy / Store / Runtime；
- 主要公开 API / Port；
- 关键调用链与旁路；
- 前台、后台、恢复入口；
- 公共基础能力和系统 choke point；
- 热点大文件、共享状态和高风险异步边界。

先回答：

```text
输入从哪里来
→ 谁负责这项能力
→ 谁拥有权威状态 / 配置
→ 谁执行副作用
→ 谁消费结果
→ 生命周期如何结束
→ 失败 / 取消 / 恢复如何处理
→ 用户最终看到什么
```

系统地图至少产出四张可核对清单，禁止只画概念图：

1. **入口表**：入口名称、触发条件、调用对象、前台/后台、手动/自动、是否可恢复；
2. **所有权表**：能力 Owner、状态 Owner、配置 Owner、副作用提交者、持久化 Owner；
3. **契约表**：公开 API / Port、DTO / Event / State、字段、Schema / version、消费者；
4. **装配表**：DI / composition root、Feature / Page / Tool / Worker / Registry 注册、Manifest / 权限、导航与恢复入口。

任一能力无法落到这四张表中的明确位置时，默认继续追查，不能直接判定边界完整。

### 3.2 横向与纵向同时检查

横向比较：

```text
Chat / Work / Automation / Subagent / Group Chat
前台 / 后台 / 恢复
本地 / 远程 Harness
单聊 / 群聊
当前会话 / 跨会话
模型 / Web / Vision / Tool / MCP
```

重点比较是否统一复用：

- Model Routing；
- Credential；
- Token Budget；
- Tool Registry；
- Approval；
- Resource Scheduler；
- Session；
- EventLog；
- Memory；
- Persistence；
- Recovery；
- Observability；
- Security Policy。

纵向沿完整链路检查。链路按真实 Owner 展开，禁止套用旧的固定“UI → Coordinator → Runtime → Store”层级模板：

```text
用户操作 / 自动触发
→ UI
→ Feature API / presentation / projection
→ 领域 Feature Owner
→ Shared Capability（仅在需要跨 Feature 中立能力时）
→ 外部 Model / Tool / Platform（如适用）
→ 领域事件 / 状态提交
→ Shared persistence / runtime owner（如适用）
→ 恢复 / 投影
→ UI 最终反馈
```

Runtime Kernel 只按架构 3.0 承担 start-once、生命周期 scope、bootstrap / recovery 触发和初始化错误投影；不得因为链路图方便，把领域业务默认画进 Kernel。

重点发现：

- 上游成功、下游失败；
- 下游成功、上游未更新；
- 中间层静默降级；
- 状态跨层丢失；
- 同一字段跨层语义变化；
- 主路径更新、旁路仍停留在旧实现；
- 每个模块单独正常，组合后出问题；
- UI 显示成功但 durable state 未成功；
- 部分成功留下半提交状态；
- 磁盘满、权限失败、IO 中断后的内存状态是否错误宣告成功；
- 并发 writer 是否会互相覆盖；
- temp / backup / primary 的恢复优先级是否唯一且可解释；
- 恢复完成后是否清理过期 running / pending / lease 状态；
- migration 中途崩溃再次启动是否安全；
- terminal state 与副作用提交顺序是否避免“副作用已发生但状态仍可重放”。

横向比较不能只看“是否都调用了同一个类”，还必须逐项比较：

- 正常成功状态转换；
- 失败分类与错误传播；
- 取消后的真实停止边界；
- timeout 后资源释放；
- retry 是否安全、是否仍为同一身份与路由；
- 恢复后由谁继续拥有任务；
- 配置变化对已启动 Run 与新 Run 的不同语义；
- 最终持久状态与用户可见状态是否一致。

### 3.3 根因、公共短板与长期演化

禁止停在表象。

```text
表象
→ 直接原因
→ 共享基础能力
→ 数据模型 / 生命周期 / 架构原因
→ 真正根因
```

必须回答：

> 哪个组件的能力上限，正在决定整个系统的能力上限？

重点关注：

- 一个公共底层短板拖累多条功能链；
- 相同业务规则在多个功能重复实现；
- 主路径与旁路存在不同所有权；
- Store / EventLog / Recovery / Route identity 等公共能力成为上限；
- 随 Session、Memory、Automation、MCP、模型供应商和后台任务增长而持续恶化；
- 新功能每次都要修改多个核心模块；
- 巨型 Store、Manager、when/if、缓存或配置对象持续膨胀。

同一根因导致多个问题时，合并为一个系统问题并列出全部影响链。

### 3.4 反向验证

从产品能力反向追代码：

```text
产品声明
→ UI 入口
→ 所有真实入口
→ 所有旁路
→ 状态 / 数据
→ 持久化
→ 恢复
→ 测试
→ 当前真实行为
```

重点检查：

- 文档说支持，代码只支持一半；
- UI 有入口，底层未闭环；
- 代码已有能力，但目标功能没有真正接入；
- 注释说后台继续，真实代码会取消；
- 测试把不合理实现固化成“正确行为”。

反向验证至少要给出四类证据中的适用项：

- 产品声明 / UI 文案来源；
- 真实入口与调用方；
- 运行时状态或持久化事实；
- 对应测试、门禁或设备行为。

如果产品声明无法一路追到运行事实，必须标记为“声明存在、实现证据不足”，禁止凭代码名称推断已经支持。

### 3.5 功能成熟度判定

每个功能都要判断成熟度，不能只分“有 / 无”：

1. 能否运行；
2. 正常路径是否完整；
3. 异常路径是否完整；
4. 边界条件是否完整；
5. 后台是否完整；
6. 取消 / 超时 / 重试是否完整；
7. 重启恢复是否完整；
8. 长期运行是否稳定；
9. 大数据量是否稳定；
10. 多会话 / 并发是否稳定；
11. 是否达到当前架构下较优实现。

重点找：

- 只能用；
- 基本可用；
- 最后一公里缺失；
- 实现只有 70%–90%；
- 小规模好用、大规模退化；
- 前台完整、后台不完整；
- 当前会话完整、恢复后语义变化。

成熟度判定不能只给比例，必须写清“缺的是哪一环”。至少区分：

```text
入口完整性
业务链完整性
异常完整性
生命周期完整性
持久化 / 恢复完整性
规模化完整性
设备 / 用户体验完整性
验证证据完整性
```

任何一项缺失，都不得用“功能已完成”概括。

## 4. 具体审计维度（按同类归组）

### 4.1 功能、架构、所有权与契约

#### 功能协作与横向一致性

检查：

- 各功能单独可用时，组合后是否仍然正确；
- 是否存在重复能力、职责冲突、职责空洞；
- 是否存在同一种能力多个功能各做一套；
- 某功能已经优化，其他功能是否仍成为短板；
- 同类能力是否共享数据却不共享生命周期；
- 是否存在新旧能力长期双轨；
- 是否存在多个事实源；
- 是否存在超级管理器或系统 choke point。

对 Chat / Work / Automation / Subagent / Group Chat / Remote 横向比较：

- 路由；
- 凭据；
- 权限；
- 工具；
- 资源预算；
- Token；
- Session；
- EventLog；
- Memory；
- Persistence；
- Recovery；
- Diagnostics。

任何同类能力实现不一致，都必须判断是合理差异还是架构漂移。

#### 架构所有权与依赖

检查：

- 高内聚、低耦合；
- 单一职责；
- 单向依赖；
- 每项业务事实只有一个权威 Owner；
- 每项能力有明确且唯一的公开进入边界；
- Registry / Coordinator / Policy / Store 按所属 Feature 或 Shared Capability 分域归属，不建立跨域“全局总管”；
- Shared Capability 只承载真正中立、可跨 Feature 复用的能力；
- Runtime Kernel 不承载 Feature 领域业务；
- 可热插拔；
- 同一能力的生产调用、状态写入、配置写入和装配入口是否收敛到一个明确 Owner。

重点找：

- Feature 互相导入 internal；
- UI 直接引用领域 Store / Coordinator / Service / Runtime；
- Shared Capability 反向依赖 Feature；
- 跨层穿透；
- Store / Policy / Gateway 旁路；
- UI 承担领域逻辑；
- 业务规则复制；
- 多个平行 Manager / Registry；
- 参数堆积掩盖职责混乱；
- 代码位置与业务 Owner 不一致；
- 同一业务事实存在两个及以上可写 Owner；
- composition root / DI 对同一能力装配多个生产实现；
- Feature / Page / Tool / Worker / Registry 出现重复注册或路由归属不唯一；
- Shared Capability 开始解释 Feature 专属领域语义；
- Feature 持有完整聚合可写状态，绕过领域状态边界；
- Runtime Kernel 承载具体 Feature 业务、领域状态或 Provider 装配；
- Shell 超出导航宿主职责，持有 Feature 业务状态或执行领域规则；
- SettingsFeature 超出设置入口职责，持有其他 Feature 的真实配置事实；
- UI 绕过 presentation / Feature API / projection 直接消费内部实现；
- `LocalHarnessState` 兼容聚合被重新作为领域权威状态或双写入口；
- Session owner、Agent run identity、迟到提交栅栏、recovery coordination 出现第二套所有权；
- FeatureCatalog 路由、页面 contribution、Back / Drawer / restore policy 的 Owner 不唯一。

#### 功能设计与实现度

反查功能本身：

- 功能目标是否清晰；
- 用户真正需要的能力是否实现；
- 默认行为是否合理；
- 功能之间是否设计冲突；
- 是否为了实现方便牺牲体验；
- 是否暴露不必要复杂度；
- 是否有入口但无闭环；
- 本应自动完成的工作是否转嫁给用户；
- 是否技术上正确但产品行为不合理。

#### 代码、文档、测试与 UI 契约一致性

交叉对比：

```text
注释
文档
测试
UI 文案
实际运行代码
```

任何一方都不能单独作为事实，必须沿真实调用链交叉验证。

#### 4.21 功能链路与契约逐项对账

任何功能不得只验证单个模块、单个入口或主调用链能够工作。

必须以完整功能为单位，对所有真实入口和关联模块逐项建立对账链：

```text
功能目标
→ 所有触发入口
→ 导入与依赖
→ 权威状态 / 数据源
→ 字段与类型
→ 配置 / 默认值 / 常量 / 枚举
→ Coordinator / Runtime / Store
→ 下游消费者
→ 关联功能
→ 生命周期变化
→ 异常 / 取消 / 恢复
→ UI / 用户最终结果
```

强制检查：

0. **先做全量发现**
   - 搜索能力定义、全部调用方、全部构造点和全部注册点；
   - 搜索状态 / 配置的全部 writer、reader、collector、callback 和 serializer；
   - 搜索同名或同语义的旧实现、兼容入口、fallback、测试替身和后台入口；
   - 不能只从当前 UI 点击路径向下追一次就结束。

1. **全入口一致性**
   - 页面操作、生命周期回调、后台任务、自动刷新、恢复、通知 / Deep Link、定时任务、快捷入口、外部事件是否进入同一权威业务边界；
   - 主路径走高层统一入口、旁路直接调用底层实现时，默认进入候选问题复核；
   - 手动路径与自动路径必须比较完整业务语义，不能只比较底层函数是否相同。

2. **上下游状态对账**
   - 生产者成功更新状态后，Projection、Store、Flow / Callback、Consumer 与 UI 是否均获得并处理最新结果；
   - 下游成功后，上游展示和控制状态是否同步；
   - 后台更新、页面重建和恢复后是否仍能重新获得当前状态。

3. **字段契约对账**
   - 字段名、类型、可空性、默认值、单位、枚举全集、时间基准、ID 含义、状态语义、序列化 key、schema / version 必须逐层核对；
   - 新增、删除、改名字段后必须检查全部消费者、转换层、持久化和恢复路径。

4. **配置与定义对账及共享配置提取**
   - 默认值、上下限、超时、重试、feature flag、能力定义、Enum、Schema、JSON key、UI 可选项、测试 fixture、构建配置和文档说明必须横向比较；
   - 发现两个及以上功能、模块或入口维护同一业务语义的配置时，必须进一步判断是否属于可共享配置；
   - 是否上收 Shared 必须先按业务所有权判断，不能仅因“多个功能都在使用”就改变配置 Owner；
   - 真正中立、跨领域、无 Feature 专属业务语义的配置，才收口到 Shared Capability 下的 Configuration / Policy / Registry / 数据事实源；
   - 属于某个 Feature 业务语义的配置继续由该 Feature 单一拥有；其他 Feature、Settings 或 UI 只能通过稳定 Port / Feature API 配置或读取；
   - 功能侧允许持有运行期快照或派生视图，但必须可追溯到权威配置 Owner，不能反向成为第二事实源；
   - 配置变更必须检查所有消费者、持久化、迁移、恢复、缓存失效和 UI 投影是否同步；
   - 只有明确领域语义、平台差异、协议差异或生命周期差异时才允许保留独立配置；
   - 禁止为了统一把无关配置全部塞进一个巨型全局配置对象；
   - 存在无依据差异、重复维护或多事实源时，按配置漂移 / 架构问题处理。

5. **依赖、导入、声明与装配对账**
   - 同类入口是否通过同一公开 API / Port / Coordinator；
   - UI 是否直接导入领域 Store / Service / Repository / Gateway；
   - Feature 是否导入 sibling Feature internal；
   - 是否绕过统一 Registry / Policy / Gateway；
   - Gradle/module 依赖方向是否与架构一致；
   - DI provider / binding / composition root 是否只装配一个权威实现；
   - Feature catalog、页面 contribution、导航、Back / Drawer / restore 是否全部注册；
   - Worker / Job / Tool / MCP / serializer / codec / registry 是否注册到真实生产入口；
   - Manifest、权限、intent/filter、deep link、foreground service 等声明是否与代码入口一致；
   - 同一能力是否只保留一套生产依赖、注册、provider、worker、serializer / codec 和真实执行入口；
   - debug/test 注册不得误进入 production，production 注册也不得只在测试中存在。

6. **关联功能协同**
   - 一个组件状态变化后，所有依赖该变化的组件是否收到通知并完成对应动作；
   - 不能因各组件单独正确就判定组合功能正确；
   - 必须显式检查状态传播顺序、消费关系和最终用户感知。

7. **自动能力闭环**
   - 自动刷新、同步、恢复、迁移、清理、重试等能力必须从触发一直验证到最终业务状态；
   - 定时器触发、网络请求成功、Worker 成功或 Store 写入均不能单独作为完成证据；
   - 自动入口失败后必须核对重试、退避、下次触发、错误可见性和是否留下半更新状态。

8. **兼容与版本演进**
   - 新旧 schema、无 schema、非法 version、未知字段、未知枚举 / 事件必须有明确策略；
   - 历史数据升级、混合新旧字段、迁移重复执行、降级 / 回退边界必须验证；
   - 新代码读取旧数据与旧数据经过新代码再次写回后均不能丢失仍受支持的信息。

9. **验证证据**
   - 每条链至少有一种能够证明真实行为的证据：单元 / conformance / instrumentation / 设备复验 / CI 门禁 / 持久化事实；
   - 测试必须覆盖本次真正风险点，不能只覆盖相邻函数；
   - 验证结果必须绑定当前 PR Head；Head、主线、依赖或门禁变化后旧结果失效。

完成判定：

```text
所有真实入口已核
+ 上下游完整
+ 依赖方向正确
+ 字段契约一致
+ 可共享配置已收口到正确的唯一 Owner
+ 独立配置差异有明确依据
+ 关联功能协同
+ 自动与手动路径语义一致
+ 注册 / DI / Manifest / Registry 装配完整
+ 兼容与版本演进路径完整
+ 生命周期完整
+ 异常路径完整
+ 最终用户结果正确
+ 验证证据覆盖真实风险且属于当前 Head
```

发现同一根因影响多个入口或功能时，归并为“链路闭环 / 契约一致性问题”，列出全部受影响链路。

满足共享条件时，必须独立沉淀到 `docs/SHARED-AUDIT-CONCLUSIONS.zh-CN.md`，具体问题与共享结论不得混写。

### 4.2 数据、状态、字段、持久化与恢复

#### 数据与事实源

跟踪核心数据完整生命周期：

```text
产生
→ 转换
→ 传递
→ 缓存
→ 修改
→ 持久化
→ 查询
→ 恢复
→ 失效
→ 清理
```

检查：

- 是否有唯一事实源；
- 是否有重复 / 过期副本；
- Snapshot 与 EventLog 的职责是否清楚；
- 内存与磁盘状态是否一致；
- Session 与 Gallery / Memory / Job / Automation 是否存在多点所有权；
- 缓存与 durable state 是否冲突；
- 删除后旧异步写是否还能回写；
- generation / version / CAS 是否完整；
- 数据恢复后的身份与版本是否一致；
- 是否存在错误转换；
- 是否越权流转；
- 是否进入不应进入的模型上下文；
- 是否该删除却长期保留；
- 是否冷数据持续侵入热路径；
- 多 Store 更新是否具备明确提交顺序、事务或补偿；
- 同一事件是否可能被重复消费，幂等键 / 去重键是否稳定；
- 删除、撤销、取消是否有 tombstone / generation / version 防止旧数据回潮；
- 私有 / 可共享 / 公开等可见性是否在写入、持久化、召回、导出全链一致；
- 数据保留、过期、归档、删除后的引用清理是否闭环。

#### 字段与 Schema

重点核对：

- 字段名称、类型、可空性、默认值；
- 枚举全集与未知值处理；
- 单位、时间基准、ID 语义；
- JSON / DB key；
- schema / version；
- 新旧字段迁移；
- decode / encode / normalize / projection 是否一致；
- 恢复后字段语义是否变化；
- encode → persist → decode 是否可 round-trip；
- 未知字段是否按契约忽略 / 保留，而非意外覆盖；
- 未知事件 / 内容类型是否保留 passthrough 或可诊断信息；
- 无 schema / 旧 schema / 新 schema 混合时，已编辑新值是否会被旧字段覆盖；
- 非法 version 是否明确拒绝，而非静默回退成旧格式；
- migration 是否幂等，重复启动不能二次破坏数据。

字段详细对账同时遵循 4.21。

#### 持久化与恢复

所有 Store 检查：

- atomic write；
- backup；
- fsync；
- temp；
- schema / version；
- migration；
- corruption；
- crash window；
- terminal state；
- recovery semantics。

重点找：

- 整库重写；
- 高频 fsync；
- 大 JSON 持续增长；
- 主备都坏后静默变空；
- Store 之间恢复语义不一致；
- terminal state 写失败被吞；
- 内存完成、磁盘仍 running；
- 恢复误判；
- 重启后重复执行；
- 部分成功留下半提交状态。

### 4.3 生命周期、并发、异步与后台

#### 生命周期

覆盖：

- 创建；
- 打开；
- 切换；
- 删除；
- 运行；
- 后台；
- 暂停；
- 取消；
- 超时；
- 完成；
- 失败；
- App 后台；
- 进程被杀；
- 重启；
- 配置中途变化；
- 插件安装 / 卸载；
- 网络断开 / 恢复。

所有生命周期路径必须与手动路径做语义对账。

还必须覆盖：

- 页面离开 / 返回、导航栈重建；
- 配置变化与 Activity 重建；
- App 前后台切换；
- 进程死亡后冷启动恢复；
- Worker / Job 被系统停止后重调度；
- 用户切换 Session / Account / Model 时旧任务是否失效；
- 权限被撤销、网络恢复、存储重新可用后的状态收敛。

#### 并发与异步

重点检查：

- Mutex / synchronized 锁粒度；
- Queue / Channel 上限；
- Flow / CoroutineScope 生命周期；
- WorkManager；
- async / launch；
- generation；
- cancellation；
- retry；
- backpressure。

重点找：

- 独立任务被全局锁串行；
- 同一 Session 本应串行却并行；
- 旧结果覆盖新结果；
- 取消后继续落盘；
- CancellationException 被吞；
- 无限重试；
- 无界队列；
- 新 Owner 接管后旧任务继续提交；
- 前台与恢复逻辑同时拥有同一任务；
- 执行期间读取可变全局配置改变已启动任务身份；
- 同一身份离开后返回形成 ABA，旧结果误认为仍属于当前操作；
- 同渠道后发先回，旧请求覆盖新请求；
- 不同渠道本可并行却被全局锁串行；
- duplicate trigger / 双击 / 重复 Worker 导致重复副作用；
- timeout / cancellation 只停 UI，不停止真实网络、工具或后台任务；
- retry 缺少幂等依据，对副作用未知状态盲目重放；
- lease / generation / requestId / runId 未贯穿到最终提交点。

### 4.4 模型、凭据、工具与外部系统

#### 模型路由与运行身份

逐项核对：

- profileId；
- provider；
- model；
- baseUrl；
- authKind；
- protocol；
- credentialRef；
- route fingerprint；
- capability snapshot；
- context window；
- tool schema；
- prompt / history / memory；
- Token usage。

必须检查：

- Run、子代理、Vision、Tool continuation 是否冻结同一完整 route identity；
- 运行中切换 UI active profile 不得改变已启动 Run；
- Retry 只在同一路由执行，不能因 429 / 5xx / 网络失败静默切供应商或 API Key；
- capability snapshot 是否决定工具、图片、streaming、replay、temperature 等能力；
- 已知不支持能力是否在网络请求前拒绝；
- 成功回复、Token 和计费事实是否记录可区分但不泄密的实际 route identity；
- 未知 / 第三方路由不能套用错误官方价格。

#### 凭据、认证与账户状态

检查：

- API Key 与 ChatGPT 套餐 profile / credential 是否隔离；
- OAuth callback 编码、state、nonce、PKCE、ID Token 验证是否完整；
- access token refresh 是否 single-flight；
- refresh token 轮换后是否原子替换；
- “身份已登录”与“具备套餐推理 scope”是否分开建模；
- scope 降级后是否先保存新 token / scope，再退休套餐 Profile；
- 活动套餐失效时是否明确变为未配置，禁止静默回退到可能产生额外计费的 API Key。

#### 协议、流式与兼容

检查：

- request / response / stream event / terminal event / error 的完整契约；
- system / user / tool 输入是否满足各协议必填项；
- tool call 与 tool result 是否稳定配对；
- continuation 只用于明确 eligible 的 post-admission 失败，并有次数上限；
- cancellation 是否传播到真实 HTTP / stream / tool 工作；
- 未知 JSON 字段是否按契约宽松处理；
- 未知事件 / 内容类型是否保留 passthrough 或诊断信息；
- 缺失可选能力是否按 capability unavailable 处理；
- 协议基线升级是否同步代码、fixture、锁定来源和一致性测试。

#### Tool / MCP / 网络副作用

检查：

- Tool / MCP 是否经过统一 Registry、Approval、Resource 和 Security Policy；
- 只读 / 计划作用域是否真的不能执行状态修改工具；
- 网络工具是否按真实方法和参数判断副作用；
- 外部进程、MCP stdio、LSP 的启动 / 停止 / 超时 / 取消是否闭环；
- 文件和网络结果是否有大小上限，二进制响应是否走文件 / 下载能力；
- 非安全 HTTP 方法是否禁止自动跟随重定向；
- 大工具结果是否有界预览，不把无界正文直接塞入模型上下文；
- 工具 Schema 是否侵占上下文；
- 是否重复发送不必要历史。

### 4.5 性能、规模化与资源控制

至少考虑：

- 1k / 10k / 50k Event；
- 大量 Session；
- 大量 Memory；
- 大量 Persona / Story；
- 长 Story；
- 多人群聊；
- 大量 Automation / Job；
- 大量 MCP Tool；
- 深目录；
- 大文件；
- 长时间后台运行。

重点识别：

- O(N) / O(N²)；
- 全量 scan / fold / sort / copy；
- 整体 serialize / decode；
- 冷数据进入热路径；
- 结果有界但工作量无界；
- 每条 Event / Progress / Token 都触发 IO；
- 高频 fsync；
- 巨型缓存或无界队列。

所有可增长结构和后台任务都必须回答：

- 数量上限；
- 字节上限；
- Token 上限；
- 时间上限；
- 并发上限；
- 扫描上限；
- 重试上限；
- 缓存淘汰；
- 归档；
- backpressure。

特别要求：

> 不能只限制“最多返回多少结果”，还必须限制“为了得到这些结果最多做多少工作”。

性能审计必须区分：

- 冷启动 / 热路径；
- 缓存命中 / 未命中；
- 小数据 / 大数据；
- 单任务 / 并发任务；
- 前台 / 后台；
- 真机 / JVM 测试。

同时检查：

- 峰值内存与对象复制；
- GC / OOM 风险；
- 磁盘读写次数和写放大；
- 网络请求次数与重复拉取；
- 解压 / 解析 / JSON 查询的输入上限；
- 缓存容量、作用域、失效和淘汰；
- 后台耗时、唤醒和电量影响；
- 性能优化是否改变正确性或恢复语义。

### 4.6 用户体验与产品正确性

检查：

- 发送反馈；
- 排队；
- 运行中；
- 取消；
- 失败；
- 重试；
- 恢复；
- 自动任务；
- 后台任务；
- 群聊；
- 模型 / 账户切换；
- Session 切换；
- 数据损坏。

重点判断：

- UI 是否真实反映底层状态；
- 用户是否能区分进行中、成功、失败和等待；
- 页面切换、重开、恢复后是否连续；
- 后台执行与前台展示是否一致；
- 是否提示成功但实际没有完成；
- 是否错误后无恢复入口；
- 是否增加重复操作、误操作或学习成本；
- 最后一公里是否完整；
- 技术实现正确时，用户体验是否仍然不合理。

用户体验属于功能正确性，不作为“纯 UI 问题”降级处理。

设备级至少检查适用项：

- loading / empty / error / partial success / retry 状态；
- 群聊部分失败、全部失败、单成员重试；
- Worker / 后台任务更新是否实时投影；
- 运行中心是否展示完整任务事实；
- 输入法展开、输入框扩展、长消息时最后内容是否仍可见；
- Back / Drawer / restore / 页面跳转 / 媒体或权限返回；
- TalkBack 状态和可访问名称；
- 130% 字号与系统大字；
- 长时间线与大量列表项；
- 明 / 夜 / 墨主题及高对比壁纸；
- 权限拒绝、离线、网络恢复、账户失效后的可恢复入口。

涉及这些体验的改动，静态截图或 JVM 单测不能替代真实设备复验。

### 4.7 工程质量、测试、可观测性与安全

#### 健壮性

覆盖：

- null；
- 非法输入；
- 极端输入；
- timeout；
- 429 / 5xx；
- 网络失败；
- 磁盘满；
- 文件损坏；
- malformed data；
- 旧版本数据；
- 权限失败；
- 并发冲突；
- 半写状态。

禁止只覆盖 happy path。

#### 可读性与可维护性

检查：

- 超大文件 / 函数；
- 参数过多；
- 状态过多；
- 隐式副作用；
- 命名不准确；
- 注释与行为不一致；
- workaround 无退出机制；
- 兼容代码残留；
- 重复逻辑；
- 魔法数字；
- 隐含调用顺序；
- 修改局部功能需要改多个无关模块。

#### 可扩展性

假设新增：

- 模型供应商；
- 认证方式；
- Tool；
- MCP Server；
- Persona 功能；
- Memory 类型；
- Automation 类型；
- Store Backend；
- Session 类型。

判断是“新增模块即可接入”，还是“继续修改核心大类 / 巨型 when”。

#### 可测试性

检查核心逻辑是否：

- 可独立单测；
- 可注入 clock / store / model；
- 可模拟 crash window；
- 可模拟并发；
- 可模拟取消；
- 可模拟重启恢复；
- 可模拟多账户；
- 可模拟迟到回调。

反查测试是否只验证结果正确，却没有验证：

- IO 次数；
- 扫描量；
- 内存峰值；
- 恢复一致性；
- 多账户隔离；
- 长时间运行；
- 大规模性能；
- 所有真实入口；
- 旁路和消费者。

#### 可观测性

系统必须能回答：

- 哪个 Session；
- 哪个 Run；
- 哪个 Agent；
- 哪个 Tool；
- 哪个模型 / 账户 / Route；
- 哪一步；
- 耗时；
- Token；
- IO；
- Retry；
- Recovery；
- Partial Success；
- 状态在哪里变化。

同时检查：

- 日志是否过量；
- 是否保存敏感正文；
- 是否泄露 Token / API Key；
- 是否为诊断复制完整 Prompt；
- 诊断本身是否拖慢系统。

#### 验证与放行证据

根据改动范围选择当前 `docs/VALIDATION.md` 规定的验证路径，不能自行降低。

产品源码 / 资源 / Gradle / Runtime 等完整产品改动，至少核对适用的：

- static-gates；
- architecture-3-gates；
- unit-tests / conformance；
- arm64 构建 / lint / APK；
- x86_64 device artifacts；
- Android 16；
- Android 17；
- merge-gate。

额外规则：

- 官方 fixture / 上游锁定来源变化必须经过 fixture provenance / reference-validation；
- 协议改动必须覆盖全部已注册协议的同一组语义契约；
- UI / UX 风险必须做设备复验；
- 只通过静态门禁不能推导单测、APK、设备或视觉体验通过；
- 所有验证必须属于同一最新 Head；
- Head、main、依赖、配置、fixture 或门禁变化后，旧验证结果作废；
- 测试应验证状态、持久化、副作用次数、取消、恢复、身份隔离等真实不变量，不能只断言返回值。

#### 安全性

重点：

- API Key / OAuth / Relay Token；
- ChatGPT 账户；
- MCP；
- Shell；
- 文件系统；
- Session；
- Memory；
- 日志；
- URL / HTTP / 下载；
- 插件。

查找：

- 权限旁路；
- Store 绕过；
- Shell 越界；
- 路径穿越；
- 跨会话数据泄露；
- 未脱敏日志；
- 敏感数据进入模型；
- Credential 生命周期错误；
- 静态黑名单代替真实边界；
- API Key / OAuth token 未使用正确安全存储；
- 完整凭据进入 Prompt、Session EventLog 或普通诊断；
- OAuth 未验证 state / nonce / PKCE，或 callback 暴露到 LAN；
- 文件路径未规范化，递归操作可经 symlink 越出工作区；
- 只读子代理仍可调用有副作用工具；
- MCP / LSP / Shell 外部进程绕过审批或取消边界；
- 非安全 HTTP 方法自动跟随重定向；
- 大型 / 二进制响应无界进入内存或模型上下文。

## 5. 多轮联审执行顺序

### 第一轮：系统地图与权威基准

建立：

- 核心模块；
- Owner；
- 数据源；
- 配置源；
- 主要 Coordinator / Registry / Store；
- 主调用链；
- 旁路；
- 热点大文件；
- 公共基础能力。

目标：找到最可能成为公共短板的位置。

### 第二轮：功能、架构与契约

逐条审：

- Chat；
- Work；
- Group Chat；
- Subagent；
- Automation；
- Webhook；
- Session；
- Memory；
- Persona / Gallery；
- Model；
- Tool / MCP；
- Remote Harness。

每条同时做：

- 横向一致性；
- 纵向全链路；
- 所有权与依赖；
- 4.21 契约逐项对账；
- 共享配置与重复规则检查。

### 第三轮：数据、状态、持久化与恢复

统一审：

- 唯一事实源；
- EventLog；
- Store；
- Snapshot；
- 字段 / Schema；
- migration；
- generation / version / CAS；
- Recovery；
- 删除与迟到写。

### 第四轮：生命周期、并发、异步与外部能力

专门模拟：

- 切 Session；
- App 后台；
- App 被杀；
- 重启；
- 网络断开；
- 取消；
- timeout；
- 迟到结果；
- 重复点击；
- 多账户切换；
- 配置中途变化；
- Store corruption；
- 副作用未知。

同时核模型、凭据、Tool / MCP 的身份与路由一致性。

### 第五轮：规模化与资源

专门找：

- 长会话；
- 大 Store；
- 全量扫描；
- 整库重写；
- 高频 fsync；
- 冷热数据混放；
- 无界队列 / 缓存；
- 结果有界但工作量无界。

### 第六轮：用户体验、工程质量、安全与观测

核：

- 最终用户状态；
- 失败与恢复入口；
- 可测试性；
- 健壮性；
- 可维护性；
- 可扩展性；
- 权限边界；
- 日志脱敏；
- 可观测性。

### 第七轮：候选问题逐条复核

每个候选继续追：

```text
入口
→ 调用方
→ Owner
→ 状态 / 配置
→ 数据
→ 下游
→ 异常路径
→ 测试
→ 用户最终结果
```

确认后才进入最终问题清单。

不确定的问题不要硬列；误报必须主动撤回。

### 第八轮：基准与回归复核

输出前重新确认：

- main 是否变化；
- PR Head 是否变化；
- 当前问题是否仍存在；
- 是否已经被其他提交解决；
- 是否与已有问题重复；
- 是否只是同一根因的另一种表象；
- 修复是否引入新旁路、新事实源或新配置副本。

### 第九轮：共享结论提炼与复核

最终问题清单稳定后，再判断哪些结论具备跨功能复用价值：

```text
本次具体问题
→ 根因归并
→ 与现有共享结论对照
→ 已有结论：引用并补本次证据
→ 新规律：建立独立共享结论
→ 重复规律：合并
→ 已失效规律：标记废弃 / 替代
```

要求：

- 具体问题继续保留本次文件、调用链和代码证据；
- 共享结论不复制整份具体问题，只记录可复用规律、适用范围、核查动作和完成标准；
- 每条共享结论必须可独立引用、独立执行、独立判定；
- 不把尚未核实的推测沉淀为共享结论；
- 不能因为已有共享结论就跳过当前代码核实。

## 6. 问题分类

每个问题至少标记一类：

- 局部 Bug；
- 链路闭环 / 契约一致性问题；
- 最后一公里；
- 架构 / 所有权问题；
- 数据模型 / 字段问题；
- 配置 / 定义漂移；
- 生命周期问题；
- 并发问题；
- 持久化 / 恢复问题；
- 性能 / 资源问题；
- 用户体验问题；
- 安全问题；
- 可观测性问题；
- 测试盲区；
- 功能设计问题。

同一问题可有多个分类。

---

## 7. 问题优先级

### 高

满足任一：

- 数据丢失 / 状态错误；
- 安全边界失效；
- 跨账户 / 跨会话串线；
- 重复副作用；
- 恢复语义错误；
- 公共底层短板拖累多个核心功能；
- 长期使用必然严重退化。

### 中高

- 功能主路径可用但关键边界不完整；
- 大规模或长期使用明显恶化；
- 跨 Store 一致性缺口；
- 背景任务 / Automation / 恢复存在重要最后一公里；
- 架构持续扩展风险较高；
- 多功能共享配置或规则存在多事实源。

### 中

- 有明确性能 / 维护 / 体验问题；
- 触发需要一定规模或特定场景；
- 不立即破坏核心正确性。

### 低

- 长期积累型轻度问题；
- 当前影响较小但有明确治理价值。

## 8. 每个问题的输出模板

### 【优先级】问题标题

**涉及文件 / 模块**

列出关键位置。

**当前实现**

准确说明当前代码怎么工作。

**具体问题**

说明实际缺陷，不写泛泛评价。

**根因**

追到数据模型、生命周期、所有权、架构边界或公共基础能力。

**关联共享结论**

如适用，引用 `SC-xxx`；如本次形成新的可复用规律，在具体问题之外单独新增共享结论。

**完整影响链路**

例如：

```text
用户操作
→ Chat
→ EventLog
→ Post-turn
→ Gallery
→ 下一轮 Context
```

**会拖累哪些其他功能**

列出横向影响。

**触发场景**

说明什么规模、状态或操作会触发。

**用户实际感知**

说明最终体验。

**长期风险**

说明数据量 / 功能增长后会怎样。

**现有测试为什么可能发现不了**

说明测试盲区。

**验证证据 / 复现证据**

写明用于确认问题存在的代码事实、运行事实、持久化事实、测试或设备证据；同时说明验证对应的 Head。

**误报排除**

写明已经核掉哪些看似相关但实际正常的路径，避免后续重复报告。

**根治方向**

给出推荐的结构性方案，不只给临时补丁。

## 9. 最终汇总要求

输出：

```text
总问题数
├─ 高
├─ 中高
├─ 中
└─ 低
```

随后按根因归并，例如：

- 所有权与依赖；
- 功能链路与契约；
- 状态与事实源；
- 字段 / Schema；
- 配置与共享规则；
- 持久化与恢复；
- 并发与资源调度；
- 模型身份与凭据生命周期；
- Context 与 Token；
- 权限与安全边界；
- 可观测性；
- 性能规模化；
- UI / 用户体验；
- 测试盲区。

最终必须明确指出：

1. 当前最限制系统上限的公共短板；
2. 哪些问题可以一起治理；
3. 哪些修复顺序存在依赖；
4. 哪些问题属于安全 / 数据正确性，应排在纯性能优化之前；
5. 哪些根因修复后能同时消除最多关联问题；
6. 本次复用了哪些共享结论；
7. 本次新增、合并、替代或废弃了哪些共享结论；
8. 本次发现了哪些跨功能通用配置，哪些应统一提取，哪些因明确领域 / 平台 / 协议差异继续独立维护。

## 10. 联审批判原则

### 必须

- 基于最新全量代码；
- 多轮联审；
- 先整体后局部；
- 横向 + 纵向；
- 功能 + 代码同时审；
- 代码 + 数据 + 状态 + 配置 + 生命周期同时审；
- 性能 + 体验 + 安全同时审；
- 每个候选问题继续追调用链；
- 已解决问题不列；
- 重复问题合并；
- 误报撤回；
- 最终再次锁基准；
- 读取并逐项复核共享审计结论库；
- 将可跨功能复用的稳定结论独立沉淀，不与本次具体问题混写。

### 禁止

- 只 grep 一轮就下结论；
- 只查 TODO / FIXME；
- 只看大文件；
- 只看单测是否通过；
- 只看某个函数“代码正确”；
- 只看 happy path；
- 只列代码风格问题；
- 把设计取舍误报成 Bug；
- 用旧代码结论代替当前事实；
- 将同一根因拆成大量重复条目；
- 为了“数量多”降低问题质量；
- 发现多处相同配置却不判断是否应统一；
- 为了统一而破坏 Feature 所有权，把无关配置塞进巨型全局对象。

---

## 11. 最终判定标准

全量联审最终必须从“单点 Bug 清单”提升为“系统能力瓶颈清单”。

真正需要回答的是：

> 哪些代码和功能目前只是“能用”？
>
> 哪些已经成为其他功能的短板？
>
> 哪些会随着长期使用必然退化？
>
> 哪些数据、状态、配置、权限和生命周期存在跨链不一致？
>
> 哪些根因修复后，可以同时提升多个功能和整个系统上限？

只有回答到这一层，才算完成全量系统联审。
