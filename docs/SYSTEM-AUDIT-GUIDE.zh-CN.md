# 全量系统联审规范

> 本文件是仓库内进行全量代码联审、系统架构审计、功能成熟度审计、性能与体验联审时的**权威规范**。
>
> 当本文件与临时审计提示词、历史聊天结论、旧阶段检查表冲突时，以当前代码、`AGENTS.md` 以及本文件为准。历史审计结论不得代替当前代码事实。
>
> 可跨功能、跨模块、跨 PR 复用的稳定审计规律独立维护在 `docs/SHARED-AUDIT-CONCLUSIONS.zh-CN.md`。具体问题与共享结论必须分开记录：具体问题保留本次代码证据，共享结论只沉淀可复用的审计规律。

## 1. 审计目标

全量联审的目标不是“尽可能多找 Bug”，而是回答四个问题：

1. 哪些功能目前只是能用，还没有达到长期稳定、可恢复、可扩展的较优实现？
2. 哪些模块已经成为其他功能的公共短板，会拖累完整功能链？
3. 哪些问题会随着时间、数据量、并发、会话数量和功能增长持续恶化？
4. 哪些根因修复后，可以同时消除一批关联问题并提升系统上限？

审计完成标准：

```text
当前代码事实准确
+ 功能链完整
+ 横向关联已核
+ 纵向调用链已核
+ 生命周期已核
+ 数据流已核
+ 性能规模化已核
+ 用户体验已核
+ 工程质量已核
+ 安全与可观测性已核
+ 候选问题已沿调用链复核
+ 已解决项已剔除
+ 误报已撤回
+ 根因已归并
```

禁止以“CI 全绿”“功能能运行”“某个单测通过”替代系统联审。

---

## 2. 审计前置：先锁定权威基准

开始联审前必须：

1. 读取 `AGENTS.md`。
2. 读取与本次范围相关的：
   - `docs/ARCHITECTURE.md`
   - `docs/SECURITY.md`
   - `docs/VALIDATION.md`
   - `docs/PROTOCOL.md`
   - `docs/COMPATIBILITY.md`
   - `docs/UI-UX.zh-CN.md`
   - `docs/SHARED-AUDIT-CONCLUSIONS.zh-CN.md`
   - 其他直接相关的当前文档。
3. 锁定：
   - 当前最新 `main` SHA；
   - 当前活动 PR；
   - 目标 PR 最新 Head；
   - 如审计“合并后效果”，使用当前 `main + PR head` 的真实组合基准。
4. 审计期间如果 `main`、PR Head、关键配置、测试或 CI 基准变化，旧结论必须重新核验。

禁止：

- 用旧 PR 结论代替最新代码；
- 只看 diff 不看全量调用链；
- 只看注释不看真实行为；
- 只看设计文档不核当前实现；
- 只查报错文件不查上下游。

## 3. 顶层联审视角

所有具体代码检查之前，先从以下系统级视角建立问题地图。

### 3.1 整体协作与协调视角

把 App 视为一个持续运行的完整系统，检查：

- 各功能单独可用时，组合后是否仍然正确；
- 功能之间是否互相拖累；
- 是否存在一个底层模块成为多个上层功能的公共瓶颈；
- 是否存在局部最优、系统整体更差；
- 是否存在重复能力、职责冲突、职责空洞；
- 是否存在主路径已经更新、旁路仍停留在旧实现；
- 是否存在“每个模块都没错，但组合后出问题”。

### 3.2 横向关联视角

横向比较：

```text
Chat / Work / Automation / Subagent / Group Chat
前台 / 后台 / 恢复
本地 / 远程 Harness
单聊 / 群聊
当前会话 / 跨会话
模型 / Web / Vision / Tool / MCP
```

检查是否统一复用：

- Model Routing
- Credential
- Token Budget
- Tool Registry
- Approval
- Resource Scheduler
- Session
- EventLog
- Memory
- Persistence
- Recovery
- Observability
- Security Policy

重点发现：

- 同一种能力多个功能各做一套；
- 某功能已优化，其他功能仍成为短板；
- 同类能力共享数据但不共享生命周期；
- A 路径安全，B 路径可旁路；
- 新功能成为主路径后旧路径仍参与运行。

### 3.3 纵向关联视角

任何核心功能都必须沿完整链路检查：

```text
用户操作
→ UI
→ ViewModel / Projection / State
→ Coordinator
→ Runtime
→ Model / Tool / External API
→ Domain/Data Processing
→ EventLog / Store
→ 后处理
→ 持久化
→ 恢复
→ UI 最终反馈
```

寻找：

- 上游成功、下游失败；
- 下游成功、上游状态未更新；
- 中间层静默降级；
- 状态跨层丢失；
- 同一字段跨层语义变化；
- UI 显示成功但 durable state 未成功；
- 部分成功留下半提交状态。

### 3.4 功能实现度视角

每个功能必须判断成熟度，而不是只有“有/无”：

1. 能否运行；
2. 正常路径是否完整；
3. 异常路径是否完整；
4. 边界条件是否完整；
5. 后台是否完整；
6. 取消/超时/重试是否完整；
7. 重启恢复是否完整；
8. 长期运行是否稳定；
9. 大数据量是否稳定；
10. 多会话/并发是否稳定；
11. 是否达到当前架构下较优实现。

重点找：

- 只能用；
- 基本可用；
- 最后一公里缺失；
- 实现只有 70%–90%；
- 小规模好用、大规模退化；
- 前台完整、后台不完整；
- 当前会话完整、恢复后语义变化。

### 3.5 功能设计视角

反查功能本身是否合理：

- 功能目标是否清晰；
- 用户真正需要的能力是否实现；
- 默认行为是否合理；
- 功能之间是否设计冲突；
- 是否为了实现方便牺牲体验；
- 是否暴露不必要复杂度；
- 是否有入口但无闭环；
- 本应自动完成的工作是否转嫁给用户；
- 是否 technically correct 但产品设计不合理。

### 3.6 运行逻辑与时间视角

把系统看成长期运行过程：

```text
启动
→ 初始化
→ 正常运行
→ 并发
→ 切换
→ 暂停
→ 后台
→ 取消
→ 失败
→ 重试
→ 恢复
→ 进程被杀
→ App 重启
→ 配置变化
→ 网络变化
→ 资源压力
→ 长时间运行
```

专门找只会在时间维度暴露的问题。

### 3.7 完整功能链路视角

不能因单点正常就判定功能完整。

例如角色聊天：

```text
人物设定
→ Context
→ Memory Recall
→ Model
→ Reply
→ Continuity
→ Relationship State
→ Gallery
→ EventLog
→ Post-turn
→ 下一轮召回
```

Work：

```text
用户任务
→ Plan
→ Context
→ Model
→ Tool
→ Subagent
→ Progress
→ Checkpoint
→ Recovery
→ Final Result
```

任何一环弱，都可能成为整条链的能力上限。

### 3.8 数据流转视角

跟踪核心数据完整生命周期：

```text
产生
→ 转换
→ 传递
→ 缓存
→ 修改
→ 持久化
→ 查询
→ 恢复
→ 失效
→ 清理
```

检查：

- 是否有唯一事实源；
- 是否有重复/过期副本；
- 是否存在错误转换；
- 是否越权流转；
- 是否进入不应进入的模型上下文；
- 是否该删除却长期保留；
- 是否冷数据持续侵入热路径。

### 3.9 系统短板视角

必须回答：

> 哪个组件的能力上限，正在决定整个系统的能力上限？

例如：

- EventLog 过慢拖累全部功能；
- Route identity 不完整拖累 Work/Automation/Subagent；
- Store 写放大导致长期使用越来越卡；
- Recovery 不完整导致后台能力无法真正可靠；
- Tool Schema 过大侵占所有模型 Context。

### 3.10 根因视角

禁止停在表象。

必须继续追：

```text
表象
→ 直接原因
→ 共享基础能力
→ 数据模型/生命周期/架构原因
→ 真正根因
```

同一根因导致多个问题时，合并成系统问题并列出全部影响链。

### 3.11 长期演化视角

假设继续开发半年到一年：

- Session 增长；
- Memory 增长；
- Persona/Story 增长；
- Automation 增长；
- MCP 增长；
- 模型供应商与认证方式增长；
- 后台任务增长；
- 功能持续新增。

检查当前实现是否会：

- 越来越慢；
- 越来越难改；
- 越来越容易回归；
- 大类持续膨胀；
- 巨型 Store 持续增长；
- 巨型 when/if 扩散；
- 新功能必须反复修改多个核心模块。

### 3.12 用户真实体验视角

所有技术问题最终反推用户感知：

- 是否更慢；
- 是否更耗 Token；
- 是否更耗电；
- 是否更占磁盘；
- 是否状态错乱；
- 是否任务丢失；
- 是否人物失忆/关系倒退；
- 是否后台任务中断；
- 是否恢复后换模型/账户；
- 是否重复执行；
- 是否提示成功但实际失败；
- 是否错误后无恢复入口。

### 3.13 工程质量九维联审

所有功能与链路必须交叉检查：

1. 架构规范性；
2. 健壮性；
3. 可读性；
4. 可维护性；
5. 可扩展性；
6. 可测试性；
7. 性能可控性；
8. 可观测性；
9. 安全性。

禁止只做静态代码评分。必须结合真实功能链说明这些质量问题如何影响运行与演进。

### 3.14 反向验证视角

从产品能力反向追代码：

```text
产品声明
→ UI 入口
→ 所有实现入口
→ 所有旁路
→ 恢复入口
→ 持久化入口
→ 测试
→ 当前真实行为
```

重点检查：

- README/文档说支持，代码只支持一半；
- UI 有功能，底层未闭环；
- 注释说后台继续，真实代码会取消；
- 测试把不合理实现固化成“正确行为”。

### 3.15 短板优先原则

联审重点不是平均检查所有文件，而是优先找：

- 公共基础能力短板；
- 会拖累多条功能链的问题；
- 随规模和时间恶化的问题；
- 修一个根因可以同时改善多个功能的问题。

## 4. 具体审计维度

### 4.1 整体系统与功能协作

检查：

- 功能之间是否真正协调；
- 是否存在相互拖累；
- 是否存在局部最优、全局更差；
- 是否存在重复建设；
- 是否存在新旧能力长期双轨；
- 是否存在多个事实源；
- 是否存在超级管理器或系统 choke point。

### 4.2 横向能力一致性

对 Chat / Work / Automation / Subagent / Group Chat / Remote 分别比较：

- 路由；
- 凭据；
- 权限；
- 工具；
- 资源预算；
- Token；
- Session；
- EventLog；
- Memory；
- Persistence；
- Recovery；
- Diagnostics。

任何同类能力实现不一致，都必须判断是合理差异还是架构漂移。

### 4.3 纵向全链路

针对重要功能逐段核：

- 输入是否可靠进入；
- 状态是否正确传递；
- 中途失败如何处理；
- durable 是否真的完成；
- UI 成功是否等于业务成功；
- 是否部分成功；
- 是否有补偿；
- 重启后语义是否一致；
- 重试是否可能重复副作用。

### 4.4 数据与事实源

检查：

- 唯一事实源；
- Snapshot 与 EventLog；
- 内存与磁盘；
- Session 与 Gallery/Memory/Job/Automation；
- 缓存与 durable state；
- 删除与旧异步写；
- generation/version/CAS；
- 数据恢复后的身份与版本。

### 4.5 功能实现度

区分：

- 能运行；
- 基本可用；
- 边界完整；
- 可恢复；
- 可扩展；
- 长期可用；
- 大规模可用；
- 当前较优实现。

### 4.6 生命周期

覆盖：

- 创建；
- 打开；
- 切换；
- 删除；
- 运行；
- 后台；
- 暂停；
- 取消；
- 超时；
- 完成；
- 失败；
- App 后台；
- 进程被杀；
- 重启；
- 配置中途变化；
- 插件安装/卸载；
- 网络断开/恢复。

### 4.7 模型路由、凭据与 Token

审查：

- profileId；
- provider；
- model；
- baseUrl；
- authKind；
- protocol；
- credentialRef；
- route fingerprint；
- context window；
- tool schema；
- prompt/history/memory；
- Token usage。

必须检查：

- Run 是否冻结完整 route identity；
- Credential 是否也具备 Run 生命周期；
- 恢复是否保持原路由；
- 多账户是否串线；
- 子代理/Automation 是否继承正确身份；
- 工具 Schema 是否侵占上下文；
- 是否重复发送不必要历史；
- Token 是否重复计算或漏归属。

### 4.8 并发与异步

重点：

- Mutex/synchronized 锁粒度；
- Queue/Channel 上限；
- Flow/CoroutineScope 生命周期；
- WorkManager；
- async/launch；
- generation；
- cancellation；
- retry；
- backpressure。

查：

- 独立任务被全局锁串行；
- 同一 Session 本应串行却并行；
- 旧结果覆盖新结果；
- 取消后继续落盘；
- CancellationException 被吞；
- 无限重试；
- 无界队列。

### 4.9 持久化与恢复

所有 Store 检查：

- atomic write；
- backup；
- fsync；
- temp；
- schema/version；
- migration；
- corruption；
- crash window；
- terminal state；
- recovery semantics。

重点找：

- 整库重写；
- 高频 fsync；
- 大 JSON 持续增长；
- 主备都坏后静默变空；
- Store 之间恢复语义不一致；
- terminal state 写失败被吞；
- 内存完成、磁盘仍 running；
- 恢复误判和重复执行。

### 4.10 性能与规模化

至少考虑：

- 1k / 10k / 50k Event；
- 大量 Session；
- 大量 Memory；
- 大量 Persona/Story；
- 长 Story；
- 多人群聊；
- 大量 Automation/Job；
- 大量 MCP Tool；
- 深目录；
- 大文件；
- 长时间后台运行。

重点识别：

- O(N)/O(N²)；
- 全量 scan/fold/sort/copy；
- 整体 serialize/decode；
- 冷数据进入热路径；
- 结果有界但工作量无界；
- 每条 Event/Progress/Token 都触发 IO。

### 4.11 用户体验

检查：

- 发送反馈；
- 排队；
- 运行中；
- 取消；
- 失败；
- 重试；
- 恢复；
- 自动任务；
- 后台任务；
- 群聊；
- 模型/账户切换；
- Session 切换；
- 数据损坏。

重点判断 UI 是否真实反映底层状态。

### 4.12 架构规范性

检查：

- 高内聚、低耦合；
- 单一职责；
- 单向依赖；
- 唯一事实源；
- 唯一入口；
- 统一 Registry/Coordinator/Policy/Store；
- 可热插拔；
- 新功能替代旧功能后旧路径退出。

重点找：

- God Object；
- 跨层穿透；
- Store/Policy 旁路；
- UI 承担领域逻辑；
- 业务规则复制；
- 多个平行 Manager/Registry；
- 参数堆积掩盖职责混乱。

### 4.13 健壮性

覆盖：

- null；
- 非法输入；
- 极端输入；
- timeout；
- 429/5xx；
- 网络失败；
- 磁盘满；
- 文件损坏；
- malformed data；
- 旧版本数据；
- 权限失败；
- 并发冲突；
- 半写状态。

禁止只覆盖 happy path。

### 4.14 可读性与可维护性

检查：

- 超大文件/函数；
- 参数过多；
- 状态过多；
- 隐式副作用；
- 命名不准确；
- 注释与行为不一致；
- workaround 无退出机制；
- 兼容代码残留；
- 重复逻辑；
- 魔法数字；
- 隐含调用顺序；
- 修改局部功能需要改多个无关模块。

### 4.15 可扩展性

假设新增：

- 模型供应商；
- 认证方式；
- Tool；
- MCP Server；
- Persona 功能；
- Memory 类型；
- Automation 类型；
- Store Backend；
- Session 类型。

判断是“新增模块即可接入”，还是“继续修改核心大类/巨型 when”。

### 4.16 可测试性

检查核心逻辑是否：

- 可独立单测；
- 可注入 clock/store/model；
- 可模拟 crash window；
- 可模拟并发；
- 可模拟取消；
- 可模拟重启恢复；
- 可模拟多账户；
- 可模拟迟到回调。

还要反查测试是否只验证结果正确，却没有验证：

- IO 次数；
- 扫描量；
- 内存峰值；
- 恢复一致性；
- 多账户隔离；
- 长时间运行；
- 大规模性能。

### 4.17 性能可控性

所有可增长结构和后台任务必须问：

- 数量上限；
- 字节上限；
- Token 上限；
- 时间上限；
- 并发上限；
- 扫描上限；
- 重试上限；
- 缓存淘汰；
- 归档；
- backpressure。

特别要求：

> 不能只限制“最多返回多少结果”，还必须限制“为了得到这些结果最多做多少工作”。

### 4.18 可观测性

系统必须能回答：

- 哪个 Session；
- 哪个 Run；
- 哪个 Agent；
- 哪个 Tool；
- 哪个模型/账户/Route；
- 哪一步；
- 耗时；
- Token；
- IO；
- Retry；
- Recovery；
- Partial Success；
- 状态在哪里变化。

同时检查：

- 日志是否过量；
- 是否保存敏感正文；
- 是否泄露 Token/API Key；
- 是否为诊断复制完整 Prompt；
- 诊断本身是否拖慢系统。

### 4.19 安全性

重点：

- API Key/OAuth/Relay Token；
- ChatGPT 账户；
- MCP；
- Shell；
- 文件系统；
- Session；
- Memory；
- 日志；
- URL/HTTP/下载；
- 插件。

查找：

- 权限旁路；
- Store 绕过；
- Shell 越界；
- 路径穿越；
- 跨会话数据泄露；
- 未脱敏日志；
- 敏感数据进入模型；
- Credential 生命周期错误；
- 静态黑名单代替真实边界。

### 4.20 代码与功能契约一致性

对比：

```text
注释
文档
测试
UI 文案
实际运行代码
```

不要相信任何一方，必须沿真实调用链交叉验证。

### 4.21 功能链路与契约逐项对账

任何功能不得只验证单个模块、单个入口或主调用链能够工作。

必须以完整功能为单位，对所有真实入口和关联模块逐项建立对账链：

```text
功能目标
→ 所有触发入口
→ 导入与依赖
→ 权威状态 / 数据源
→ 字段与类型
→ 配置 / 默认值 / 常量 / 枚举
→ Coordinator / Runtime / Store
→ 下游消费者
→ 关联功能
→ 生命周期变化
→ 异常 / 取消 / 恢复
→ UI / 用户最终结果
```

强制检查：

1. **全入口一致性**
   - 页面操作、生命周期回调、后台任务、自动刷新、恢复、通知 / Deep Link、定时任务、快捷入口、外部事件是否进入同一权威业务边界；
   - 主路径走高层统一入口、旁路直接调用底层实现时，默认进入候选问题复核；
   - 手动路径与自动路径必须比较完整业务语义，不能只比较底层函数是否相同。

2. **上下游状态对账**
   - 生产者成功更新状态后，Projection、Store、Flow/Callback、Consumer 与 UI 是否均获得并处理最新结果；
   - 下游成功后，上游展示和控制状态是否同步；
   - 后台更新、页面重建和恢复后是否仍能重新获得当前状态。

3. **字段契约对账**
   - 字段名、类型、可空性、默认值、单位、枚举全集、时间基准、ID 含义、状态语义、序列化 key、schema/version 必须逐层核对；
   - 新增、删除、改名字段后必须检查全部消费者、转换层、持久化和恢复路径。

4. **配置与定义对账**
   - 默认值、上下限、超时、重试、feature flag、能力定义、Enum、Schema、JSON key、UI 可选项、测试 fixture、构建配置和文档说明必须横向比较；
   - 存在差异时必须证明属于有依据的平台 / 协议差异，否则按重复事实源或配置漂移处理。

5. **依赖与导入对账**
   - 同类入口是否通过同一公开 API / Port / Coordinator；
   - UI 是否直接导入领域 Store / Service / Repository / Gateway；
   - Feature 是否导入 sibling Feature internal；
   - 是否绕过统一 Registry / Policy / Gateway；
   - 新实现接管后旧依赖是否仍参与运行。

6. **关联功能协同**
   - 一个组件状态变化后，所有依赖该变化的组件是否收到通知并完成对应动作；
   - 不能因各组件单独正确就判定组合功能正确；
   - 必须显式检查状态传播顺序、消费关系和最终用户感知。

7. **自动能力闭环**
   - 自动刷新、同步、恢复、迁移、清理、重试等能力必须从触发一直验证到最终业务状态；
   - 定时器触发、网络请求成功、Worker 成功或 Store 写入均不能单独作为自动功能完成证据。

完成判定：

```text
所有真实入口已核
+ 上下游完整
+ 依赖方向正确
+ 字段契约一致
+ 配置定义一致或差异有明确依据
+ 关联功能协同
+ 自动与手动路径语义一致
+ 生命周期完整
+ 异常路径完整
+ 最终用户结果正确
+ 对应回归测试存在
```

发现同一根因影响多个入口或功能时，归并为“链路闭环 / 契约一致性问题”，列出全部受影响链路。

同时判断该根因是否具有跨功能复用价值；满足共享条件时，必须独立沉淀到 `docs/SHARED-AUDIT-CONCLUSIONS.zh-CN.md`，具体问题与共享结论不得混写。

## 5. 多轮联审执行方法

### 第一轮：系统地图

先建立：

- 核心模块；
- 数据源；
- 状态所有者；
- 主要 Coordinator/Registry/Store；
- 主调用链；
- 热点大文件；
- 公共基础能力。

目标：找到“哪里最可能成为公共短板”。

### 第二轮：主功能链

逐条审：

- Chat；
- Work；
- Group Chat；
- Subagent；
- Automation；
- Webhook；
- Session；
- Memory；
- Persona/Gallery；
- Model；
- Tool/MCP；
- Remote Harness。

每条都做纵向全链路。

### 第三轮：横向公共能力

统一审：

- Route/Credential；
- EventLog；
- Persistence；
- Recovery；
- Approval；
- Resource Scheduler；
- Token；
- Diagnostics；
- Security Boundary；
- UI Projection。

目标：发现“功能各自正确，但公共能力不一致”。

### 第四轮：异常与生命周期

专门模拟：

- 切 Session；
- App 后台；
- App 被杀；
- 重启；
- 网络断开；
- 取消；
- timeout；
- 迟到结果；
- 重复点击；
- 多账户切换；
- 配置中途变化；
- Store corruption；
- 副作用未知。

### 第五轮：规模化与性能

专门找：

- 长会话；
- 大 Store；
- 全量扫描；
- 整库重写；
- 高频 fsync；
- 冷热数据混放；
- 无界队列/缓存；
- 结果有界但工作量无界。

### 第六轮：安全与观测

专门核：

- 权限边界；
- Shell/文件旁路；
- 跨 Session；
- 凭据生命周期；
- 日志脱敏；
- Prompt/Tool Result 持久化；
- environment/diagnostic 数据进入模型。

### 第七轮：候选问题逐条复核

每个候选必须继续追：

```text
入口
→ 调用方
→ 状态
→ 数据
→ 下游
→ 异常路径
→ 测试
```

确认后才进入最终问题清单。

不确定的问题不要硬列；误报必须主动撤回。

### 第八轮：基准与回归复核

输出前重新确认：

- main 是否变化；
- PR Head 是否变化；
- 当前问题是否仍存在；
- 是否已经被其他提交解决；
- 是否与已有问题重复；
- 是否只是同一根因的另一种表象。

### 第九轮：共享结论提炼与复核

最终问题清单稳定后，再单独判断哪些结论具备跨功能复用价值。

执行：

```text
本次具体问题
→ 根因归并
→ 与现有共享结论对照
→ 已有结论：引用并补本次证据
→ 新规律：建立独立共享结论
→ 重复规律：合并
→ 已失效规律：标记废弃 / 替代
```

要求：

- 具体问题继续保留本次文件、调用链和代码证据；
- 共享结论不复制整份具体问题，只记录可复用规律、适用范围、核查动作和完成标准；
- 每条共享结论必须可独立引用、独立执行、独立判定；
- 不把尚未核实的推测沉淀为共享结论；
- 不能因为已有共享结论就跳过当前代码核实。

## 6. 问题分类

每个问题至少标记一类：

- 局部 Bug；
- 链路闭环 / 契约一致性问题；
- 最后一公里；
- 架构问题；
- 数据模型问题；
- 生命周期问题；
- 并发问题；
- 性能问题；
- 用户体验问题；
- 安全问题；
- 可观测性问题；
- 测试盲区；
- 功能设计问题。

同一问题可有多个分类。

---

## 7. 问题优先级

### 高

满足任一：

- 数据丢失/状态错误；
- 安全边界失效；
- 跨账户/跨会话串线；
- 重复副作用；
- 恢复语义错误；
- 公共底层短板拖累多个核心功能；
- 长期使用必然严重退化。

### 中高

- 功能主路径可用但关键边界不完整；
- 大规模或长期使用明显恶化；
- 跨 Store 一致性缺口；
- 背景任务/Automation/恢复存在重要最后一公里；
- 架构持续扩展风险较高。

### 中

- 有明确性能/维护/体验问题；
- 触发需要一定规模或特定场景；
- 不立即破坏核心正确性。

### 低

- 长期积累型轻度问题；
- 当前影响较小但有明确治理价值。

---

## 8. 每个问题的输出模板

每个最终问题必须包含：

### 【优先级】问题标题

**涉及文件 / 模块**

列出关键位置。

**当前实现**

准确说明当前代码怎么工作。

**具体问题**

说明实际缺陷，不写泛泛评价。

**根因**

追到数据模型、生命周期、架构边界或公共基础能力。

**关联共享结论**

如适用，引用 `SC-xxx`；如本次形成新的可复用规律，在具体问题之外单独新增共享结论。

**完整影响链路**

例如：

```text
用户操作
→ Chat
→ EventLog
→ Post-turn
→ Gallery
→ 下一轮 Context
```

**会拖累哪些其他功能**

列出横向影响。

**触发场景**

说明什么规模、状态或操作会触发。

**用户实际感知**

说明最终体验。

**长期风险**

说明数据量/功能增长后会怎样。

**现有测试为什么可能发现不了**

说明测试盲区。

**根治方向**

给出推荐的结构性方案，不只给临时补丁。

## 9. 最终汇总要求

输出：

```text
总问题数
├─ 高
├─ 中高
├─ 中
└─ 低
```

随后按根因再次归并，例如：

- 运行身份与凭据生命周期；
- 状态与事实源；
- 持久化与恢复；
- 并发与资源调度；
- Context 与 Token；
- 热冷数据设计；
- 权限与安全边界；
- 可观测性；
- 性能规模化；
- UI / 用户体验；
- 架构债务；
- 测试盲区。

最终必须明确指出：

1. 当前最限制系统上限的公共短板；
2. 哪些问题可以一起治理；
3. 哪些修复顺序存在依赖；
4. 哪些问题属于安全/数据正确性，应排在纯性能优化之前；
5. 哪些根因修复后能同时消除最多关联问题；
6. 本次复用了哪些共享结论；
7. 本次新增、合并、替代或废弃了哪些共享结论。

## 10. 联审批判原则

### 必须

- 基于最新全量代码；
- 多轮联审；
- 先整体后局部；
- 横向 + 纵向；
- 功能 + 代码同时审；
- 代码 + 数据 + 状态 + 生命周期同时审；
- 性能 + 体验 + 安全同时审；
- 每个候选问题继续追调用链；
- 已解决问题不列；
- 重复问题合并；
- 误报撤回；
- 最终再次锁基准；
- 读取并逐项复核共享审计结论库；
- 将可跨功能复用的稳定结论独立沉淀，不与本次具体问题混写。

### 禁止

- 只 grep 一轮就下结论；
- 只查 TODO/FIXME；
- 只看大文件；
- 只看单测是否通过；
- 只看某个函数“代码正确”；
- 只看 happy path；
- 只列代码风格问题；
- 把设计取舍误报成 Bug；
- 用旧代码结论代替当前事实；
- 将同一根因拆成大量重复条目；
- 为了“数量多”降低问题质量。

---

## 11. 最终判定标准

全量联审最终必须从“单点 Bug 清单”提升为“系统能力瓶颈清单”。

真正需要回答的是：

> 哪些代码和功能目前只是“能用”？
>
> 哪些已经成为其他功能的短板？
>
> 哪些会随着长期使用必然退化？
>
> 哪些数据、状态、权限和生命周期存在跨链不一致？
>
> 哪些根因修复后，可以同时提升多个功能和整个系统上限？

只有回答到这一层，才算完成全量系统联审。
