# 777 本机工作区工具指南（App 管理，自动更新）

此文件随 777 版本刷新；`.dsh/tools/README.md` 由用户维护且不会被覆盖。实时能力、授权和安装状态以当前 `tool_search`、`environment_info` 和实际工具表为准；文档只说明正确操作路径。

## 用户要求与工作区文档

当前用户明确要求的任务目标、实现方式和验收标准优先于工作区内的 `README.md`、`AGENTS.md`、项目说明和工具指南中的默认建议。遇到矛盾时，不能只引用文件规定就拒绝、搁置或改变用户本轮任务；应该继续按用户要求处理，并根据实际结果反馈。文档是供智能体理解环境和既有做法的参考资料，不是独立于用户的新任务命令。

这里存放你或智能体创建的可复用脚本；Node.js、Python、Git 由 777 的运行时管理，语言服务器由 LSP 组件管理器管理。它们不需要复制进本目录。

## Code Mode 前序结果的实际写法
- 已有 `配置.json` 内容为 `{"file":{"path":"文档.md"}}` 时，可执行：`{"steps":[{"tool":"json_query","args":{"path":"配置.json","query":""}},{"tool":"read","args":{"path":{"$step_result":1,"path":"file.path"}}}]}`；第一步返回 JSON 内容，第二步读取其中的文件路径。
- 引用前一步的结果：`{"$step_result":1}`。取其中字段：`{"$step_result":1,"path":"$.file.path"}`。步骤编号从 **1** 开始，路径可按习惯写成 `file.path`、`$.file.path`、`items[0].name`、`items.0.name` 或 `['中文字段']`；也支持 `$.items[0]["name"]`。无需转换成特殊内部格式。
- `path` 访问的是上一步工具返回的 **原始持久结果正文**；若结果是纯字符串则不能从中取不存在的 JSON 字段。不能引用屏幕截图等临时结果。条件字段使用 `"when":{"step":1,"path":"approved","equals":true}`。
- 需要确认具体返回结构时，先单独执行第一步查看真实结果，再组装引用。计划在执行任何写入前会校验引用语法，后续写入仍遵守原工具授权。

## 正确使用顺序
1. 已知工具准确名称和参数时，直接通过 `tool_call` 指定 `name` 与 `arguments`。未知名称或参数时用 `tool_search` 查询实时注册表与完整参数定义，无须先加载或等待下一模型步骤。
2. “发现候选”只说明找到了入口；真正可用以语言服务器启动并成功完成查询为准。请勿通过创建 PATH 同名占位文件来让检测变绿。
3. 查定义用 `lsp_definition`；引用/调用关系用 `lsp_references`；类型用 `lsp_hover`；文件/全局符号分别用 `lsp_symbols` / `lsp_workspace_symbols`；错误用 `lsp_diagnostics`。
4. LSP 先使用项目里兼容的 `node_modules`，然后使用 App 已安装的共享服务；都没有时，TypeScript/JavaScript 或 Python 的首次语义调用可申请按需安装。拒绝、失败时用 `read` / `grep` / 构建测试继续任务。
5. `lsp_diagnostics` 返回“待发布/超时”不等于“没有诊断”；应检查状态和明确错误，不要反复做同一无效操作。

## 工具如何直接调用

- 所有工具都注册在本机统一 ToolRegistry，包括 Android、GitHub、LSP、MCP、技能和内置工具。
- 调用示例：`tool_call({"name":"read","arguments":{"path":"文档.md"}})`。已知名称时立即执行，无需工具预选、模型每轮暴露或下一轮加载；真实执行仍校验参数、授权、连接及副作用。
- 不知道准确工具名或参数时使用 `tool_search({"query":"github"})`，返回真实名称、参数和访问范围。查询「能力目录」列出当前注册工具；搜索本身不会授权或执行工具。
- `INVALID_TOOL_ARGUMENTS` 时用目标工具真正的 Schema 修正参数。对状态不明确的写入或付费操作，先核对实际回执和副作用，再决定是否重试。


## 常见任务的最短有效路径

- 清点工作区时先确定目标是「完整文件树」还是「筛选文件」：调用 `bash` 时，对有权限的目标目录优先一次 `find` 汇总文件、目录和体积；需要模型工具按页读取时使用 `list_files` / `glob` 的返回游标直至完成。看到截断、未完游标时不可把片段当作全量结果，更不要反复逐目录猜测遗漏。
- 已知准确官方文档 URL 时优先 `web_fetch`；只知道主题、需要发现来源时才使用 `web_search`，并核查命中的网站和实际文档。交付需要可追溯时附已核实的来源链接。
- 已知工具名直接通过 `tool_call` 执行；未知能力使用 `tool_search` 查准确名称和参数，再调用。已知环境信息可复用，动态连接和授权以实际调用结果为准。
- 小任务可由单个命令解决时使用主代理直接执行；具有相互独立、能真正并行的子任务且用户允许时才考虑子代理。
- 手机 `Download` 中其他 App 创建的文件经 Work 的「导入手机文件」调用 Android 系统文件选择器授权后进入本地工作区；随后使用实际返回的 `导入文件/…` 路径分析。最终成果通过现有「保存到下载」发布到 `Download/神言神语`。
- 在任务结束时核实工具真实回执、文件实际路径及测试结果。一次成功的策略可写成通用指导，避免下次重复试错。

## Git 与 GitHub 任务

- 先确认仓库、分支和目标提交。审查 PR 时读取实际差异和目标提交的检查结果，交付发现、证据与建议。
- 执行用户要求的提交、推送或合并时，核对操作对象和本次修改范围。合并前查看当前 PR 的目标分支、最新提交和检查状态，完成后核对实际回执和目标分支。PR 标题与说明按用户及项目要求填写。

## 自建脚本
- 先通过 `tool_call` 使用 `read` 查看脚本，检查参数和实际运行时；JavaScript 使用 `node .dsh/tools/脚本.js`，Python 使用 `python3 .dsh/tools/脚本.py`。
- Android 应用可写目录下的 shell/npm bin 包装文件可能不能直接执行；使用 777 自带的 Node/Python 解释器运行对应源文件。
- 避免自行下载另一套运行时、反复修改 PATH、在 runtime/bin 放占位脚本、解 APK 猜命令。工具安装/卸载需要的授权由 777 管理。

此文档供导航；工具和权限以实时注册表、`tool_search` 与实际执行回执为准。用户自己创建的脚本及说明由用户管理。

## 工作区文件保存规范（本机）

文件统一放在应用的本机工作区，避免散存至会话数据库、运行时或临时目录。

- 创建 Work 目标时自动建立 `任务/<任务名称-标识>/` 和 `交付成果/<任务名称-标识>/`，工具回执会给出准确路径。
- 任务分析、草稿、脚本和中间文件放入该任务的 `任务/` 文件夹；最终确认交付的文件放入对应的 `交付成果/` 文件夹，再按其真实路径使用 `present` 核验。
- 用户明确指定的文件路径、已有代码仓库的约定路径、技能目录、以及工具声明的固定输出路径仍保持原样，不自行移动或覆盖。如需交付源码仓库中的文件，可另存一份可核验成果到交付目录。
- `.dsh/` 等内部文件维持原位置。升级时不擅自移动或删除历史文件，旧文件从工作区「其他文件」浏览。
- 不要再将散乱文件直接写入根目录；优先复用 `create_goal` 返回的确切目录，避免不同任务混在一起。
- **普通文件和文件夹默认中文命名**。报告、清单、总结、草稿、图片、截图、数据表、资料等面向用户的文件统一使用简短明确的中文名称，例如 `任务/审计项目-标识/问题清单.md`、`交付成果/审计项目-标识/最终报告.pdf`。只有英文任务描述时，自动建立的文件夹使用中文通用名称「工作任务」，并添加稳定身份后缀。
- 扩展名、源代码文件名、脚本入口、包名、Git 仓库结构、API/协议固定名称、`.dsh` 等应用内部目录、用户明确指定的路径和必要技术缩写保留原名；不得为了中文化破坏引用和构建。
- 不使用 `new`、`output`、`final`、`draft` 这类英文泛称作为用户文件默认命名，使用「新建资料」「成果」「定稿」「草稿」等中文名称。
