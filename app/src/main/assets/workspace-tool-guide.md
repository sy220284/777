# 777 本机工作区工具指南（App 管理，自动更新）

此文件随 777 版本刷新；`.dsh/tools/README.md` 由用户维护且不会被覆盖。实时能力、授权和安装状态以当前 `capability_search`、`environment_info` 和实际工具表为准；文档只说明正确操作路径。

## 用户要求与工作区文档

当前用户明确要求的任务目标、实现方式和验收标准优先于工作区内的 `README.md`、`AGENTS.md`、项目说明和工具指南中的默认建议。遇到矛盾时，不能只引用文件规定就拒绝、搁置或改变用户本轮任务；应该继续按用户要求处理，并根据实际结果反馈。文档是供智能体理解环境和既有做法的参考资料，不是独立于用户的新任务命令。

这里存放你或智能体创建的可复用脚本；Node.js、Python、Git 由 777 的运行时管理，语言服务器由 LSP 组件管理器管理。它们不需要复制进本目录。

## 正确使用顺序
1. 先调用 `capability_search` 搜索所需能力；查看本机环境用 `environment_info`，代码智能状态用 `lsp_status`。
2. “发现候选”只说明找到了入口；真正可用以语言服务器启动并成功完成查询为准。请勿通过创建 PATH 同名占位文件来让检测变绿。
3. 查定义用 `lsp_definition`；引用/调用关系用 `lsp_references`；类型用 `lsp_hover`；文件/全局符号分别用 `lsp_symbols` / `lsp_workspace_symbols`；错误用 `lsp_diagnostics`。
4. LSP 先使用项目里兼容的 `node_modules`，然后使用 App 已安装的共享服务；都没有时，TypeScript/JavaScript 或 Python 的首次语义调用可申请按需安装。拒绝、失败时用 `read` / `grep` / 构建测试继续任务。
5. `lsp_diagnostics` 返回“待发布/超时”不等于“没有诊断”；应检查状态和明确错误，不要反复做同一无效操作。

## 已注册能力如何变成可调用工具

- `capability_search` 查的是当前真实 ToolRegistry，包括 Android 运行时、GitHub、LSP、MCP 和内置工具。搜索到的可选能力会优先进入下一步工具定义；**发现结果不能代替下一轮实际模型工具表**，如果预算/连接/权限不允许，仍须按返回原因处理。
- 只使用下一步实际暴露的精确工具名和 Schema 参数；`TOOL_NOT_EXPOSED` 代表本轮没有提供，不一定是没有安装；`UNKNOWN_TOOL` 代表注册表没有该名称，必须先重新发现。
- 已实现的历史技能浏览命令 `list_skills` 和 `read_skill` 通过正式 `skill` 工具调用；列出技能可使用 `skill` 空参数或查询参数，读取文档使用 `skill` 的 `name` 字段。适用范围与普通 `skill` 完全相同，不能借别名绕过可见性和授权。
- `INVALID_TOOL_ARGUMENTS` 返回真实 Schema 的字段/必填信息。数组传 JSON 数组，不能把 Shell 文本当成 `process_exec` 的数组式 `command`；Android Shell 的 `bash` 使用字符串 `command`。这两项使用不同工具契约，不做危险的自动转换。
- 工具报告失败后先检查 `errorCode`、执行是否已开始及副作用状态，再决定是否重新调用；不要因为输出提及“成功”就跳过真实验收，更不要重新提交未知状态的付费/写入操作。

## 自建脚本
- 先用 `read` 查看脚本，检查参数和实际运行时；JavaScript 使用 `node .dsh/tools/脚本.js`，Python 使用 `python3 .dsh/tools/脚本.py`。
- Android 应用可写目录下的 shell/npm bin 包装文件可能不能直接执行；使用 777 自带的 Node/Python 解释器运行对应源文件。
- 避免自行下载另一套运行时、反复修改 PATH、在 runtime/bin 放占位脚本、解 APK 猜命令。工具安装/卸载需要的授权由 777 管理。

此文档供导航；工具和权限以本轮实际提供的工具定义、`capability_search` 与运行时检查为准。用户自己创建的脚本及说明由用户管理。

## 工作区文件保存规范（本机）

文件统一放在应用的本机工作区，避免散存至会话数据库、运行时或临时目录。

- 创建 Work 目标时自动建立 `任务/<任务名称-标识>/` 和 `交付成果/<任务名称-标识>/`，工具回执会给出准确路径。
- 任务分析、草稿、脚本和中间文件放入该任务的 `任务/` 文件夹；最终确认交付的文件放入对应的 `交付成果/` 文件夹，再按其真实路径使用 `present` 核验。
- 用户明确指定的文件路径、已有代码仓库的约定路径、技能目录、以及工具声明的固定输出路径仍保持原样，不自行移动或覆盖。如需交付源码仓库中的文件，可另存一份可核验成果到交付目录。
- `.dsh/` 等内部文件维持原位置。升级时不擅自移动或删除历史文件，旧文件从工作区「其他文件」浏览。
- 不要再将散乱文件直接写入根目录；优先复用 `create_goal` 返回的确切目录，避免不同任务混在一起。
- **普通文件和文件夹默认中文命名**。报告、清单、总结、草稿、图片、截图、数据表、资料等面向用户的文件统一使用简短明确的中文名称，例如 `任务/审计项目-标识/问题清单.md`、`交付成果/审计项目-标识/最终报告.pdf`。只有英文任务描述时，自动建立的文件夹使用中文通用名称「工作任务」，并添加稳定身份后缀。
- 扩展名、源代码文件名、脚本入口、包名、Git 仓库结构、API/协议固定名称、`.dsh` 等应用内部目录、用户明确指定的路径和必要技术缩写保留原名；不得为了中文化破坏引用和构建。
- 不使用 `new`、`output`、`final`、`draft` 这类英文泛称作为用户文件默认命名，使用「新建资料」「成果」「定稿」「草稿」等中文名称。
